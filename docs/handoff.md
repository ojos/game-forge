## 4. 並列作業のやり方

worktree とサブエージェントで **計 8 波・21 レーン**を走らせました（3 レーン × 4 波 →
**3 / 2 / 1 レーンの 3 波** → **3 レーンの波 1**）。**第 2 波以降、レーンどうしの所有ファイルの
衝突はゼロです。**

**波の大きさは issue の数ではなく依存で決めます。** 直近の 3 波は「バグ 3 件を並列 →
機能 2 件 → その 2 件に依存する 1 件」で、**後ろの波ほど細くなりました。**

- **所有ファイルを重ねない。** レーンごとに明示して渡す
  - **重ねるのはレーンではなく、渡す側です。** 直近の波で `test/schema.test.ts` を 2 レーンの
    所有に書いてしまいました（どちらもマイグレーションを足したため）。**渡す前に、レーンの
    所有一覧どうしを機械で突き合わせること**（`comm -12`）。今回は触った行域が離れていて
    衝突しませんでしたが、それは偶然です
- **所有一覧には「新規に足すファイル」も含めて渡す。** 直近の波で、既存ファイルを 1 つも
  触らなかったレーンが `scripts/` と `migrations/` へ新規ファイルを足し、報告では
  「所有外には触っていない」と書きました。**判断は妥当でしたが、申告としては不正確です。**
  所有の定義を「編集するファイル」ではなく「触る場所」にすること
- **`docs/product-spec.md` は誰にも編集させない。** 各レーンは文面を報告に書いて返し、
  **取り込む側が版と節番号を付けて 1 本のブランチで入れる。** これで衝突が消えました
- **マイグレーションの連番は先に割り当てる**
- **1 つの継ぎ目を触る 2 issue は同じレーンに畳む**（#28/#29、#148/#153、#164/#165、#149/#166）。
  1 issue = 1 PR は守りつつ、worktree は 1 つにして直列に出させる
- **worktree を消さない。** 再利用すると `node_modules` が残り `npm ci` を省けます
- **食い違いを作った本人へ差し戻す。** 「所有外なので取り込む側で」と言われても、
  **所有ファイルを 1〜3 個足して本人へ返す**ほうが、こちらの指摘より深い直し方が返ります
- **報告を鵜呑みにしない。** 「非コメント行は変更していない」「検査は空振りしない」は
  `diff` と変異で独立に確かめられます。**18 レーン中、申告が誤っていたのは 0 件**でしたが、
  確かめる側が確かめなかった例は 1 件ありました（下記）
- **レビュー指摘は、真偽を確かめてから本人へ返す。** 直近の波で Copilot が 6 件指摘し、
  **5 件は実在、1 件は偽陽性**でした（「正規表現が `_` を扱えない」——文字クラスに `_` が
  入っており、実際に `APP_HOST` の値を変えて赤になることも確かめました）。**偽を本人へ返すと、
  直しようのないものを直させることになります**
- **`gh pr merge` はブランチが worktree に checkout されていると「ローカルブランチを消せない」で
  終わります。** マージ自体は成功しているので、**`gh pr list` で確かめること**（エラー文言だけ
  読んで失敗と判断しない）
- **PR を出したら `gh pr checks` を見る。** `bash scripts/loop-gate.sh` は step 1 で identity を
  見るようになりましたが（#215）、**CI にしかない検査は他にもあります**
- **`gh pr create` の本文に `Closes #NNN` を書く。** 書かないと**マージしても issue が open のまま
  残ります**（直近の 5 件がそうなり、後から手で閉じました）
- **次のブランチを切る前に `git checkout main` を挟み、`git log --oneline -1` で起点を確かめる。**
  1 人で連続して PR を出すとき、**直前のブランチに居たまま `git checkout -b` すると、前の PR の
  コミットが丸ごと相乗りします**（#229 の squash に #228 の docs 64 行が入りました）。
  レビューも CI も緑のまま通ります——**どちらも「その差分が正しいか」しか見ておらず、
  「その差分がこの PR のものか」は見ていません**
- **`gh pr merge` の衝突は「ブランチが古い」とは限りません。** 上の事故では、**そのブランチの
  内容が別の PR 経由で先に入っていた**ことの現れでした。**そのまま入れると先の 2 本を巻き戻す
  ところで、衝突が唯一の防波堤でした。** 衝突を見たら **`git fetch` してから**
  `git diff origin/main` を取ること（エラー文言から原因を推測しない）。**`origin/main` は
  fetch しないと古いまま**で、確かめたいのはまさに「その間に main が動いたか」なので、
  古い写しを見ると**探している事実だけが見えません**

### 実物を通すまで、動いているかは分からない

**「プレイ経路は本番で動作」と 2 日にわたって報告していたが、実際には動いていなかった**（#180 / #181）。
根拠にしていたのは **`curl` の 200 と CSP の文字列照合**で、**どちらも CORS を評価しない。**

| 検査 | 通してしまうもの |
|---|---|
| CSP の文字列照合・`curl` | **CORS**（評価しない） |
| `SELF.fetch`（vitest の workers pool） | **HTTP のエンコード**（境界を通らない） |

**どちらも「緑だから正しい」と読める形だった。** 実ブラウザを通して初めて見え、しかも
**1 つ目を直した時点で止めていれば 2 つ目を本番でもう一度踏んでいた**（ブラウザ検査の層が
赤のまま残ったことが、それを防いだ唯一の理由）。

**配信を触ったら `scripts/check-sandbox-browser.sh` を回すこと。** 層 0 は**ブラウザ不要**で
30 秒（`GF_SKIP_BROWSER=1`）、しかも**いちばん見えにくい二重圧縮をそこで捕まえる。**

**そして、同じ根で両方向に間違えた。** 「`Accept-Encoding` の有無でサイズが違う」のを
「Cloudflare の再圧縮だろう」と流して二重圧縮を見逃し、直したあとは正しい本文を
「二重圧縮だ」と誤報した。**どちらも「経路が透過的に展開しうる」ことを勘定に入れていない。**

### 変異が当たったことを、変異の結果より先に確かめる

**第 5 波で、こちらが 3 回続けて「緑だから空振りだ」と誤読しかけた。** `sed` の綴りが
本文の整形変更で当たっておらず、**ファイルは変わっていないのに変異したつもりでいた**
（1 回はコメント行だけを書き換えていた）。**md5 か `grep` で当たったことを確かめてから
回すこと。** 当てていない変異の緑は、検査の欠陥ではなく手順の欠陥である。

**同じことを書いた本人が自分で踏んだ例もある。** #26 で足した「既定値が戻っていないこと」の
検査は、設定の読み取りを別ファイルへ移した瞬間に**何も見なくなった**（`process.env[...] ??`
という綴りを探していた）。**綴りを絞った検査は、対象の綴りが変わった日に黙って空振りする。**

### 変異が当たっても、変異が弱いと緑になる

**上の「当たったことを先に確かめる」だけでは足りません。** 波 1 の取り込みで、4.5 の
キャッシュ検査へ揮発値として `Date.now()` を混ぜる変異を当てました。**`md5` は変わって
いたのに、テストは緑でした。** 2 回の呼び出しが同じミリ秒に入っただけで、`Math.random()`
に替えると赤になりました。

**当てたことの確認と、変異の強さは別の話です。** 当たった変異の緑は、検査の欠陥とも
手順の欠陥とも読めます。**その変異が「確かめたい性質」を本当に壊しているかまで見ること。**

### 確認に使う `grep` そのものを疑うこと

**`grep` の引数は正規表現として解釈されます。** 波 1 の取り込みで
`grep -c 'builds/${sourceSha256}'` が **0 件**を返し、これを「復元できていない」と
読みかけました（テストが緑だったので矛盾に気づけました）。

**原因は `$` です。行末アンカーとして解釈されるため、`$` の後ろに文字が続く綴りは
決して当たりません。**

```
$ printf 'a$b\n' > /tmp/t
$ grep -c 'a$b'  /tmp/t   # → 0（$ が行末アンカー）
$ grep -c 'a\$b' /tmp/t   # → 1（エスケープすれば当たる）
```

**`{}` のせいだと 1 度書きましたが、違いました**（レビューで指摘され、実測して直しました。
`{}` はこの綴りでは効いていません）。**思い込んだ原因を書くと、次の人が別の綴りで同じ罠に
落ちます。**

- **変異や復元の確認には `grep -F` を使うこと**（固定文字列。`$` も `{}` も素通りします）
- **この環境の `grep` は ugrep です**（`grep --version`）。**利用者の端末（macOS）は
  BSD grep で、また別です。** スクリプトへ書く `grep` も `-F` を明示するほうが安全です
  （#210 のレビューで同じ指摘が出ました）

### 検査そのものを疑うこと

**緑の検査が何も確かめていないことがあります。** #160 で停止対象を IAM ユーザーからロールへ
移したとき、層 3 の検査は識別子を取れずに**赤**になりましたが、層 2 の検査は**消えた output（空）と
消えた環境変数（空）を突き合わせ、空どうしが一致して緑**でした。**確かめていない検査は、
確かめた証拠として読まれるぶん赤より悪い。**

**移動は 3 点セット（許可・停止・検査）です。** 検査の追随漏れは
`scripts/check-tf-output-refs.sh` が機械で見ます。
