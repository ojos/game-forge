# ループコーディング 解説ガイド

このドキュメントは、**ループコーディング**という開発ワークフローの考え方を解説します。
従来のコーディングワークフローと何が違い、なぜその違いが必要なのかを説明します。

規範（守るべきルール）の正本は [loop-workflow.md](loop-workflow.md) です。本書はその**解説版**であり、
「なぜそう定めるのか」を補足します。ルールとして参照する場合は loop-workflow.md を、
考え方を理解する場合は本書を読んでください。

## ループコーディングとは

AI エージェントが **実装 → 検証 → 修正** を自律的に反復し、**機械が「緑」と判定できる決定的な信号**に
到達したところで収束させる開発ワークフローです。

反復を人が 1 手ずつ回すのではなく、エージェントが回します。人は入口（要件・ゴール・受け入れ条件の確定）で
承認し、以降は原則自動で進みます。その代わり、**完了は人の目視ではなく、再現可能な機械判定**で決めます。

## 従来のコーディングワークフローとの違い

従来（AI 補助を含む）のワークフローは、人が主体で 1 反復ずつ回し、**完了を人の判断で決めます**。
ループコーディングは、反復をエージェントに委ね、**完了を機械判定に委ねます**。

| 観点 | 従来のワークフロー | ループコーディング |
|---|---|---|
| 反復の駆動 | 人が 1 手ずつ（書く → 実行 → 直す） | エージェントが自律反復 |
| 完了の判定 | 人の目視・レビューでの合意（儀式で通りやすい） | 機械が検証できる受け入れ信号（迂回できない） |
| 人の関与ポイント | 各反復に都度関与 | 入口（要件・acceptance 確定）で承認、以降は自動 |
| 受け入れ条件 | 文章で書く（「テストする」「動作確認する」） | 非対話で実行でき、合否が終了コードで出る形 |
| レビュー | 指摘 → 修正を人が何度も往復 | 収束を目的化し、往復を打ち切る規則を持つ |
| 典型的な破綻 | 「動くはず」で未検証のまま完了扱いが積み上がる | 収束しない反復・レビューの無限往復 |

要点は 2 つの委譲です。

1. **反復をエージェントへ委譲する** — 人は入口で承認し、以降の実装→検証→修正の回転はエージェントが担う。
2. **完了判定を機械へ委譲する** — 「緑」を人の主観ではなく、再現可能な検証で決める。

この 2 つが成立して初めて、ループは自律的に閉じます。

## なぜ機械判定に委ねるのか

人の目視や、実装したモデル自身の自己レビューは、**儀式で通過しやすい**という弱点があります。
「作業状況を更新した」「動作確認した」は、実質を検査できず、形だけ整えても通ってしまいます。
その結果、**計画されただけ・確認したつもりの作業が完了扱いで積み上がります**。

ループコーディングは、完了の定義を **機械が再現できる信号**（受け入れ検証の通過）に固定します。
これは [shared-ai-rules.md](shared-ai-rules.md) の「機構化の判断基準」に沿った選択です。受け入れ検証は
**機構が結果そのものを生む**（実際に合否を生成し、迂回できない）対象なので、指示文ではなく機構で保証します。

## ワークフローの流れ

```
入口承認（要件・ゴール・acceptance を確定）
      │  ← 人が承認。acceptance は「非対話で実行でき機械判定できる」形にする
      ▼
┌─────────────────────────────┐
│  実装 → 検証（verify）→ 修正   │  ← エージェントが自律反復
│      ▲___________緑でなければ___│     verify が「緑」になるまで
└─────────────────────────────┘
      │  ← verify が緑
      ▼
ローカル事前ゲート（受け入れ検証 → 第二意見）
      │  ← 別ベンダーのモデルで独立クロスチェック（収束優先・往復を打ち切る）
      ▼
push / PR
```

- **入口承認・以降自動**: 承認は入口で取り、通過後は自動で回す。重大変更（外部状態・不可逆・機密/公開影響）のみ実行前に承認を求める。
- **収束と打ち切り**: 反復が収束しない場合は無限に回さず打ち切り、ブロッカーとしてエスカレーションする。レビューの往復は [review-workflow.md](review-workflow.md) の収束規則で打ち切る。

## 何が「実行体」を供給するのか

ループの接地信号（受け入れ検証の機械ゲート）は、[loop-workflow.md](loop-workflow.md) の **verify ランナー契約**を満たす
実行体が供給します。この契約はツール・言語に依存せず、単体で動作することを要求します。

- **DCB（DevContainer Bootstrap）を使う場合**: この契約を満たす実行体（`verify.sh` / `acceptance.sh` / `loop-gate.sh`）が
  生成されます。操作手順は DCB のドキュメント（README の「ループコーディング支援」）を参照してください。
- **DCB を使わない場合**: verify ランナー契約を満たす手段をプロジェクト層で用意します。実装はスクリプトでも
  専用ランナーでも構いません。契約を満たせば差し替え可能です。

## まとめ

ループコーディングは、**反復をエージェントに、完了判定を機械に委譲する**ワークフローです。
その代わりに、受け入れ条件を機械が検証できる形にすること（入口の規律）と、
収束を目的化して往復を打ち切ること（出口の規律）を要求します。
この 2 つの規律があるからこそ、自律反復が破綻せず収束します。
