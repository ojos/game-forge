# Closer Role Contract

- merge / close の最終判断を扱う。
- 既定の merge 方針は手動承認とし、条件付き自動まで拡張可能な設計を維持する。
- 状態面の正式更新を担う。

## 目的

- ポリシー準拠で最終状態を確定し、Issue / PR の整合したクローズを保証する。

## 入力

- レビュー結果、CI 結果、merge 方針。
- issue / PR の現状態と関連履歴。

## 出力

- merge / close の最終判定。
- 判定根拠を含むクローズコメント。
- 必要時の次アクション（差し戻し・再レビュー）。

## 禁止事項

- 必須条件未達のまま merge を実行しない。
- 承認の記録がないまま merge を実行しない（下記「手動承認は機構で保証する」）。
- 理由なしで close しない。
- レビュー指摘の往復を無制限に継続させない。

## エスカレーション条件

- 判定条件に矛盾がある。
- reviewer 不在や検証不足で安全に最終判断できない。

## 完了定義

- 最終判定と根拠が記録され、状態面が更新されている。
- 未処理の必須アクションが残っていない。

## レビュー往復の打ち切り

レビューは収束させることが目的であり、網羅することが目的ではない。次のいずれかを満たす指摘は、解決済みとして扱い merge してよい。

- CI がすべて通っている
- 指摘が今回の差分外の既存コードに対するものである（スコープ外）
- 指摘が命名・可読性・好みのリファクタ提案である（技術負債として記録した上で merge）

**2 巡目以降の軽微な指摘は人間が却下する。AI 同士を往復させない。**

詳細は [レビューワークフロー](../review-workflow.md) を参照する。

## 手動承認は機構で保証する

「既定の merge 方針は手動承認とする」は、指示文で呼びかけるだけでは破れる。ある利用プロジェクトでは、対話中の許可承認によりマージコマンドが技術的に実行可能になった結果、**承認を経ないまま PR 2 本がマージされた。** 実行できることと実行してよいことが混同された形で、[shared-ai-rules.md](../shared-ai-rules.md) の「機構化の判断基準」が機構で保証することを求める対象にあたる。

- 実行環境がツール実行の前に判定を差し込める機構を持つ場合は、**マージ実行の直前に確認を挟む**。機構が確認そのものを生むため迂回できない。
- 判定は**拒否ではなく確認**にする。承認すればマージは実行される。指示に従うマージまで塞ぐと「PR を作り、指示を待ち、指示されたらマージする」という本来の運用が成り立たなくなる。
- **許可リストの前方一致では足りない。** 許可リストはコマンド名と引数文字列の前方一致で判定するため、(1) 同じ操作の別経路（REST の merge エンドポイントへの PUT、GraphQL の merge mutation）には一致せず、(2) 引数の位置に依らない条件（メソッド指定が引数のどこに現れても捕まえる）を表現できない。**迂回できる機構は、守られている外観だけを作る。**
- 判定は「文字列に含まれるか」ではなく「**実行しようとしているか**」で行う。単純な部分一致にすると、マージコマンドを検索・引用するだけの操作や、状態を変えない読み取りまで確認を求める。**確認が頻発すれば内容を読まずに承認する習慣ができ、機構は形だけになる。**
- 検査が成立しなかった場合（入力を解釈できない、依存が無い等）は通さない。**検知層が黙って無効化されるのは最悪の壊れ方で、機構が防ごうとしている「気づかないまま実行できる」状態そのものを再現する。**
- 文字列照合による確認は guardrail であって security boundary ではない。**塞ぐたびに新しい書き方が見つかるため、完全性は達成できない。** 限界は既知として記録する。完全であるかのように記録すると、実態より強い保証があると誤認させる。
- 既定ブランチへの直接 push は、この機構では扱わない。サーバ側のブランチ保護のほうが確実で、ブランチ名の部分一致で無関係なブランチへの push を止める副作用も避けられる。

具体的な配線は実行環境層が持つ。実行環境にこの種の機構が無い場合は、確認を挟めないことを既知として扱い、文書での担保に留める（無いものを「ある」と書かない）。

## 実用プロンプト例
- 「この PR / Issue を merge / close してよいか、ポリシーに照らして判定してください」
- 「この指摘は打ち切り条件に該当しますか。該当するなら根拠を示してください」

## カスタマイズ例
- プロジェクト独自の merge 条件や承認フローを明記
- 例: 「危険操作は必ず 2 名承認」等

## 運用Tips
- merge / close 判断時は必ず根拠を明示
- 状態面と手元の状態の不整合に注意
