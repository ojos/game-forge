# Plan Review Task Skill

## 目的

- 実装に入る前に、計画の矛盾と漏れを見つけて直す。
- 単一の要件の intake 票と、複数の issue をまとめて着手するときの作業計画の両方を、同じ出し方でレビューする。

計画の漏れは、実装が進んでから見つかるほど直す費用が大きくなります。受け入れ条件の欠けは、実装もテストも緑のまま素通りし、レビューや利用者の確認で初めて現れます。計画の段階で見つければ、文面を直すだけで済みます。

## 起動する時点

| 対象 | 時点 | 担うロール |
|---|---|---|
| intake 票 | intake 確認ブロックの承認の後、issue 化の前 | [intake-manager](../role-contracts/intake-manager.md) |
| 複数の issue をまとめる作業計画、または 1 つの issue を複数のレーンへ分ける作業計画 | 計画（レーンの分割と割当）の確定の後、委譲の前 | [planner](../role-contracts/planner.md) / [orchestrator](../role-contracts/orchestrator.md) |

1 つの issue を 1 つのレーンで実装する場合は、観点 A だけで足ります。複数の issue をまとめる場合、または 1 つの issue を複数のレーンへ分ける場合は、観点 B も通します。

## 入力

- 観点 A: intake 票（goal / scope.in / scope.out / constraints / acceptance / priority）。
- 観点 B: 対象の issue それぞれの intake 票（または本文）、レーンの一覧、各レーンの所有（触る場所）、依存と順序、統合の手順。

## 手順

1. 対象に応じて、下の観点 A（と観点 B）を順に当てはめる。
2. 問題を見つけたら、「問題と修正案」の表にまとめる。
3. 修正案を当てた計画の差分（追加・変更する行）を示す。
4. 修正が、利用者の承認した内容（goal / scope / acceptance / priority）を変える場合は、修正後の計画を利用者に承認し直してもらう。承認を得るまで、issue 化・委譲へ進まない。intake 票では、確認ブロックの承認をやり直すことがこの承認し直しにあたる（承認を二重に求めない）。
   - 観点 B の修正のうち、承認した内容を変えないもの（レーンの分け方、所有の境界、起点、統合の手順）は、承認し直しを求めず、修正した計画を記録して進む。入口で承認を得たあとは重大な変更だけで止める、という [orchestrator](../role-contracts/orchestrator.md)「入口承認・以降自動」と揃えるためである。
5. 問題が無ければ、「レビュー通過」を明示してから次へ進む。

## 観点 A（intake 票）

| 観点 | 確かめること |
|---|---|
| goal と acceptance の整合 | acceptance が goal を検証できるか |
| goal の要素ごとの対応 | goal に含まれる要素（機能・性質）の**それぞれ**について、それを検証する acceptance の項目があるか。goal 全体と acceptance 全体を見比べるだけでは、一部の要素の検証が欠けていても気づけません |
| scope の境界 | scope.in と scope.out が重ならず、境界が明確か |
| 検証できる形か | acceptance に曖昧な完了条件が無いか |
| 機械で判定できるか | 少なくとも 1 つ、非対話で実行でき、合否が終了コードで判定できる検証があるか（[loop-workflow](../loop-workflow.md)「前提: 完了条件は機械が検証できる形にする」）。下の「機械で判定できない作業」も参照 |
| 前提・依存の漏れ | 未検証の前提、他の issue・作業への依存が constraints に書かれているか |
| 規範が課す付随作業 | 規範が変更に伴って求める作業が scope.in に入っているか。例: 索引（[shared-ai-rules](../shared-ai-rules.md)「10. カタログ更新ルール」）、正本と写しの同期、設定の雛形（値のない example ファイル）、構成表の更新 |
| 配線と生成物の検証 | 足すもの（スクリプト・設定・スキル）の本体だけでなく、それが配布され、呼び出し元につながることまで acceptance が確かめているか。本体のテストが緑でも、配線が無ければ利用者には届きません |

### 機械で判定できない作業

acceptance が機械で判定できる形に達しないときは、原則として差し戻し、機械で判定できる acceptance を定義し直します。

ただし、本質的に機械で判定できない作業（例: 純粋な設計相談、ドキュメントの合意）は、「ループコーディング非対象」であることを intake 票に明記したうえで通過してよいものとします。この場合、完了は人の判断で確定し、自律反復のループには載せません。

## 観点 B（複数 issue の計画）

各観点の詳細と理由は、[shared-ai-rules](../shared-ai-rules.md)「13. 実装委譲パターン」の「統合する側の実務」が正本です。ここでは、計画の段階で何を確かめるかだけを挙げます。

| 観点 | 確かめること | 正本 |
|---|---|---|
| acceptance を検証するレーン | 各 issue の acceptance の項目それぞれについて、どのレーンが検証するかが決まっているか。どのレーンにも属さない項目が無いか | — |
| 所有の機械照合 | 各レーンの所有の一覧を、渡す前に機械で突き合わせ、重なりを解消したか | 「所有一覧の機械照合」 |
| 所有の定義 | 所有を「編集するファイル」ではなく「触る場所」で切り、新規に追加するファイルも含めたか | 「所有の定義」 |
| 正本文書の扱い | 複数のレーンが触りうる文書を、どのレーンにも編集させず、統合する側に残したか | 「正本文書の扱い」 |
| 依存と順序 | issue 間・レーン間の依存が明示され、依存のあるものが並列に置かれていないか | [planner](../role-contracts/planner.md)「並列化を前提とした分解」 |
| 各レーンの起点 | 各レーンの起点（既定ブランチの最新など）が決まっていて、前のレーンの変更が相乗りしないか | 「相乗りの防止」 |
| 波及先 | 変更の波及先を (a) 名前を参照する文書・テスト、(b) 新しく足す検査の対象、(c) 決定を説明する散文、の 3 方向で洗い出したか | 「波及先の洗い出し」 |
| 統合後の検証 | 統合したツリーで各レーンの受け入れ条件を再実行する手順が、計画に入っているか | [review-workflow](../review-workflow.md)「並列実装後の統合検証」 |

## 出力

- 問題があるとき: 「問題と修正案」の表（観点・見つかった問題・修正案）と、修正後の計画の差分。
- 問題が無いとき: 「レビュー通過」の明示と、確かめた観点の一覧。

## 注意事項

- このレビューを機構（フックや検査）で強制しません。計画の中身が妥当かは機械では検査できず、検査できるのは「レビューしたか」という儀式だけだからです（[shared-ai-rules](../shared-ai-rules.md)「12. 機構化の判断基準」）。担保はレビューと利用者の承認で行います。
- 修正案は、計画の文面を直すところまでに留めます。レビューの中で実装を始めません。
- 問題を見つけても、指摘だけを出して先へ進めません。修正を計画に反映し、承認した内容を変える修正なら利用者に承認し直してもらいます（手順 4）。承認した内容を変えない観点 B の修正は、修正後の計画を記録して進みます。
