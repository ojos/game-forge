## 2. dev01 の諸元（実測）

```
機種      Dell XPS 15 7590 / Ubuntu 26.04.1 LTS / x86_64 / kernel 7.0.0-34
CPU       Intel Core i7-9750H（6 コア 12 スレッド。負荷時 平均 3684 / 最大 3900 MHz）
メモリ    14 GiB（空き 9.7 GiB）
ディスク  468 GB（空き 427 GB）
GPU       NVIDIA GeForce GTX 1650 / 4096 MiB / Turing（TU117）
GPU 帯域  128 GB/s ← clocks.max.memory = 4001 MHz は GDDR5 版（GDDR6 版なら 6001 MHz）
```

**アーキテクチャは本番と同じ amd64 である。** 架構依存の検査（束のハッシュ・Go のビルド）が
本番と食い違う心配は無い。

**アイドル時のクロック 1200 MHz は問題ではない。** `powersave` ガバナは `intel_pstate` のもので、
負荷をかければブーストする（上記の 3684 MHz は 12 スレッドに負荷をかけた実測。パッケージ温度 58℃、
サーマルスロットリングなし）。

**この機械の弱点はシステムコールである。** `/sys/devices/system/cpu/vulnerabilities/` に
**Meltdown の PTI・MDS の Clear CPU buffers・retbleed の IBRS・vmscape の IBPB before exit to
userspace** が並ぶ。2019 年の Coffee Lake なので当然で、**すべてシステムコールと文脈切り替えに
課金される。**

| 指標 | devcontainer（M 系 / 14 スレッド / aarch64） | dev01 | dev01 は |
|---|---:|---:|---:|
| 単一コア演算（mawk） | 0.638 秒 | 0.965 秒 | 1.5 倍遅い |
| 全コア演算 | 0.920 秒 | 1.798 秒 | 2.0 倍遅い |
| **fork/exec 3000 回** | **0.755 秒** | **5.79 秒**（3 回再現） | **7.5 倍遅い** |

## 3. 取り下げた案

### 3.1 CI の self-hosted runner（取りやめ）

**動機は「実行時間の短縮」だった。** 費用は動機にならない——このリポジトリは public で、
GitHub ホストの実行枠は無料・無制限である。

**`verify` ジョブの内訳が、前提を崩した。**

| 段 | CI（`ubuntu-latest`） | devcontainer |
|---|---:|---:|
| checkout ＋ node ＋ `npm ci` ＋ terraform ＋ go（**セットアップ一式**） | **26 秒** | — |
| `scripts/acceptance.sh` | 270 秒 | 131 秒 |
| `scripts/report-selftest.sh` | 260 秒 | 164 秒 |
| **合計** | **550 秒**（成功 n=24 の中央値） | 295 秒 |

- **「毎回ツールチェインを入れ直すのが遅い」は誤りだった。** セットアップは 550 秒のうち 26 秒で、
  キャッシュが手元に残ることで削れる余地はここにしか無い。**短縮幅は CPU の速さだけで決まる。**
- **`acceptance.sh` はシェルスクリプトの束で、fork/exec が支配的である。** 2 章の 7.5 倍がそのまま効く。
  手元の実測（user 280 秒 / sys 54 秒）に係数を当てると **dev01 で約 394 秒**——**CI の 270 秒より遅い。**
- 他のワークフローは中央値 8〜13 秒で削る余地が無い（`deploy-compiler` は 178 秒だが起動が稀）。

**判定根拠**: 実測（2026-09-23）。`gh run list` の n=24 と、両機での `acceptance.sh` / `report-selftest.sh` の計時。

**設計として決めていたこと**（採らなかったが、再開するなら出発点になる）:

- fork からの PR は `runs-on` の条件式で GitHub ホストへ逃がし、承認方針を
  `all_external_contributors` へ上げる。**fork は 0 件・直近 100 PR はすべて本人由来**なので、
  逃がしても失うものが無い（`ojos/game-forge` は public。共同編集者は 1 人）。
- 退避は**リポジトリ変数 1 つ**（`vars.VERIFY_RUNNER`）で切り戻せるようにする。dev01 が落ちている間、
  GitHub は拾い手のいないジョブを最大 24 時間キューに置く。

**副産物（別件として残っている）**: [verify.yml:160](../.github/workflows/verify.yml#L160) の注記は
「`report-selftest.sh` は 17 秒、`acceptance.sh` は 20 秒」と書いているが、**実測は 164 秒と 131 秒**である。
この注記は「17 秒を毎回払う価値は薄い」という判断の根拠になっているので、**数字が 8 倍ずれたまま
判断だけが残っている。**

### 3.2 Copilot レビューの置き換え（保留。費用の問題は未解決）

**費用は実在する。** [#654](https://github.com/ojos/game-forge/issues/654) の実測モデル:

```
credits ≒ 16.1 × PR本数 + 0.0172 × 変更行数
```

9 月は 260 本で 6,678 credits＝$66.78（CSV 実測 6,669 と一致）。**消費は 100% が PR code review**
（IDE のチャットもエージェントも使っていない）。このままなら**超過 $164.60/月**、Pro+ の $39 を足すと
**コードレビューに月 $200 前後**である。

**置き換えを勧めない理由は、精度の非対称である。**

- 文書に残る Copilot の実績は **5/5・6/6・5/5 で 16 件すべて実在**、うち 1 件は Guardrail を
  すり抜けて Bedrock へ届いていた穴だった。
- `review-workflow.md`「指摘の却下」は、**却下のたびに再現手順と実測結果を残すこと**を要求する。
  弱いモデルへ替えると、**浮いた $200 を却下の手間で払い直す。**
- 4 章の実測から、**7〜8B は VRAM 4 GB に載らない**（重み 4.7 GB）。上へ逃げる道が無い。

**ランナーの紐付きについて（調べた事実）**: 登録先は**リポジトリ / Organization / Enterprise** の 3 階層で、
共有できるのは Organization 以上。**`ojos` は User アカウント**（`type: "User"`、所属 org 0 件、
所有リポジトリ 27）なので、**いまはリポジトリ階層しか無く、複数リポジトリで共有できない。**
共有するなら Organization を作って移すか、1 台に複数のランナーを別登録する。

**残っている選択肢**（この文書では決めない。7 章の論点 F）:

- **費用モデルの支配項は PR 本数（固定費）である。** 本数を減らす方が差分を減らすより効く。
- **Bedrock の `deepseek.v3.2` は東京で使え、登録簿に実装済みである**（3.3 の表）。レビュー用途に
  向くかは測っていない。

### 3.3 チャットの全面置き換え（不成立）

#### 制約が合格条件を決めた

```
terraform/chat-function.tf:70   chat_function_timeout_seconds = 30
src/chat-payload.ts:182         CHAT_MAX_OUTPUT_TOKENS = 1_500
```

- **タイムアウトは 30 秒。** 注記は理由まで書いている——「**エッジは応答を待っている**ので、
  長く取りすぎると壊れた日に利用者の画面が長く止まる」。
- **返事は流れない。** `src/chat/` と `src/chat*.ts` に `stream` / SSE は 1 件も無い
  （`Converse` であって `ConverseStream` ではない）。**利用者は画面に何も出ないまま全部の完了を待つ。**
- 予約同時実行数は 2、メモリ 512 MB。

**したがって合格条件は「前処理 ＋ 生成 ＋ トンネル往復が 30 秒以内」である。**

#### いまのチャットが要求しているもの

| 項目 | 値 | 出典 |
|---|---|---|
| モデル | **`sonnet-4-6`**（生成と同じ） | 確定37 / 仕様 5.16 |
| 呼び方 | エッジから Lambda を**同期**で呼ぶ | 確定37 |
| 1 往復 | 1,710 トークン・**¥0.64**（単価 0.371 円/1,000 トークン） | 本番実測 v1.114 |
| 月額 | 約 **¥1,000** | 同上 |
| 送る上限 | 20 通・12,000 文字 | v1.121 |
| **ソースを渡す往復** | **64 KiB を通すなら蓋は約 27,000 トークン** | v1.115 |
| 枠 | 1 人 1 日 **¥20** / 当月累計 **¥2,000**（4.3 の 10%） | `CHAT_DAILY_COST_LIMIT_JPY` / 仕様 5.16 |
| 参加者の上限 | **50 人** | 8.1 |

**蓋が客寄せとして効かない。** ¥1,800/月 という試算の前提は **3 人**である。取り分 ¥2,000 は
**3.3 人が毎日枠を使い切っただけで尽きる。** 50 人が枠まで使えば ¥20 × 50 × 30 ＝ **¥30,000/月** で、
チャット単体が全体予算 2 万円を超える。**人が増えたときに止まる客寄せは、いちばん要るときに消える。**
ローカル推論は限界費用がほぼ 0 なので、**この蓋そのものを外せる**——これが置き換えの本来の動機だった。

#### 何が落ちたか

**速度は 1 か所だけ落ちた**（4 章の実測より）。

| 往復の種類 | 前処理 | 生成(230tok) | 合計 | |
|---|---:|---:|---:|:-:|
| 軽い・初回 | 2.3 s | 2.8 s | 5.1 s | ◯ |
| 軽い・2 回目以降（キャッシュ） | 0.1 s | 2.8 s | 2.9 s | ◯ |
| 軽い・最悪（出力 1,500） | 2.3 s | 18.6 s | 20.9 s | ◯ |
| **ソース付き・初回** | **123.7 s** | 2.8 s | **126.5 s** | **✕ 4.2 倍超過** |
| ソース付き・2 回目以降 | 0.1 s | 2.8 s | 2.9 s | ◯ |

- **前処理は線形でない**（4 章）。**どの規模でも 27K の初回は 30 秒に入らない。**
- **「作品を選んだ時点で裏で温めておく」案は成立しない**——同時実行が直列なので、その 124 秒の間、
  他の全員のチャットが止まる。
- **ソースの圧縮（27K → 約 2K）が唯一の解**だった。前例が `scripts/tile-reachability/` にある。

**質は全滅した。** 本番と同一のシステムプロンプト（`renderChatPromptText()`、版 4、2,020 字）で、
6 往復の会話を 4 モデルに通し、`CHAT_PROMPT_DRAFT_RULES` の 5 規則と仕様 5.7 で採点した。

| モデル | VRAM（単独・ctx 8192） | 下書きを出すか | 日本語 |
|---|---|---|---|
| `qwen2.5:1.5b` | 1.4 GB / 100% GPU | **6 往復で一度も出さない** | 破綻なし |
| `qwen2.5:3b` | 2.4 GB / 100% GPU | 出す（67〜127 字） | **壊れている**（下記） |
| `TinySwallow-1.5B` Q5_K_M | 1.5 GB / 100% GPU | **一度も出さない** | **自然** |
| `sarashina2.2-3b` Q4_K_M | **3.8 GB / 30%/70% CPU/GPU** | 一度も出さない | 自然 |

`qwen2.5:3b` の出力（形式だけ通り、中身が壊れた例）:

> 【指示文】
> 「**【指示文】を参照してください。**…プレイヤーが**敵の機関銃を攻撃する**ように設計します。
> …プレイヤーの**シャーベルト**を攻撃します。」

`TinySwallow` は日本語が最も自然だったが、3 回目の返事で**一度に 5 つ質問した**
（プロンプトは「一度に 1 つだけ」「3 回目までに下書きを出す」と明記している）。

**落ちているのは流暢さではなく指示追従である。**

#### 小規模モデル向けにプロンプトを書き直した（改善したが届かなかった）

規則を 15 本前後（2,020 字）から **6 本（396 字）＋ 実例 2 往復**へ置き換え、**実例は地の文ではなく
会話ターンとして渡した**（地の文に置くとモデルが実例を続けてしまう。5 章の誤り③）。

| | 本番プロンプト | 小規模向け |
|---|---|---|
| 下書きを出すか | 3/4 が一度も出さない | **3/3 が 1 回目から出す** |
| 日本語 | 「シャーベルト」 | 文法的に正常 |

**同一条件を 3 回回した結果**（`qwen2.5:3b`）:

| 項目 | 3 回 | 性質 |
|---|---|---|
| 1 回目から下書き / 毎回下書き / 質問 1 つ以下 / コード返さず / 実例漏れ無 | OK OK OK | **形式** |
| 下書きが 200 字以上 | OK OK **NG** | 形式（揺れ） |
| **利用者が言った要素が入る** | **NG NG NG** | **意味** |

**「左右」が 6 返事すべての下書きに一度も入らなかった。** しかも下書きはこう書いた。

> 敵は上から降りてくる形で来ます。…**敵の移動は上下だけ設定します。**

利用者が言ったのは「**自機**は**左右**だけ動かしたい」である。**制約を別の主体・別の軸へ付け替えている。**

**これは「精度」の問題ではない。** 下書きは生成へ渡る。生成は 1 回 **¥22.41**（4.2 の平均）で
チャットの 1 往復の **35 倍**なので、**作り直しが 1 回増えるだけで浮かせた額を超える。**

**判定根拠**: 実測（2026-09-24）。本番プロンプト 4 モデル × 6 往復、小規模向け v2/v3 × 3 モデル、
同一条件 3 回の揺れ測定。

## 4. ローカル LLM の実測値（再利用できる定数）

**この章の値は、将来どの設計を採るときにも使える。** 校正は `qwen2.5:1.5b`（986 MB / 100% GPU / ctx 32768）。

| 測定 | 実測 |
|---|---|
| 前処理 1,624 トークン | **2.25 秒**（722 tok/s） |
| 前処理 11,414 トークン | **39.5 秒**（289 tok/s） |
| 前処理 25,659 トークン | **123.7 秒**（207 tok/s） |
| **生成** | **80.8 tok/s** |
| KV キャッシュ再利用（同一プロンプト） | 23.6 秒 → **0.02 秒** |
| KV キャッシュ再利用（末尾に追記） | **0.09 秒** |
| KV キャッシュの 2 会話の共存 | **両方保持**（`num_ctx` を超えても。A→B→A→B で確認） |
| **同時 2 本** | **直列化**（1 本 2.79 秒 / 2 本 5.36 秒） |

**読み取り。**

- **前処理は O(n²) の attention が効いて非線形に落ちる**（722 → 289 → 207 tok/s）。
  **パラメータ数に比例する、という外挿は 3 倍外した。**
- **生成は帯域律速で 80.8 tok/s。** 出力 1,500 トークンで 18.6 秒。キャッシュが温まっていれば
  30 秒の予算で**約 2,200 トークンまで出せる。**
- **KV キャッシュが決定的に効く。** 会話の 2 往復目以降は前処理がほぼ 0 になる。
- **同時実行は直列。** 2 人が同時に送れば 2 人目は待つ。

**モデルの占有量**（単独・`num_ctx` 8192）: `qwen2.5:1.5b` 1.4 GB / `qwen2.5:3b` 2.4 GB /
`TinySwallow-1.5B` Q5_K_M 1.5 GB は **100% GPU**。`sarashina2.2-3b` Q4_K_M は **3.8 GB で
30%/70% CPU/GPU**（ファイルは 2.1 GB だが、日本語モデルは語彙が大きく埋め込みが重い）。

**`num_ctx` は必ず明示する。** 既定（4096）のままだと長いプロンプトが黙って切られ、**偽の高速値が出る。**
`prompt_eval_count` で実際に読まれたトークン数を検証すること。

## 5. 測定方法の誤り（4 件）

**どれも結論を左右した。次に測る人が同じ穴に落ちないために残す。**

| # | 誤り | 何が起きたか |
|---|---|---|
| ① | `temperature: 0` で走らせた | **本番は `maxTokens` だけを指定**し、温度は提供側の既定に任せている（`src/chat/handler.ts:279`）。貪欲法は小規模モデルで反復ループを誘発し、`TinySwallow` が毎回 1,500 トークンで打ち切られていた |
| ② | 4 モデルを続けて走らせた | VRAM を取り合って CPU へ落ち、`sarashina` の所要時間が無効化（43.5 → 66.8 秒）。**モデルごとに `ollama stop` してから測る** |
| ③ | few-shot の実例を地の文（システムプロンプト）に置いた | `qwen2.5` が**実例の質問を丸写し**し、`TinySwallow` が実例の題材（「横スクロール」）を下書きへ漏らした。**会話ターンとして渡す** |
| ④ | n=1 で結論を出しかけた | 同一条件 3 回で、7 項目のうち 1 項目が揺れると判明。**プロンプト版の差の一部は揺れだった** |

**採点の設計にも穴があった。** 禁止語を全体で 1 つの一覧として持つと、**列挙した軸しか守れない。**
「敵の降り方を**横方向に**変更する」が、土台の「敵は上から降りてきます」と矛盾するのに通った。
**禁止語は項目ごとに持たせる必要がある**（「敵の動き＝上から」という項目が「横／斜め／下から」を
自分で知っている形）。

## 6. 残った設計案（テンプレート ＋ 一工夫）

### 6.1 形

```
穴埋めフォーム（LLM 無し）
  → 指示文の組み立て（コード。定型文へ差し込む）
  → 一工夫の提案 3 案（dev01 のローカル LLM。キャラ付き）
  → 利用者が選ぶ（0〜1 案）
  → 生成（Bedrock sonnet-4-6 ＋ 8.2）
```

| 部品 | 担当 | 根拠 |
|---|---|---|
| 穴埋め → 指示文の組み立て | **コード** | 費用 0・待ち時間 0・意味の取り違えが起きない |
| 一工夫のフレーバー | **dev01** | **0.3〜1.0 秒**（実測。4 章の値と整合） |
| リフォージ（スロット編集） | **コード** | `games.prompt`（migration 0047）が既にある |
| フォーク（スロット引き継ぎ） | **コード** ＋ **1.2.54 の決定** | 7 章の論点 D |
| 型を超える改変・練りたい人 | **Bedrock** | ここに単価の価値がある |
| 生成 | **Bedrock ＋ 8.2** | 変更なし |

### 6.2 なぜ成立するのか

- **土台をコードが持つので、3.3 の失敗が構造的に起きない。** 悪い出力の被害範囲が
  「指示文まるごと」から「利用者が採否を選ぶ 1 文」に縮む。
- **忠実さが要らない用途である。** 3.3 で失格になった挙動（勝手に足す・ずらす）が、ここでは長所になる。
- **8.2 が残る。** `withInputModeration` は**オーケストレータ Lambda の中だけにある**ので、
  生成へ渡る指示文は出所を問わず Guardrail を通る。**ローカル LLM を混ぜても安全層は消えない。**
- **蓋が要らない。** 穴埋めの経路に限界費用が無いので、3.3 の「50 人で止まる」が消える。
- **費用を需要側から下げる。** 初心者が往復を消費しなくなるので、**チャットは Bedrock のまま残せる**
  （質が要る人だけが使う形になり、単価の高さが正当化される）。

### 6.3 一工夫の実測

| | 違反 | 印象 |
|---|---|---|
| キャラ無し（9 本） | 2 / 9 | 弱い出力が**故障に見える**（「隠れ家にいるお友達と喜ぶ映像を流す」） |
| **キャラ有り（6 本）** | **1 / 6** | 弱い出力が**愛嬌に見える**（「少し早起きして元の場所に戻るってどうですか？」） |

- **キャラ付けは中身を劣化させなかった。** 違反率は同程度で、**弱い出力の受け取り方だけが変わった。**
- `qwen2.5:3b` は**キャラを付けたほうが提案が具体的になった**（「画面の右上に『PLAY AGAIN』の文字を
  表示してみたらどうでしょうか？」——文字描画は許可済みなのでそのまま実装できる）。
- **9 本中 3〜4 本が使える水準。** 3 案出して選ばせれば実用上ほぼ 1 つは当たる。
  **選ばれなければ費用 0。**
- タッチの違反は **15 本中 0 件**。
- **`TinySwallow` の「自機は上下左右にジャンプ」は、キャラ有無どちらでも同じ位置で出た。**
  口調とは無関係な、モデル固有の安定した失敗である（→ 5 章の「項目ごとの禁止語」）。
- **モデルの向き不向きが 3.3 と逆転した。** 忠実さが要らないこの用途では、
  3.3 で落ちた `TinySwallow`（日本語が自然）が良い案を出す。

**守りは緩めず強める。** キャラは提案を**採られやすく**する。損得が非対称である——
**選ばれない珍案は費用 0、選ばれた矛盾案は ¥22.41 ＋ 遊べない作品。**

守るべき 3 つ:

1. **項目の矛盾**（項目ごとの禁止語で機械化できる）
2. **記録済みの禁則**——**タッチを書かせない**（仕様 6.1 の **#490 注記**「入力の例にタッチ
   （`TouchIDs` など）を足さない」。公開済みの作品は 1 本もタッチを読まず、スマホの手当ては
   プレイ画面の側で行う〈3.9〉。仮想パッドはタッチ端末にしか出ないので、作品がタッチを読むと二重になる）
3. **実装できない提案**——「映像を流す」は外部アセット禁止の外。
   **なお音は許可されている**（`github.com/hajimehoshi/ebiten/v2/audio` の 1 件だけ。
   **波形をコードで組み立てる経路**のみで、デコーダと外部ファイルは不可）

**提案文の表示は 8.3 の表で受ける**（`src/denied-terms.ts` / `inspectText`）。**前例がある**——
自己紹介・題名・作品の説明が同じ形で、8.2 を通さない理由 3 つも記録済み（うち 1 つは
「fail-closed を持ち込むと AWS の障害で書けなくなる」）。**表示は 8.3、採用後の生成は 8.2 の二層。**

### 6.4 テンプレートが育つこと

**既存の規律をそのまま継げる**（システムプロンプトが同じ問題を解いている）。

| 部品 | 既にあるもの |
|---|---|
| 版の記録 | `generations.prompt_version`（migration 0046） |
| 版の規律 | **本文の SHA-256 と照合し、本文を変えたら版を上げるまでテストが落ちる** |
| 効果の測定 | `source_quality_metrics`（0046。`has_win_text` / `has_lose_text` / `color_count` / `sprite_count` / `state_count` / `rule_version`）。**費用 0**——ソースは既に R2 にある |
| 改善の主体 | **「指標で見るべき生成を絞り込み、プロンプトの次の 1 行は人が書く」**（v1.95） |

**「日々」は速すぎる。** 理由が 2 つある。

- **記録済みの禁則に触れる。** 仕様 v1.95 は「**代理指標に最適化しないことを明記した**……
  **目的関数にすると指標をハックする方向へ進む**」と書いている。自動で毎日指標を上げにいく形は
  この決定の正面である。
- **標本が足りない。** 確定25 の日次は 1 人 10 回、想定 3 人。4.2 の A/B はお題 6 本で測り、
  `effort` の A/B は n=2 のときに「**横並びにできない**」と明記して据え置いている。
  **日次だと雑音を追う。**

**「日々」ではなく「証跡が溜まったら」にする。** 育つこと自体には異論が無い。

### 6.5 フォークとリフォージ

**リフォージ（自作）はいますぐ成立する。** `games.prompt`（migration 0047）に最初の指示文が残り、
`GET /api/me/works/<id>` が作者本人へ返している。**スロットを保存しておけば
「開いて直す → 再生成」になる**——LLM 不要・ソース読解不要・仕様の変更なし。
3.3 で破綻した 27K の読み込みがまるごと消える。

**フォークはそのままでは成立しない。**

> **フォーク元の最初の指示文** → **出さない**（**1.2.54**。指示文は作者本人にしか出さない）
>
> **フォーク元の最初の指示文は、SQL で選んでもいない**（**1.2.54**）。**選ばなければ、後から漏れない**

（仕様 5.3 のフォーク元から見せるものの表と、その実装注記。**行番号では引かない**——
`docs/product-spec.md` は 13,000 行を超える生き物で、枝によって行がずれる。節と確定番号で引く。）

スロットは指示文の構造化された姿なので、**引き継がせるには 1.2.54 を見直す決定が要る**（論点 D）。

**見直しを支持する材料**（情報量の序列が逆転している）:

| フォーク元から得られるもの | いまの扱い | 情報量 |
|---|---|---|
| 題名・説明・タグ | **常に出す** | 小 |
| **スロット** | （存在しない） | **中** |
| **ソース全文** | **作者が求めたときだけ出す** | **最大** |
| 最初の指示文 | **出さない** | 中 |

**ソースを渡せるのに、それより情報量の少ないスロットを渡せないのは筋が通らない。**

**スロットは交換形式になり、コードで導出できる。**

```
テンプレート製の作品  → スロットを保持している      → そのまま引き継ぐ
ソースを共有した作品  → ソースから構造を機械で抜く  → スロットにする（前例: scripts/tile-reachability/）
どちらでもない作品    → 従来どおり（題名・説明・タグ ＋ Bedrock のチャット）
```

**残る弱さを正直に書く。** スロット編集のフォークは安くて安全だが**テンプレートの空間に閉じる。**
型を超える改変には届かない。そこは自由文の理解が要るので **Bedrock の出番として残す**
（ローカル LLM では届かない。3.3 / 4 章の実測どおり）。
