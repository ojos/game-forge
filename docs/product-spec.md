## 1. エグゼクティブサマリー

- **プロダクト名:** **Game Forge**（確定16）。アプリ本体は `app.game-forge.ojos.jp`、ユーザー生成コンテンツは `sandbox.game-forge.ojos.jp`（v1.4 でアプリ側に `app.` を足した。1.2.11 / #89）。
- **コンセプト:** プロンプト1行で生まれるブラウザ2Dゲームと、フォーク型 UGC コミュニティ。
- **コア仮説:** **他人の作品を改造（フォーク）する連鎖が起きること。** 生成体験だけなら競合が複数存在し、そこで勝つ根拠はない。**フォーク機能そのものも差別化にならない**（1.3）。差別化は、**系統を機能ではなく評価軸に据えること**にある。したがって本プロダクトの成否は、生成数ではなくフォーク率で判定する（10 章）。
- **公開形態:** 招待制クローズドβで開始する。プレイと URL 拡散は招待不要、生成のみ招待コード保有者に限定する。

### 1.2.8 v1.0 からの主要な変更

| # | v1.0 の記述 | v1.1 での扱い |
|---|---|---|
| 1 | 開発分の枠の分離は**アカウント分割ではなく Bedrock 側の機構**で行う（9.2 / 確定21） | **アカウント分割へ戻す**（9.2 / 確定21）。Dev / Prod の 2 アカウントとし、それぞれに Bedrock を置く |

**判断の決め手は Bedrock のクォータの粒度である。** クォータは
**アカウント × リージョン × モデル**で定義され、**IAM プリンシパルの次元を持たない**（実測）。

```
Cross-region model inference tokens per minute for Anthropic Claude Sonnet 5   (Adjustable: True)
Global cross-region model inference tokens per day for Anthropic Claude Sonnet 5 (Adjustable: False)
```

したがって **1 アカウント内では、開発と本番に別々のレート上限を張れない。** 4.3 の
最外周の候補のうち、**即時に効くのはクォータだけ**であり（Budgets Actions はコスト
データの反映に数時間かかる）、**その唯一の速い層がアカウントでしか割れない。**

同居させると、開発の暴走がそのまま本番のレート枠を食う。これは 4.3 が
「開発の実験が本番の枠に混ざると判定基準が壊れる」として避けている事態そのものである。

**v0.9 で分割をやめた理由は、もう成立していない。** 当時の理由は「Dev に置くものが
Claude Platform on AWS の組織だけで、直販へ差し替えたら置くものが無くなった」であり、
**確定21 の根拠（blast radius・IAM・請求行の分離）を否定したものではなかった**（9.2）。
Bedrock という置くものができた時点で、その根拠が復活する。

### 1.2.11 v1.3 からの主要な変更

**アプリ用ホストを `game-forge.ojos.jp` から `app.game-forge.ojos.jp` へ改めた（#89 / 確定16 の改訂）。**
本番配備の実作業で、当初の綴りでは DNS を張れないことが分かったための変更である。

| # | v1.3 の想定 | v1.4 での扱い |
|---|---|---|
| 1 | アプリは `game-forge.ojos.jp` に置く | **`app.game-forge.ojos.jp` に置く。** `game-forge.ojos.jp` は確定17 で委譲した Route53 **ホストゾーンの apex** であり、**Route53 は apex に CNAME を作れない**（apex には SOA と NS が必ず在り、CNAME は他のレコードと同居できない） |
| 2 | Pages のカスタムドメインは CNAME 1 本で足りる（9.3） | **サブドメインなら足りる、が正確。** Cloudflare Pages は、外部 DNS のままの apex を対象外としている（apex へ配備するならドメインごと Cloudflare のゾーンにしてネームサーバを向けることを要求する） |
| 3 | サンドボックスはアプリの真のサブドメイン | **兄弟になった。** `app.` と `sandbox.` が `game-forge.ojos.jp` の下に並ぶ |

**7.2 の結論は変わらない。** 変わったのは 2 つのホストの位置関係だけで、登録可能ドメインは
どちらも `ojos.jp` のままである。兄弟であっても `Domain=game-forge.ojos.jp` の cookie は
相手へ届くため、**`__Host-` 接頭辞と CSP `sandbox` ヘッダの必要性はそのまま**である。

**採らなかった案と理由。**

| 案 | 採らなかった理由 |
|---|---|
| `ojos.jp` ごと Route53 へ委譲する | `game-forge.ojos.jp` が apex でなくなり当初の綴りを保てるが、**Google Workspace の MX を含む本番のメール経路を移送する**ことになる。ホスト名 1 ラベルのために本番メールを危険に晒す釣り合いではない |
| `ojos.jp` ごと Cloudflare DNS へ移す | 同じ移送リスクに加え、確定17（Route53 で宣言的に管理する）を差し替えることになる |
| `game-forge.ojos.jp` だけを Cloudflare のゾーンにする | 親が外部 DNS の場合、Cloudflare のサブドメイン単独ゾーンは **Business / Enterprise プラン限定**である（9.3 が既に記していた制約） |
| CloudFront を前段に置き Route53 の ALIAS で apex を解決する | ALIAS は張れるが、Pages 側のカスタムドメインが apex に対して発行できない以上、**オリジンへ渡す `Host` を本来の名前にできない**。`src/index.ts` のホスト出し分けと OAuth の `redirect_uri` が両方壊れる |

**`game-forge.ojos.jp` そのものは空いたままである。** 後日 `ojos.jp` の移送を決めたときに
当初の綴りへ戻せる。戻す場合に変えるのは `wrangler.toml` の `[env.production.vars]`、
`terraform/dns.tf`、Google OAuth のリダイレクト URI の 3 か所である。

| 2 | VPC は封じ込めのために足す | **3 か所で悪化させる。** DNS の穴／実行ロールに付く EC2 権限が **AWS 明文で「関数のコードにも暗黙に付与される」**／**14 日アイドルで最初の呼び出しが必ず失敗する** |

| 4 | NAT を立てると ¥5,092/月 で費用が逆転する | **議論自体が無くなった。** あわせて **¥5,092（$0.045/h）は東京の単価ではなかった**（us-east-2 の値。東京は $0.062/h ＝ 1 AZ ¥7,020/月） |

**代償は egress の遮断を一切持たないことである。** 非 VPC の Lambda はフルのインターネットへ出られ、**AWS にこれを無効化する手段が無い**。7.1 の「受け入れた劣化」へ 5 点目として記録した。

**受け入れる根拠は実測である。**「たぶん安全」ではない。

- **偽バイナリ 16 個（`gcc` `cc` `clang` `ld` `git` `make` `python3` `bash` `sh` ほか）を PATH の先頭に置いてビルド → 外部プロセスの起動 0 件**（ビルドは成功）
- **`GOOS=js GOARCH=wasm` では cgo が構造的に動かない**（`cgo: unknown ptrSize for $GOARCH "wasm"`）
- `//line` による詐称（CVE-2023-39323 の形）は**現行版で拒否される**
- **ビルド時 RCE の CVE は判明した全件が cgo 依存**

**部分的な遮断のために、確実に発生する 3 つの悪化を買うのは釣り合わない**という判断である。

**あわせて、VPC の要否とは独立の穴が 2 つ見つかった**（7.1 に事実として記録し、対処は別 issue が持つ）。**import ホワイトリストがまだパイプラインへ結線されていないこと**（#17）と、**`//go:wasmimport` が import 文を持たずにホスト関数を呼べるため、import を見る検査器では原理的に検出できないこと**（#100）である。後者を実際に押さえているのは 7.1 ではなく **7.2 の CSP `sandbox` ＋ `connect-src 'none'` ＋ 別オリジン iframe** である。

### 1.3 競合と差別化

| 競合 | フォーク機能 | 出力形式 | 母数 |
|---|---|---|---|
| Websim | あり（fork / remix、URL 単位） | HTML / JS | オープン。2026-01 に無料クレジット施策を終了 |
| Rosebud AI | あり（remix / clone） | HTML / JS（2D / 3D / voxel） | 230 万本超のライブラリ |
| 本プロダクト | あり | **Go/Ebitengine → Wasm** | 招待制・数十人 |

**フォークできること自体は差別化にならない。** 主要な競合はいずれも remix / clone を備えている。この事実は v0.2 の「差別化はフォークと系統の記録にある」という主張を部分的に否定する。

残る差は次の 3 点で、**優先順位を明示する**。

1. **系統を評価軸に据えていること（第一位）。** 競合は remix を「機能」として持つが、成否の判定基準にはしていない。本プロダクトは主 KPI をフォーク率に置き、撤退条件（10.3）も系統で判定する。**この一点だけが、撤退条件が実際に検証している対象と一致している。**
2. **出力形式（Wasm ネイティブ）。** 模倣されにくいが、プレイヤーから見える差ではない。差別化の主張には使わず、6.1 の制約が著作権防御になっている点（6.2）の裏付けとして扱う。
3. **招待制による密度。** クローズドβ期には効くが、招待制を外した時点で失われる。長期の仮説には使わない。

2 と 3 を差別化の第一位に置かない理由は、**撤退条件が測っているものとずれるから**である。フォーク率 40% という線は系統の仮説を検証するものであって、描画方式や運用形態を検証しない。仮説と判定基準が食い違うと、撤退判断が「何を否定したのか」を答えられなくなる。

## 2. ターゲット層 & ユーザー体験 (UX)

### 2.1 ターゲットペルソナ

- **クリエイター層:** アイデアはあるがゲーム開発を学ぶ時間がないネットミーム好き・大喜利好き（20代〜40代）。
- **プレイヤー層:** スマホ・PC の隙間時間（10秒〜3分）で手軽に笑えるゲームを求める SNS ユーザー。

**クローズドβ期の現実的な母数:** 生成枠が月350〜500回（4 章）であるため、招待者は数十人規模を想定する。プレイヤー層は招待不要のため制限されない。

### 2.2 UGC ＆フォークのコア体験ループ

1. **発見:** タイムライン・SNS の URL から起動。OGP 画像が付く。
2. **ロード:** **タップから数秒**（2〜3MB のダウンロード＋Wasm インスタンス化）。この待ち時間は「空白」ではなく、作者名・親ゲーム名・OGP スクリーンショットの提示に充てる（3.4）。2回目以降はブラウザキャッシュで即時。
3. **プレイ & リアクション:** ワンタップスタンプで評価（MVP 対象外。11 章）。
4. **改造（Fork）:** 「このゲームを改造する」を押す。
   - 招待コード保有者: 親のソースを読み込んだ状態でエディタが起動し、差分プロンプトを入力して再生成（5.3）。
   - 未招待: **待機リストへの登録導線**に変換する。希少性は初期の話題性として機能させる。
5. **系統の可視化:** 作品ページに「元ゲーム」1リンクと「このゲームからの改造 N件」を表示（5.5）。
6. **通知:** 自分の作品が改造されたとき、作者にメールを1通送る。バッジのみでは再訪しない限り気づけず、コア体験ループが閉じない。

### 3.3 書き込み経路（v0.1 で未定義だった部分）

生成の一連の流れは以下の順序で確定する。

1. ブラウザ → Workers: 生成リクエスト（招待コード検証済みセッション必須）
2. Workers: 日次クォータと月次上限を判定。超過なら即座に拒否。
3. Workers → Amazon Bedrock: 生成。レスポンスの `usage` から費用を算出（モデル別単価。4.2）。
4. Workers → D1: 費用を台帳に加算（**成功・失敗・リトライを問わず全件**）。
5. Workers → ビルド関数（Lambda）: ソースを渡してビルド依頼（同期。タイムアウト 10 秒。3.8）。
6. ビルド関数: 隔離環境でビルドし、**関数の中で brotli 圧縮**して、`.wasm.br` と `source.go` を **AWS 側から R2 へ直接**（S3 互換 API）書き込む（7.1）。
7. ビルド関数 → Workers: 結果を返す。
8. Workers → D1: `games` 行を `status='draft'` で作成。

**R2 の認証情報はビルド側のみが保持する。** ブラウザにも Workers にも渡さない。

### 3.4 Wasm 配信の最適化（確定1に伴う必須仕様）

Go/Ebitengine の Wasm は最小構成でも未圧縮 8〜12MB 前後になる。Go ランタイム（GC・スケジューラ）を同梱するためであり、ゲーム内容を減らしても下限は変わらない。以下を仕様として固定する。

1. **R2 へは Brotli 事前圧縮した `.wasm.br` を置き、`Content-Type: application/wasm` と `Content-Encoding: br` の両方を付けて返す。** wasm への自動圧縮は当てにしない。圧縮後 2〜3MB。
2. **`WebAssembly.instantiateStreaming` を使う。** `wasm_exec.js` の同梱例は非ストリーミングのことがあり、ダウンロード完了まで待つ実装になっていると体感が悪化する。
   **`Content-Type: application/wasm` は必須**である。`instantiateStreaming` は MIME type を検証し、一致しなければストリーミング経路に入れない。`Content-Encoding` だけを設定して `Content-Type` を落とすと、圧縮は効いているのにストリーミングだけが黙って失われる。R2 のオブジェクトメタデータに両方を設定すること。
3. **ビルドフラグは `-ldflags="-s -w"`。** TinyGo は Ebitengine 非対応のため選択肢に入らない。
4. **プロンプト制約に「`fmt` と `reflect` を使わせない」を含める**（6.1）。バイナリサイズに効く。
5. **ロード中の画面に OGP スクリーンショット・作者名・親ゲーム名・「改造する」ボタンを先に表示する。** 数秒を「待ち」ではなく「文脈の提示」に変える。
6. ゲーム1本ごとに別ファイルであり、初見の URL を踏むのがコア体験であるため、**CDN キャッシュは基本的にヒットしない**。この前提でロード時間を見積もる。

### 3.5 `wasm_exec.js` のバージョン整合（運用事故の予防）

`wasm_exec.js` はビルドに使った Go のバージョンと厳密に一致する必要がある。Go を更新すると過去にビルドした全 wasm との組み合わせが壊れる。

**採用バージョン: Go 1.26.5**（確定12）。選定理由は次のとおり。

- 現時点でサポート中の Go は 1.26.x と 1.25.x の 2 系統。Go は「2 つ新しいリリースが出るまでサポート」の方針であり、**1.27 が 2026 年 8 月に出ると 1.25 はサポート切れになる**。ビルドサーバーは攻撃者が制御しうるコードをコンパイルする環境（7.1）であるため、セキュリティ修正が届かないバージョンは選べない。
- 1.26 を選べば 1.28 リリースまでサポートが残り、MVP の実装期間中にサポート切れを踏まない。
- Ebitengine は v2.9.9 の `go.mod` が `go 1.24.0`、main ブランチが `go 1.25.0` を要求する。いずれも 1.26 上でビルドできる。
- 1.27 の x.0 を待つ選択は取らない。リリース日まで M2-4（ビルドコンテナ）が着手できず、かつ Ebitengine 側の追随が未検証になるため。

**`wasm_exec.js` の位置:** Go 1.24 以降は `$(go env GOROOT)/lib/wasm/wasm_exec.js`（1.23 以前は `misc/wasm/`）。イメージからこのファイルを取り出して配信側へ配置する。

**出し分け方針:** ビルド時の Go バージョンを `games.go_version` に保存し、**対応する `wasm_exec.js` を出し分ける**。全件再ビルドは生成枠を消費しないが**ビルドの実行時間**（確定24 以降は Lambda の課金時間。4.6）と R2 オペレーションを消費するため、通常運用では選ばない。

**更新手順（Go を上げるとき）:**

1. Dockerfile のバージョンを上げ、Ebitengine のサンプルビルドが通ることを確認する。
2. 新バージョンの `wasm_exec.js` を配信側へ追加する（**既存バージョンのものは消さない**）。
3. 以後の新規ビルドのみ新バージョンになる。過去の `games` 行は `go_version` に従って旧 `wasm_exec.js` で配信され続ける。

### 3.6 D1 の無料枠に関する注意

D1 は読み取りより**書き込みの無料枠が桁で小さい**。実値は次のとおり（2026-08-11 時点、Workers Free）。

| 項目 | 無料枠 | 有料プランの単価 |
|---|---|---|
| 行書き込み | **10万行 / 日** | 月 5,000万行まで込み、以降 $1.00 / 100万行 |
| 行読み取り | 500万行 / 日 | 月 250億行まで込み、以降 $0.001 / 100万行 |
| ストレージ | 5 GB | 5 GB まで込み、以降 $0.75 / GB-月 |

書き込みと読み取りで**単価が 1,000 倍違う**。無料枠の差（50 倍）以上に、有料化後の差が大きい。

- **リクエスト毎の書き込みを避ける。** プレイ回数やスタンプ評価を都度書くと即座に枯れる。集計はバッチ、またはカウンタを別レイヤに置く。
- タイムラインの読み取りは Cache API を前段に置く。
- 本仕様の書き込みは生成・公開・フォーク・招待に限定されるため、月数百件規模であり無料枠を圧迫しない。

### 3.7 R2 の保存量とゴミ掃除

エグレスは無料だが、**保存量とオペレーションは課金対象**である。実値は次のとおり（2026-08-11 時点、Standard ストレージ）。

| 項目 | 単価 | 無料枠 |
|---|---|---|
| ストレージ | $0.015 / GB-月 | **10 GB-月** |
| Class A（書き込み・一覧） | $4.50 / 100万リクエスト | 100万 / 月 |
| Class B（読み取り） | $0.36 / 100万リクエスト | 1,000万 / 月 |
| エグレス | 無料 | — |

- 1本あたり `.wasm.br` 2〜3MB ＋ `source.go` 10〜30KB。
- **月 500 生成でも 1.5GB/月**であり、無料枠 10GB を使い切るまで約 6 ヶ月かかる。オペレーションは月数百件で無料枠の 0.1% 未満。**当初想定よりコスト圧力は弱い。**
- **未公開のまま放置された成果物が溜まる。** 確定4（生成 → 試遊 → 「公開」。5.4）により、プレビュー用のビルドは公開前に走るため、公開されなかった分がそのまま残る。
- **ライフサイクルルールで「14日間未公開なら自動削除」を設定する（確定13）。** 金曜に生成して翌週末に戻る程度の間隔を吸収でき、最悪ケースでも未公開分の常時保存量は 0.7GB（無料枠の 7%）に収まる。
- **この 14 日はコストではなく体験から決めた値である。** 無料枠が厚いため保存量は制約にならない。設定する理由は、ゴミが溜まって保存量が公開本数と乖離した状態を可視化できなくすることを防ぐためである。

### 3.8 ビルド実行環境（AWS Lambda / コンテナイメージ）（確定24）

- **ベースイメージ:** `GOOS=js GOARCH=wasm` のクロスビルドであり musl/glibc は無関係なので、Alpine である必然性はない。**`golang:1.26.5` をピン留めする（確定12）。更新手順は 3.5 に定義済み。** これを **Lambda のコンテナイメージ**として ECR へ置き、入口だけ Lambda Runtime API へ付け替える。イメージは **1.51 GB 実測**（Lambda の上限 10 GB。#76）。
- **CPU とタイムアウト:** **メモリ 3,538 MB（`--cpus=2` 相当）で 5.3 秒**（実測）。**タイムアウトは 10 秒を維持する。** Lambda の vCPU はメモリに比例するため、**`--memory=512m` では 2 vCPU を得られない**。7.1 が書いていた `--cpus=1` は実測 **11.3 秒**で 10 秒に収まらないため、ここで改める（7.1）。
  - **未実測:** **brotli q11 の圧縮時間**を 5.3 秒に足して 10 秒へ収まるかは**未検証**である（7.1 の「実測なし」）。
- **高速化:** **`GOMODCACHE` の永続化は成立しない。** 永続ボリュームが無く、書き込めるのは実行環境ごとの `/tmp` だけになるためである（7.1）。**もともと効きが薄いことは実測済み**で、キャッシュ空 12 秒 / 温 11〜12 秒とほぼ差が出ない。**支配項はコンパイルではなくリンク**で、そこにキャッシュは効かない（#76）。したがって**速度はキャッシュではなくメモリ配分で買う**（上記 3,538 MB）。Ebitengine を vendor 済みでイメージに焼き込む点は変わらない（7.1 のネットワーク遮断のため必須）。
- **ビルド結果キャッシュ:** 生成ソースのコンテンツハッシュでビルド結果をキャッシュし、実質同一コードの再ビルドを避ける。**保存先は関数の `/tmp` に置けない。** `/tmp` は実行環境ごとに分かれ、しかも 7.1 の掃除で毎回消えるためである。**関数の外**（R2 の既存オブジェクトと D1 の索引）に置く。
- **同時実行制御:** Worker Pool は不要になり、**Lambda の予約同時実行数（reserved concurrency）**で並列数を絞る。タイムアウトは関数のタイムアウト設定（10 秒）で与える。**プラットフォーム側の機能で足りる。**
- **degrade 設計:** ビルド経路が止まっても、**既存ゲームのプレイと URL 拡散は R2 からの静的配信で生き続ける**。これは本構成の資産であり、実行環境が Lambda になっても変わらない。停止時は生成 UI に「生成停止中」を表示し、プレイ側には一切影響を出さない。
  - **ただし主語が変わった。** VPS では「サーバーが落ちる」が停止事象だったが、Lambda には常時起動の資産が無いため、停止事象は**関数の失敗・スロットリング（予約同時実行数の枯渇）・リージョン障害**になる。**degrade の発火条件は「VPS の死活監視」ではなく「ビルド依頼の失敗」で判定する。**

> **#76 注記（確定24）。** v1.8 までの 3.8 は表題が「ビルドサーバー（さくらのVPS / Docker）」で、
> 「**高速化:** `GOCACHE` に加えて **`GOMODCACHE` も永続化**する」「**同時実行制御:** Worker Pool に
> よる並列数制限とタイムアウト（最大10秒）」「**degrade 設計:** VPS が停止しても、…」と書いていた。
> **旧記述はこの注記に残す。** `GOMODCACHE` の永続化は永続ボリュームが無くなったため成立せず、
> **「永続ボリュームが要るから VPS」という論拠は実測でも消えている**（キャッシュがほぼ効かない）。

**失敗の質も違う。** Sonnet 4.6 の唯一の失敗は存在しない API の捏造
（`vector.DrawFilledRoundRect`）で、**機械修正では救えず LLM の再生成が要る。**
DeepSeek の失敗は未使用 import が支配的で、**半分は機械修正で救えた**（下記）。

#### フォーク（試算）

親ソースが入力に乗り、thinking も乗る。

| 内訳 | トークン | `jp.anthropic.claude-sonnet-4-6` |
|---|---|---|
| 入力（システムプロンプト 1k ＋ 親ソース 9k） | 約 10,000 | $0.030 |
| 出力（新規生成の実測 4,171 を基準に、差分生成でやや増える想定） | 4,000〜6,000 | $0.060〜0.090 |
| **1 生成** | | **約 14〜18 円** |

**親ソースの想定を 5KB から 9KB へ上げた。** 新規生成の実測が平均 9,158 bytes だったため
（v1.1 までの 5KB は根拠のない見積もりだった）。

#### 実効値はコンパイル成功率で決まる

**単価より成功率が効く。** #7 の実測（DeepSeek v3.2、6 本）:

| 状態 | 成功 |
|---|---|
| 生成のまま | 1 / 6 |
| **未使用 import を機械的に除去して再ビルド** | **3 / 6** |

**機械修正は追加トークンを消費しない。** リトライは 2 段構成にする（#20）。

1. **機械修正**（費用ゼロ）— 未使用 import の除去、不足 import の補完
2. **LLM 再生成**（費用が発生）— 型の不整合など、意味を要する失敗

許可外パッケージの import は**リトライしない**（5.2-5 に従い即拒否）。

**支配項は出力トークンである。** prompt caching は入力側にしか効かず、Claude 側にしか無い。
コスト削減の主戦場は次の 3 点。

- **モデルの選択**（本章の表のとおり桁が違う）
- **ソースサイズの上限（5.3 で 30KB）**
- **`effort` の設定**（Claude のみ）。thinking トークンは出力として課金されるため、`effort` は
  実質そのままコスト倍率になる。**`high` と `medium` の A/B は最優先の実験項目**とし、
  生成成功率と併せて初期に必ず測定する（#25）。

### 4.3 月次上限機構（必須実装）

- **上限額: 1万円/月。** 実質の生成枠は**モデル構成で変わる**（4.2 の実測）。すべて
  Sonnet 4.6 なら月およそ **840 本**（1 日あたり 28 本）、すべて DeepSeek なら月およそ
  **6,100 本**。いずれもコンパイル成功 1 本あたりの実効コストで割った値である。
- **判定は推定値ではなく実測累計で行う。** 各レスポンスの `usage`（`inputTokens` /
  `outputTokens` / `cacheReadInputTokens` / `cacheWriteInputTokens`）から**モデル別の単価で**
  円換算し、D1 の費用台帳に加算する（#84）。**リトライ分も必ず計上する。**
- **`usage` の項目はモデルで違う。** DeepSeek はキャッシュの 2 項目を返さない（4.1）。

#### 日次クォータは 1 人あたり 1 日 12 回とする（2026-08-27 決定 / #7 / 確定25）

**数える単位は「費用の出る LLM 呼び出し回数」である。** 1 利用者・1 暦日あたり **12 回**。
**リトライによる LLM 再生成は数に入れ、費用ゼロの機械修正（4.2）は数えない。**
枠の境界は **JST の 0 時**とする（UTC 0 時にすると日本時間の午前 9 時に枠が戻り、
4.4 が示す「翌日の再開時刻」が利用者の「明日」と一致しない）。判定位置は 3.3-2 で、
月次 1 万円の判定と同じ層 1 に属する（実装は #23 / M3-2）。

##### 逆算（Claude Sonnet 4.6 の実測を前提にする）

| 段 | 式 | 値 |
|---|---|---|
| 月次上限 | 確定6（動かさない） | **10,000 円/月** |
| 1 日あたりの全体枠 | 10,000 ÷ 30 日 | 約 **333 円/日** |
| 成功 1 本の実効コスト | 4.2 の実測（9.9 円 ÷ 成功率 5/6） | **11.9 円/本** |
| 全体で 1 日に出せる成功本数 | 333 ÷ 11.9 | 約 **28 本/日**（＝ 月 840 本） |
| 同じものを生成回数で見ると | 333 ÷ 9.9 | 約 **34 回/日** |
| **1 人の 1 日の取り分** | 34 ÷ **3 人** ＝ 11.3 → 切り上げ | **12 回**（成功に直して 12 × 5/6 ＝ **10 本ちょうど**） |

**割る「3 人」は招待者数ではない。同じ日に枠を上限まで使い切る人数の想定である。**
言い換えると、**1 人が 1 日で全体枠（34 回）の 35% までしか食えない**ように蓋をした値である。
**11.3 を 12 へ切り上げたのは、成功換算がちょうど 10 本になり 4.4 の残枠表示が説明しやすいからで、
この 0.7 回分は月次判定（層 1）の内側にある。**
1 人が上限まで使い続けたときの月額は 12 回 × 9.9 円 × 30 日 = **3,564 円**（月次上限の 36%）で、
**1 アカウントだけでは月を落とせない。**

**日次クォータは、合計しても月次上限を保証しない。** 招待者 30 人が毎日 12 回ずつ使えば
1 日 3,564 円で、3 日で 1 万円へ届く。**総額を止めるのは層 1 の月次判定であり、
日次クォータの役割は 1 人あたりの上振れの蓋である。** 両方を同じレバーで担わせない
（層 4 をレート専用の補助に降ろしたのと同じ理由である）。

##### 招待者数の想定は 30 人（天井は 100 人）

2.1 の「数十人規模」を、**8.1 の天井の 3 割**に置いた。天井は招待枠の設計（確定2 / 8.1 の
1 人 3 本）ではなく、**Google OAuth を Testing のまま運用する決定（#89 / 8.1）による
テストユーザー登録の上限 100 人**である。

| 招待者 | 全体枠 34 回/日 を割った平均 | 意味 |
|---|---|---|
| **30 人（想定）** | **1.1 回/日・人** | 12 回の枠に対する平均利用率 9%。毎日は生成しない母数として成立する |
| 100 人（天井） | 0.34 回/日・人 | 3 日に 1 回。**枠の値ではなく平均利用率の想定が先に破れる** |

**天井まで招待しても日次クォータ 12 回は変えない。** 変わるのは平均利用率の前提であり、
**招待者が 60 人を超えた時点で 10.2 の補助指標「招待者あたりの生成数」の実測と突き合わせ、
本節の値を見直す**（下記）。

##### なぜ DeepSeek ではなく Sonnet 4.6 を前提に引くか

1. **安いほうを前提にした枠は蓋にならない。** DeepSeek（0.8 円/生成）で引くと同じ式で
   **139 回/日**（333 ÷ 0.8 ÷ 3）になる。その枠のまま Claude を選ぶと 1 人 1 日 1,376 円、
   **7 日で月次上限に届く。** 逆に Sonnet で引いた枠を DeepSeek で使っても費用は減るだけである。
2. **既定のモデルが Sonnet 4.6 である。** `GENERATION_MODEL` の既定は
   `jp.anthropic.claude-sonnet-4-6`（`src/generation-models.ts` の
   `DEFAULT_GENERATION_MODEL_KEY`）で、実際に燃えるのはこちらの単価である。
3. **遊べる 1 本を出す主経路が Sonnet である。** DeepSeek の成功率は機械修正込みでも 3/6 で、
   4.2 の「1 本の成功あたり」で見ても利用者が受け取る本数が半分になる。

**モデルによって枠は変えない。** DeepSeek を選んだ日も 12 回である。枠は費用の器ではなく
暴走の蓋であること、モデル別に枠を変えると 4.4 の「本日の残り生成枠 N 回」が利用者から見て
説明できない数字になることによる。**DeepSeek に寄った月は費用側に余裕が出る**
（12 回 = 9.6 円/日・人で Sonnet の 1/12）。ただし成功率が 3/6 のため、**受け取れる本数は
12 回で約 6 本**に減る。

##### 層 2 より先に発火することの確認

層 2 は 5 分間で 300,000 トークンである。**日次クォータはその手前で止まる。**

| | トークン | 層 2 のしきい値に対して |
|---|---|---|
| 1 生成（Sonnet 4.6 の実測 1,092 ＋ 4,171） | 5,263 | 1.8% |
| **1 アカウントが日次クォータ 12 回を使い切る** | **63,156** | **21%** |
| 1 生成（DeepSeek の実測 911 ＋ 2,159） | 3,070 | 1.0% |
| 同じく 12 回 | 36,840 | 12% |

- **1 アカウントのループバグは、層 2 のしきい値の 1/4 に届く前に層 1 が止める**（21%）。
- 層 2 が発火するには 5 分以内に 57 生成、すなわち **5 アカウント弱が同時に枠を使い切る**
  必要がある。招待者 30 人・想定利用率 1.1 回/日の母数では正常な利用で起きず、起きたときは
  4.3 の判定基準どおり「アプリのループバグ」である。
- 月次側も同じ向きである。層 1 の 1 万円は、層 3 の 85 USD（130 円/ドルでも約 11,050 円）より
  先に発火する。

> **ただし層 2 の「正常な利用で到達しない」は母数に依存する。** 天井の 100 人が同じ 5 分間に
> 1 本ずつ生成すると 526,300 トークンで層 2 を超える。クローズドβでは起こらない想定だが、
> **招待者を 57 人より増やす場合は層 2 のしきい値も併せて見直す。**

##### この値を動かす引き金

- **招待者が 60 人を超えた**（上表の平均利用率の前提が半分になる）
- **層 1 の 80% 警告が、月の 20 日より前に出た**（想定利用率が実測で破れている）
- **4.2 の成功率が動いた。** 成功率が 5/6 を下回れば 1 本の成功あたりの実効コストが上がる。
  `effort` の A/B（#25）はここを直接動かす
- **値を動かすときは、4.2 の実測との差がどこから来たのかを必ず併記する。** 実測を捨てて
  丸めた値に置き換えない

##### 旧記述との関係（削らずに残す）

- **4.4 の「1日12〜17回という枠」と確定6 の括弧書き「実質 月350〜500生成」は、v1.1 までの
  試算（1 生成 20〜35 円）に基づく「サービス全体」の枠である。** 数字の 12 が本節と
  一致するのは偶然で、**意味が違う**（あちらは全体の 1 日、こちらは 1 人の 1 日）。
  4.2 の実測での全体枠は Sonnet 4.6 で月約 840 本、DeepSeek で約 6,100 本である。
  4.4 の「本日の残り生成枠 N 回」は、**本節の 12 回を 1 人あたりの残数として表示する。**
- **11.3 の「10 本の作成でリトライ込み 15 回前後＝ほぼ 1 日分の生成枠」も旧試算に基づく。**
  本節の値では全体枠 34 回/日 の約 4 割であり、1 アカウントの日次枠（12 回）で見れば
  **2 日に分かれる。** コールドスタートが枠の中の話であることは変わらないため、
  記述はそのまま残す。

#### 上限は四層で担保する（v1.3 で再設計。#81）

D1 の費用台帳による判定は**アプリ層**の制御であり、**アプリのバグでは効かない**（例外パスでの計上漏れ、リトライ分の記録漏れ、判定順序の誤り）。アプリ層だけでは不足する。

**Bedrock には spend limit も前払いクレジットも無い。** 直販で最外周に据えていた「残高が
尽きたら物理的に止まる」層は作れない。代わりに、**役割の違う 3 つの機構を外側に積む。**

| 層 | 実体 | 捕まえるもの | 遅れ | 迂回可能性 |
|---|---|---|---|---|
| 1. アプリ層 | D1 費用台帳＋月次 1 万円判定 | **主。** 80% 警告・残枠 UI・degrade（4.4） | 即時 | アプリのバグで迂回されうる |
| 2. **暴走検知** | CloudWatch アラーム（短時間のトークン量）→ **明示的 Deny の付与** | **ループバグによる暴走** | 5〜10 分 | **迂回不可** |
| 3. 会計層 | AWS Budgets Actions（月次予算）→ **明示的 Deny の付与** | **台帳が静かにずれた緩やかな超過** | 数時間 | **迂回不可** |
| 4. 補助 | Bedrock のレートクォータ引き下げ | ピーク燃焼率の抑制 | 即時 | **迂回不可**（ただし下記の制約あり） |

**2 と 3 は役割が違う。1 つの機構では両方を捕まえられない。**

- **2 は「速いが総額を知らない」。** 短時間のトークン量しか見ないため、緩やかな超過は素通りする。
- **3 は「総額を知っているが遅い」。** コストデータの反映に数時間かかるため、暴走を止めるには遅すぎる。

##### なぜクォータを最外周にしないのか（#81 で覆った想定）

**クォータはレートを縛るだけで総額を縛らない。** 月 1 万円は約 1,012 生成/月 = 平均 123
トークン/分にあたるが、**1 回の生成に約 5,300 トークン要る**ため、そこまで絞ると 1 本も
生成できない。「1 生成を通す」と「月を縛る」を同じレバーでは両立できない。

**さらに DeepSeek のクォータは 1 つも調整できない**（実測）。

| モデル | RPM | TPM | 日次トークン |
|---|---|---|---|
| Claude Sonnet 4.6 | 10 **（調整可）** | 6M **（調整可）** | 10.8M（調整不可） |
| **DeepSeek V3.2** | **100（調整不可）** | **100M（調整不可）** | 5.4B（調整不可） |

したがってクォータは**補助**（層 4）に留まる。**層 4 が無くても設計は成立する**ように、
層 2 のしきい値は現行クォータのままで上振れが収まる値にする。

> **クォータの引き下げが API で要求できるかは未確認である。** Service Quotas は増加要求の
> API しか持たない。引き下げられなければ層 4 は無いものとして運用する。

##### 上振れの見積もり（実測に基づく）

現行クォータで両モデルが同時に暴走した場合の燃焼は **1 分あたり約 181 円**
（Claude 10 RPM × 9.88 円 ＋ DeepSeek 100 RPM × 0.82 円）。

| 検知手段 | 遅れ | 上振れ |
|---|---|---|
| **層 2（CloudWatch）** | 5 分 | **約 900 円** |
| 同 | 10 分 | **約 1,800 円** |
| 層 3（Budgets）のみ | 8 時間 | 約 87,000 円 |
| 同 | 12 時間 | 約 130,000 円 |

**層 2 を置かず層 3 だけにすると、月 1 万円の上限に対して 1 桁多い上振れを許す。**
本章が「必須実装」としている「機構的に停止する」を満たさない。

##### 層 2 の設定

- **メトリクス:** `AWS/Bedrock` の `InputTokenCount` ＋ `OutputTokenCount`（全モデル合算）
- **期間:** 300 秒、1 データポイントで発火
- **しきい値:** **5 分間で 300,000 トークン。** Claude なら約 57 生成、DeepSeek なら約 98
  生成にあたる。招待制で数十人という規模では**正常な利用で到達しない**一方、発火時点の
  損害は 600 円程度に収まる
- **動作:** SNS → Lambda が `game-forge-bedrock-invoker` へ**明示的 Deny のポリシーを付ける**
- **復旧は手動とする。** 暴走の原因を調べる前に自動で戻すと、同じ暴走を繰り返す

##### 層 3 の設定

- **月次予算 85 USD**（100% で**明示的 Deny の付与**、80% で通知のみ）
- **為替バッファの向き。** アプリ層の 1 万円より**先に発火してはいけない**ので、円高側に
  振れても余裕が残る値にする。85 USD は 130 円/ドルでも約 11,050 円で、1 万円を上回る
- **開発アカウントは別予算 10 USD。** Dev は SSO の一時資格情報で人が手動に叩く場所で、
  アプリのループが走らない。予算は事故の上限としてのみ置く

##### 停止の実体は「剥奪」ではなく「明示的 Deny の付与」である（v1.7 / #82）

> **v1.6 まではこの節が無く、上の記述は「IAM ポリシーを剥がす」だった。** 実装時に
> 成立しないことが分かったため改めた。**旧記述は上の表と設定から差し替えてある**が、
> 何をどう変えたかはこの節に残す。

層 2 と層 3 は、許可ポリシーを**剥がすのではなく**、専用の Deny ポリシーを
`game-forge-bedrock-invoker` へ**付ける**ことで停止する。明示的 Deny は同一アカウント内の
Allow を必ず上書きするため、**停止の効果は剥奪と同じ**である。理由は 2 つある。

1. **剥がすと宣言と喧嘩する。** 許可は Terraform の宣言（`aws_iam_user_policy`）として
   存在する。ガードがそれを削除すると `terraform plan` に差分として現れ、**発火とは
   無関係な apply が、原因を調べる前にアクセスを黙って復活させる。** これは上の
   「復旧は手動とする」に正面から反する。DNS やリポジトリ設定の変更でも apply は走るため、
   これは想定しにくい事故ではない。
2. **層 3 は付与しかできない。** AWS Budgets Actions の `APPLY_IAM_POLICY` は、指定した
   ポリシーを**付ける**動作しか持たない。層 2 だけを「剥がす」にすると、**発火した層に
   よって復旧手順が変わる。** 揃えれば復旧は常に「Deny を外す 1 回」で済む。

**復旧を権限で強制する。** Lambda に detach の経路を持たせず、実行ロールにも
`iam:DetachUserPolicy` を与えない。手動復旧は規約ではなく権限で担保する。

##### 判定基準（再定義）

**どの層が発火したかで、何のバグかが分かる。**

| 発火した層 | 意味すること |
|---|---|
| 層 2（暴走検知） | **アプリのループバグ。** リトライの暴走、例外パスでの再入 |
| 層 3（Budgets） | **台帳のずれ。** 計上漏れ、円換算の誤り、判定順序の誤り |

**いずれもアプリ層のバグである。** 層 1 が正しく動いていれば、2 も 3 も発火しない。
v0.9 までの「プロバイダ層が先に発火したらアプリ層のバグ」という基準は維持されるが、
**どちらの種類のバグかまで切り分けられるようになった。**

##### 受け入れた劣化

- **「事実による即時停止」は作れない。** 直販の前払いクレジット残高は設定ミスの影響を
  受けない層だったが、Bedrock は後払いのみで同等物が無い。層 2 と 3 はどちらも
  「設定」であり、設定を誤れば効かない
- **最大で約 1,800 円の上振れを許容する。** 層 2 の検知が最も遅い場合の値である
- **DeepSeek のレートを絞れない。** 暴走時の燃焼率の大半はここで決まる

##### その他

- **開発分は Dev アカウントで分離する**（9.2 / 確定21）。同居させるとレートクォータが
  共有され、開発の暴走が本番の枠を食う。
- **80% で警告、100% で生成停止。** 停止時は 3.8 の degrade 設計に従い、プレイと拡散は継続する。

### 4.4 生成枠の UX 上の扱い

1日12〜17回という枠は、UI に露出させなければ「押しても動かないボタン」になる。

- 「本日の残り生成枠 N回」を常時表示する。
- 枠が尽きたら「本日の枠は終了しました」と明示し、翌日の再開時刻を示す。
- 月次上限に達した場合は「今月の生成は終了しました。プレイと共有は引き続きご利用いただけます」と表示する。

### 4.5 prompt caching の設計

レンダリング順は `tools` → `system` → `messages`。Sonnet 5 の**最小キャッシュ長は 1,024 トークン**。

**本節は Claude 経路にのみ適用される。** DeepSeek は `Converse` 経由でキャッシュの課金次元を
持たない（4.1）。また **Bedrock では自動 prompt caching が使えない**ため、`cache_control` を
手動で配置する。#79 で 2 回目の呼び出しに効くことを確かめる（#82 へ移管済み）。

- **システムプロンプト（6 章の Ebitengine 制約、2,000 トークン程度）を `system` に置く。** 全生成で共有されるプレフィックスとなり、トラフィックが続く限り常時ホットになる。TTL は 5 分（書き込み 1.25倍）で足りる。
- **親ソースは `messages` の先頭ブロックに置き、別ブレークポイントを打つ。** 親ごとのキャッシュになる。1時間 TTL（書き込み 2倍）はバズ中の作品に限定しないと、書き込み割増で損をする。
- **キャッシュヒットの検証:** `cacheReadInputTokens` がゼロのまま推移する場合、プレフィックスに揮発値（タイムスタンプ・UUID・ユーザーID）が混入している。システムプロンプトには一切の動的値を入れない。

> **項目名の表記について。** 本仕様で参照するのは **`Converse` が返す camelCase**
> （`inputTokens` / `outputTokens` / `cacheReadInputTokens` / `cacheWriteInputTokens`）である。
> 4.1.1 と 5.1 に出てくる snake_case（`input_tokens` 等）は、それぞれ Anthropic 直販の
> `count_tokens` API の表記と、D1 の列名であり、**Bedrock のレスポンスのキーではない。**

## 5. 生成・フォーク・公開のデータモデルと仕様

### 5.1 主要テーブル（D1）

| テーブル | 主な列 |
|---|---|
| `users` | `google_sub`（一意）、`email`、`display_name`、`x_handle`（任意・未検証）、`invited_by`、`created_at`、`banned_at` |
| `invites` | `code`、`issued_by`、`used_by`、`used_at`、`expires_at` |
| `games` | `id`、`author_id`、`parent_id`、`status`（draft/published/removed）、`title`、`go_version`、`source_key`、`wasm_key`、`fork_count`、`created_at`、`published_at` |
| `generations` | `id`、`game_id`、`user_id`、`prompt`、`model`、`input_tokens`、`output_tokens`、`cache_*_tokens`、`cost_jpy`、`succeeded`、`created_at`（**D1 の列名。** Bedrock のレスポンスは camelCase で、そこから写す。4.5） |
| `reports` | `id`、`game_id`、`reporter_id`、`reason`、`created_at` |
| `waitlist` | `id`、`email`（一意）、`source`、`created_at` |

`games.parent_id` にインデックスを張る。`fork_count` は非正規化して一覧を軽くする。

`waitlist` は未招待ユーザーの導線（8.1 / 2.2-4）の保存先である。`email` を一意にするのは、同じ人が繰り返し登録しても 10.2 の「待機リスト登録率」の分子が増えないようにするため。`source` はどの導線から来たかを区別し、同じく 10.2 の補助指標に使う。

時刻の列はすべて **UNIX 秒の INTEGER** で持つ。文字列の日時にすると比較のたびに変換が要り、境界の扱いが実装ごとにぶれる。招待コードとセッションの失効判定も UNIX 秒で揃える。

### 5.2 生成フロー（新規作成）

1. 招待コード保有ユーザーが自然文プロンプトを入力。
2. 入力の安全性検査（8.1）。
3. Workers が日次クォータと月次上限を判定。
4. Sonnet 5 で Go ソースを生成。
5. **AST でパッケージのホワイトリスト検査**（7.1）。違反は再生成に回さず拒否。
6. **ビルド関数（Lambda）でビルド**し、**そのまま R2 へ置く**（3.3 / 確定24。v1.8 までは「VPS でビルド。」。**v1.9 は「返り値の `.wasm.br` を書き戻し関数が R2 へ置く」だったが、#76 で VPC ごと撤回した**）。
7. **コンパイル失敗時はエラー出力を LLM に返して自動リトライ（最大2回）。** 各試行の費用を台帳に計上する。
8. 成功したら `status='draft'` で作成し、作者のプレビュー画面へ。

### 5.3 フォークの仕様

**フォークは「親のソースコード＋差分プロンプト」で行う。** プロンプト履歴を積んで再生成する方式は採らない。理由は、LLM が同じ入力でも別の出力を返し、モデルを更新すれば過去の全作品が別物になるため、系統図が意味を失うからである。

- **親の最終ソースコードを永続保存する**（R2 に `source.go`）。これがなければフォークは再現できない。
- 差分の出し方は **MVP では全文再出力**とする。search/replace 形式のパッチは出力トークンを減らせるが LLM が壊しやすく、リトライが増えて逆効果になりやすい。
- **ソースサイズの上限を 30KB とする。** フォークのフォークで肥大化すると入力コストと失敗率が同時に上がる。

#### 30KB を超えたときの挙動（確定18）

**超過時は、作者の選択で LLM に整理させる。拒否のみは採らない。**

拒否だけだとフォーク連鎖が 30KB で行き止まりになる。**撤退条件（10.3）に「3 世代以上の系統が 1 本も出ていない」が入っている以上、システムが構造的に世代数を制限するのは、自分で立てた撤退条件を自分の実装で不成立にしうる**ためである。

実装は次の 4 条件を伴う。1 つでも欠くと、枠の浪費か体験の破壊になる。

| # | 条件 | 理由 |
|---|---|---|
| 1 | **入力段階で事前警告する。** 親ソースが閾値（24KB＝上限の 80%）を超えていたら、フォーク開始前に「この作品はすでに大きめです」と伝える | 事前警告が無いと、作者は「生成してみたら枠を 2 回使わされた」体験になる |
| 2 | **整理は自動実行せず、作者が明示的に選ぶ。**「整理して続けますか（生成枠を 1 回使います）」と問う | 整理パスは全文再出力で実質もう 1 生成分（20〜35円）。日次枠 12〜17回の 1 回を、作者の知らないうちに消費させない（4.4 の方針と逆行するため） |
| 3 | **整理は 1 回まで。** 整理後も 30KB を超えたら、そこで拒否する | 無限ループの防止 |
| 4 | **整理パスがコンパイルに失敗しても自動リトライしない。** 元のソースへ戻して拒否する | リトライ（5.2-7）が乗ると最悪 3 回分の枠を消費する。失敗の連鎖を切る |

- **整理したことは作者に開示する。** 6.2 の「置換したことをユーザーに開示する。黙って別物を出すのは体験として悪い」と同じ原則を適用する。
- **整理でゲームの挙動が変わるリスクは機械検証できないが、新しいリスクではない。** 5.4 が既に「コンパイルは通るがゲームとして成立していない」ことは機械判定できないため作者を唯一のフィルタとする設計を採っている。整理後も作者が試遊して「公開」を押すため、このフィルタはそのまま効く。
- 系統は**単一親のツリー**とする（DAG は不要）。
- **親の削除は物理削除せず tombstone 化**し、子は残して「削除済みの作品から派生」と表示する。連鎖削除は荒れるため採らない。

### 5.4 公開フロー

**生成 → 作者が試遊 → 「公開」操作で初めて URL が有効になる。**

- 生成直後は `status='draft'`。作者だけがプレビューできる。
- プレビュー配信の権限制御は、**Workers 経由で所有者チェックしてから R2 から返す**（R2 → Workers 間は無料）。MVP では推測不能なランダムキーによる unlisted 配信でも実用上足りる。
- **OGP 画像の生成は「公開」時まで遅延する。** 未公開分のスクリーンショット生成コストが丸ごと不要になる。
- 未公開のまま 14 日経過した成果物は自動削除（3.7、確定13）。
- 試遊画面の主ボタンは「**公開して共有**」とし、1タップに畳んでフォーク連鎖の遅延を最小化する。

この一段があることで、「コンパイルは通るがゲームとして成立していない」作品がタイムラインに流れることを防ぐ。これは機械判定できないため、作者を唯一のフィルタとして使う設計である。

### 5.5 系統の表示（MVP 範囲）

- 作品ページに「**元ゲーム: ○○**」（1リンク）と「**このゲームからの改造: N件**」（`status='published'` のみ、新しい順、20件＋もっと見る）を表示する。
- ツリー全体の家系図 UI は MVP 対象外（11 章）。
- **自分の作品が改造されたら作者にメールを1通送る。** バッジのみでは再訪しない限り気づけず、コア体験ループが閉じない。
- **送信は Resend を使う（確定14）。** 無料枠 3,000通/月・100通/日・1ドメイン。生成枠が 12〜17回/日である以上、日次上限には構造上到達しない。HTTP API のため Workers の無料プランからそのまま呼べる。
  - Cloudflare Email Sending は Workers 有料プラン（$5/月）を要求するため採らない。3.2 の「Workers は無料枠」と 4.6 の「実質ゼロ」の両方を崩す。
  - Amazon SES は単価では最安（$0.10/1,000通）だが、サンドボックス解除申請と、管理する資格情報が 1 つ増える。月数百通の規模でその手間に見合わない。

### 5.6 権利と原作者クレジット

- 作品ページと OGP に原作者名を表示する。`x_handle` は**未検証の自称値**であるため、**MVP ではリンク化せず表示のみ**とする（なりすましの踏み台を作らない）。
- 利用規約に「**投稿は、他ユーザーによる改変・再配布を許諾するものとする**」旨を明記する。これがなければフォーク機能そのものが法的に不安定になるため、MVP でも省略できない。
- 生成物の権利帰属（ユーザーに帰属し、サービスへ非独占の利用許諾）を規約に定める。
- **LLM プロバイダ側の規約は確認済み（確定15）。** Anthropic の商用利用規約は「顧客が Output を所有する」「Anthropic は Output に対する権利を顧客へ譲渡する」「自社の顧客・エンドユーザーへ提供する製品・サービスに使える」と定めており、**生成物の再配布・サブライセンスに制限はない。** 本プロダクトの構成（生成物をユーザーに帰属させ、公開・フォークを許諾する）と矛盾しない。
- **ただし通知義務がある。** 同規約は「Output に含まれる事実の主張は、正確性を独自に確認せずに依拠すべきでない」旨をユーザーへ通知することを求める。**利用規約にこの一文を含める**（M6-5 の範囲）。

## 6. プロンプトエンジニアリング & ガードレール

### 6.1 Ebitengine 生成の共通制約（システムプロンプト）

- `ebiten.Game` インターフェース（`Update` / `Draw` / `Layout`）の厳格な実装。
- **外部ファイルロードの全面禁止**（`ebitenutil.NewImageFromURL` 等）。描画手段は次の 3 つとする（確定23 / #72）。
  1. `vector` パッケージによる図形描画
  2. コード内の算術ピクセル描画
  3. `text/v2` ＋ `basicfont` による文字描画

  **3 を許しても外部ファイルロードの全面禁止には抵触しない。** `basicfont` は Go のソースにビットマップを埋め込んだフォントであり、実行時に何も読まないためである（`basicfont` の `mask7x13` は 96 グリフ分 7,488 バイトの `image.Alpha` を Go のソース中の配列リテラルとして持つ。ファイルを開かないだけでなく、許可していない `embed` パッケージも要らない）。**禁じているのは実行時に外部から取ってくる経路であって、フォントという概念ではない。** 許す以上、**`text/v2` の使い方までプロンプトへ書くことが必須になる**（下記「制約を並べるだけでは足りない」）。
- **`fmt` と `reflect` を使わない**（3.4：バイナリサイズ削減）。
- 許可パッケージのホワイトリストを明示し、AST 検査（7.1）と一致させる。
- ソース全体を 30KB 以内に収める。

**システムプロンプトはモデルごとに持つ（確定5）。** 上の制約は共通だが、**同じ制約文でも
モデルによって出力が変わる**ため、1 本のプロンプトを全モデルで共有しない。

このシステムプロンプトは **prompt caching の共有プレフィックス**となる（4.5）。動的値を一切含めないこと。

#### 制約を並べるだけでは足りない（#7 の実測）

DeepSeek v3.2 に上の制約と許可リストだけを与えたところ、**6 本中 6 本がコンパイルに失敗し、
すべて同じ箇所で落ちた。**

```
cannot use basicfont.Face7x13 (variable of type *basicfont.Face)
  as *text.GoTextFaceSource value in struct literal
```

**許可リストが `text/v2` と `basicfont` を並べているが、この 2 つは直接つながらない。**
`text/v2` は `text.Face` を要求し、`basicfont.Face` は `golang.org/x/image/font.Face` である。
橋渡しには `text.NewGoXFace()` が要る。**モデルは旧 `text`（v1）の書き方を出す。**

システムプロンプトに次を書き足したところ、この原因の失敗は 6 本中 0 本になった。

- `text.NewGoXFace(basicfont.Face7x13)` でフォントを作ること
- `text.Draw(dst, str, face, op)` は 4 引数で、座標は `op` で与えること
- `text.Measure(str, face, 0)` は 2 値を返すこと
- 経過時間はフレーム数で数えること（`time` は許可リストに無い）
- `ebiten.Termination` は `errors.New` に渡さずそのまま返すこと

**許可リストに載せた API の「使い方」まで書く必要がある。** 一覧を示すだけでは、
モデルが学習データ中の古い用例を出す。**文字描画を許す以上（確定23 / 下記）、この書き足しは
任意ではなく必須である。** 上の 6 本は「許すかどうか」ではなく「どう書かせるか」で結果が
変わった事例であり、6.1 の制約文だけを整えても成功率は上がらない。

#### 許可パッケージのホワイトリスト

| パッケージ | 用途 |
|---|---|
| `github.com/hajimehoshi/ebiten/v2` | ebiten.Game の実装とゲームループ（6.1） |
| `github.com/hajimehoshi/ebiten/v2/vector` | 図形描画。6.1 が描画手段として名指ししている |

#### 6.1 と 8.3 の食い違いは決着した（確定23 / #72）

**かつて 6.1 と 8.3 は食い違っていた。** 6.1 は描画を「`vector` による図形描画、またはコード内の算術ピクセル描画に限定する」とし、8.3 は「`text` 描画で差別語を画面に出すことは容易」として**文字描画が可能である前提**で出力側モデレーションを設計していた。#17 / #69（M2-3）で上の表を作った時点では 8.3 の前提を採って文字描画と埋め込みフォントを許可したが、**6.1 の文言を直すか、文字描画を落として 8.3 を書き換えるかは未決として残していた。** ここではその未決を消さずに残し、決着の内容を続けて書く。

**決着は「文字描画を許す」である。** 6.1 の「限定する」を上記のとおり改め、`text/v2` と `basicfont` は一覧に残す。**一覧そのものに変更はない。** 根拠は 3 つ。

1. **4.2 の実測はすべて「文字描画あり」で取られている。** コンパイル成功率（Sonnet 4.6 = 5/6、DeepSeek v3.2 = 1/6）も 1 生成あたりのトークン単価も、文字描画を許した許可リストで測った値である（#7）。いま禁じれば 4.2 が丸ごと無効になり、12 章 #1（日次クォータの逆算）が実測のやり直しへ戻る。
2. **サイズを根拠に禁じることはできない。** `text/v2` / `basicfont` の有無を対照した実測は存在しない。**両方を含む隔離ビルドのサンプルで brotli q11 後 1,987,011 bytes**（#76 の実測）であり、3.4 の目標と M4-4 の受け入れ条件である 3MB に対して約 1MB の余裕がある。禁止で削れる量は測られていないのに、失うもの（1 の実測）は確定している。
3. **禁じても 8.3 は完全にならない。** 6.1 が明示的に許す**コード内の算術ピクセル描画**で任意のグリフが描け、その経路には検査対象の文字列リテラルが 1 つも残らない。文字描画の禁止は 8.3 の穴を塞がず、体験（スコア・残機の表示）だけを削る。

**8.3 側は弱めず、限界を明記する形で追随させた**（8.3）。すなわち出力側モデレーションは「安い検査で大半を捕まえる層」であり、算術ピクセル描画や `strconv` での組み立てを捕まえられないことを、仕様として認めた上で 8.4 の通報・審査キューへ渡す。

### 6.2 著作権・有名IP回避ガードレール

## 7. セキュリティ

### 7.1 ビルドサーバーの封じ込め（最重要）

**ビルドサーバーは、攻撃者が制御しうるコードをコンパイルする環境である。** `go build` は cgo 経由のリンカフラグ注入や `go.mod` の依存取得を通じて任意コード実行に至りうる。以下は選択肢ではなく前提条件とする。

> **#76 注記（確定24）。** **本番のビルド実行環境は AWS Lambda（コンテナイメージ）になった**（3.8）。
> 下の `docker run` のフラグ列は、**ローカル開発と `scripts/check-isolated-build.sh` が回す形**として
> そのまま残す（削らない）。**本番構成との対応と、そこで下がった水準**は、フラグ列の後に置いた
> 「本番は AWS Lambda で満たす」以下に書いた。

```
CGO_ENABLED=0
GOFLAGS=-mod=vendor
GOCACHE=/cache/go-build
GOMODCACHE=/cache/go-mod
GOTMPDIR=/tmp

docker run --rm \
  --network=none \
  --read-only \
  --tmpfs /tmp:rw,nosuid,nodev,size=512m \
  --tmpfs /work:rw,nosuid,nodev,size=256m \
  -v go-cache-vol:/cache \
  --user 65534:65534 \
  --pids-limit=64 \
  --memory=512m \
  --cpus=1 \
  --security-opt no-new-privileges \
  ...
```

**`--read-only` だけでは `go build` は動かない。** ビルドは一時ファイルとキャッシュを書くため、書き込み可能な領域を明示的に与える必要がある。上記は「ルートファイルシステムは読み取り専用のまま、書き込みを3か所（`/tmp`・作業ディレクトリ・キャッシュ）に限定して許す」形である。

この構成が成立するには、**イメージ側に次の2つの前提が必要**である。どちらも欠けると確定で失敗するため、Dockerfile と `docker run` は必ずセットで設計すること。

> **#76 注記（確定24）。次の前提 1・2 は、本番では根拠ごと無効になる。** どちらも
> 「`--tmpfs /work` が vendor を隠す」「named volume `/cache` が `root:root` で作られる」という
> **Docker 固有の事情から出た前提**であり、**Lambda には `/work` の tmpfs も `/cache` の
> named volume も存在しない**（書けるのは `/tmp` だけ）。**ローカルでは依然として必要**なので
> 削らずに残すが、本番では前提 1 のコピー先が `/tmp/work` に変わり、前提 2 は消える。

1. **vendor 済みテンプレートは `/work` ではなく `/src` に焼き込む。** `--tmpfs /work` は空のファイルシステムをその位置にかぶせるため、`/work` に vendor を置くと**マウント時に隠れて見えなくなり**、`--network=none` 下で依存を解決できずビルドが必ず失敗する。エントリポイントで `/src` から `/work` へコピーし、そこへ生成コードを置いてビルドする。`/src` は読み取り専用のルートファイルシステム上にあってよい（`go build` はソースツリーへ書き込まない）。
2. **`/cache` はイメージビルド時に作成し、実行ユーザーへ chown しておく。** named volume はマウント先がイメージ内に存在しない場合 `root:root` 0755 で作られるため、非 root 実行では書き込めず `permission denied` になる。Dockerfile に `RUN mkdir -p /cache && chown 65534:65534 /cache` を含める。

その他の設計意図:

- `/tmp` と `/work` は **tmpfs**（コンテナ終了時に消え、ホストに残らない）。
- キャッシュのみ永続ボリューム（3.8 の `GOCACHE` / `GOMODCACHE` 永続化）。**ここだけがリクエストをまたいで残る領域**なので、汚染の影響範囲として意識すること。（**本番では成立しない。** 永続ボリュームが無く、またぐ領域は `/tmp` 全体になる。下の「受け入れた劣化」）
- `--user` は数値 UID/GID で指定する（`nobody` は名前解決がイメージ依存）。`GOCACHE` を `/root/.cache` に置く一般的な例は非 root 実行と両立しないため、`/cache` へ移している。
- **上記は形であって検証済みのコマンドではない。** 着手時に実際にビルドを通し、`size` の値と tmpfs のマウントオプションを実測で確定すること。

- **1リクエスト1コンテナ使い捨て。**（**本番では保証されない。** Lambda は実行環境を再利用する。下の「受け入れた劣化」）
- **`--network=none` にするため、Ebitengine は vendor 済みでイメージに焼き込む**（3.8）。（**本番には `--network=none` に相当する遮断が無い**が、**`GOFLAGS=-mod=vendor` による依存の固定は本番でもそのまま効く**。下の「受け入れた劣化」1 点目）
- **import パッケージのホワイトリストを AST で検査する**（5.2 の手順5）。プロンプトインジェクションで `os/exec` が混入する前提で設計する。**この層は実行環境に依存しないため、Lambda でもそのまま効く。**
- ビルドタイムアウト最大10秒。（**`--cpus=1` では 11.3 秒で収まらない。** 本番は 2 vCPU 相当で 5.3 秒。3.8）

#### 本番は AWS Lambda（コンテナイメージ）で満たす（確定24 / #76）

本番のビルド実行環境は Lambda である（3.8）。**上の各フラグが本番で何に対応するか**を先に置く。

| 7.1 の要件 | Docker（ローカル） | Lambda（本番） |
|---|---|---|
| egress の遮断 | `--network=none` | **対応物なし**（#76。**非 VPC の Lambda はフルのインターネットへ出られる。** 下の「受け入れた劣化」1 点目） |
| 読み取り専用 FS | `--read-only` | `/tmp` 以外は読み取り専用（プラットフォーム既定） |
| 書き込み領域 | tmpfs `/tmp` 512m ＋ tmpfs `/work` 256m ＋ volume `/cache` | **`/tmp` のみ**（エフェメラルストレージ 1〜2 GB）。`GOCACHE` / `GOTMPDIR` / 作業ディレクトリ / 出力先をすべて `/tmp` 配下へ寄せる |
| 非 root 実行 | `--user 65534:65534` | 既定で非 root。ただし **`65534` 固定にはできない**（下の「受け入れた劣化」） |
| CPU | `--cpus=1` → **2 相当へ改める** | **メモリ 3,538 MB**（Lambda の vCPU はメモリに比例。3.8） |

##### 受け入れた劣化

**#76 の制約は「封じ込めの水準を下げる決定にはしない」だったが、この決定は次の 5 点で下げている。**
4.3 の同名の節と同じ形で、**下がったことを認めたうえで**受け入れる理由を残す。

> **#76 注記（v1.11 で改訂）。** **v1.9 ではここが 4 点だった。1 点目（egress の遮断が無い）は
> v1.11 で増えた。** v1.9 は egress を「NAT ゲートウェイの無い VPC サブネット」で塞ぐつもりで
> いたため、**遮断の欠落は劣化の一覧に載っていなかった。** その前提が成り立たないことが
> 分かったので、**遮断を持たないことを劣化として記録する。** 他の 4 点は v1.9 のままである。

- **egress の遮断が無い。** **`--network=none` に相当する遮断は本番に存在しない。**
  **非 VPC の Lambda はフルのインターネットへ出られ、AWS にこれを無効化する手段が無い**
  （関数の設定・API のパラメータ・リソースポリシー・SCP のいずれにも見当たらない。#76 の調査）。
  - **VPC を採っても解決しなかった。これが v1.9 の構成を撤回した理由である。**
    NAT ゲートウェイの無い VPC サブネットに置いても **DNS は開いたままになる。**
    VPC の Route 53 Resolver（`169.254.169.253`）は**再帰解決を行い**、AWS は
    **セキュリティグループでも NACL でも遮断できない**と明文で書いている。
    **AWS 自身がこれを DNS tunneling による持ち出し経路として解説しており**
    （帯域は link-local 合計 1024 pps）、塞ぐには **Route 53 Resolver DNS Firewall が追加で要る。**
    `docker run --network=none` にこの穴は無い（インターフェイスも経路表も持たず、
    `scripts/check-isolated-build.sh` が `/proc/net/route` の 0 件を実測している）。
  - **そのうえ VPC は封じ込めを 3 か所で悪化させる。** ①上の **DNS の持ち出しチャネルが既定で
    開く。** ②**実行ロールに EC2 の権限**（`ec2:CreateNetworkInterface` 等）が要り、AWS は
    **「その権限は関数のコードにも暗黙に付与される」**と明文で書いている
    （**攻撃者由来のコードをコンパイルする関数がその権限を持つ**ことになる。AWS 自身が
    明示的な Deny ポリシーの追加を推奨している）。③**14 日アイドルで ENI が回収され、
    最初の呼び出しが必ず失敗する**（`Inactive` になる。AWS 明文）。**招待制クローズドβで
    生成が途切れれば現実に踏む。**
  - **部分的な遮断（DNS は開いたまま）のためにこの 3 点を買うのは釣り合わない**と判断した。
  - **受け入れる理由は「たぶん安全」ではない。`go build` が攻撃者のコードを実行しないことの
    実測である**（Go 1.26.5。ビルドイメージと同一版。#76）。
    - **PATH 汚染試験**: `gcc` `cc` `clang` `ld` `git` `make` `python3` `bash` `sh` など
      **偽バイナリ 16 個を PATH の先頭**に置いてビルドしたところ、**外部プロセスの起動は 0 件**
      だった（ビルドは成功。2,052,563 bytes）。
    - **`GOOS=js GOARCH=wasm` では cgo が構造的に動かない**（`cgo: unknown ptrSize for
      $GOARCH "wasm"`）。`import "C"` は `CGO_ENABLED=0` の下で
      `build constraints exclude all Go files` になり**ファイルごと無視され**、
      `//go:cgo_ldflag` は `only allowed in cgo-generated code` で拒否される。
    - **`//line` による詐称（CVE-2023-39323 の形）も現行版で拒否される。**
    - **`//go:generate` は `go build` では走らない**（AWS ではなく **Go の明文**）。
    - **過去のビルド時 RCE の CVE は、判明した全件が cgo 依存**である
      （`#cgo LDFLAGS` / `//go:cgo_ldflag` / `//line` 詐称 / SWIG）。**この構成では cgo が動かない。**
  - **残る露出は「ビルド中に go ツールチェイン自身が出る通信」である。** vendor 固定
    （`GOFLAGS=-mod=vendor`）とイメージへの焼き込みで依存取得は起こらないが、**それは
    遮断ではなく設定である**ことをここに記録する。

- **tmpfs の分離が消える。** 3 領域（`/tmp` 512m / `/work` 256m / volume `/cache`）が **`/tmp` 1 つへ潰れる。**
  7.1 が意図した「**キャッシュだけがリクエストをまたぐ領域**」という汚染の境界がここで消え、
  **`/tmp` 全体がまたぐ領域になる。** 受け入れる理由は、Lambda に書き込み可能な領域が
  `/tmp` しか無く、分離する手段が存在しないためである。**代わりに掃除の範囲を `/tmp` 全体へ広げる**
  （境界を守るのではなく、またぐ領域そのものを毎回消す）。
- **「1 リクエスト 1 コンテナ使い捨て」が保証から運用へ格下げになる。** Lambda は暖まった実行環境を
  次の呼び出しへ再利用するため、`docker run --rm` が機構として与えていた性質を、
  **ハンドラ先頭で `/tmp` を掃除する実装**で代替することになる。**掃除の実装バグが、そのまま
  封じ込めの穴になる。** 受け入れる理由は、生成コードは**ビルド時には実行されない**ため
  直ちに穴ではないことと、掃除がテスト可能な単位であること。**呼び出しごとに一意の
  ディレクトリを掘り、ハンドラ先頭で掃除する**ことを実装の要件とする（M2-5）。
- **`--pids-limit=64` と `--security-opt no-new-privileges` に対応物が無い。** **#76 の照合表にも
  載っていない未検討項目**であり、「同等の別機構がある」とは言えない。受け入れる理由は、
  この 2 つが守っていたのは**ビルド中に実行されるプロセスの暴走**であり、
  `CGO_ENABLED=0` ＋ vendor 固定 ＋ import ホワイトリスト（5.2-5）で
  **そもそもビルド中に外部プロセスを起こさせない**という上流の層が残っているためである。
  **上流が破れたときの二重の受けが 1 枚薄くなる**ことを、そのまま劣化として記録する。
  **※ この「上流の層」は、まだコード上で結線されていない**（下の「#76 の調査で判明した
  別の穴 2 件」の 1 件目）。**受け入れの理由が現時点では仕様の上にしか無い**ことも記録する。
- **実行 uid が固定できない。** 非 root ではあるが `65534` 固定ではない。**7.1 が数値指定を
  選んだ理由は `nobody` の名前解決がイメージ依存だったこと**で、本番ではその選択自体が
  できなくなる。受け入れる理由は、非 root であること自体は保たれ、`/tmp` 以外が
  読み取り専用である以上、uid の値に依存した設計を持たないためである。**実値は未実測。**

**この 5 点は、封じ込めを「自分の `docker run` フラグ」で持つことと引き換えに、
宣言的管理（Terraform）を取った結果である**（確定24）。

> **#76 注記（v1.11 で改訂）。** v1.9 はここを「宣言的管理（Terraform）**と egress の本物の
> 遮断**を取った結果である」と書いていた。**旧記述はこの注記に残す。後半は事実ではなかった。**
> **取れたのは宣言的管理だけである**（上の 1 点目）。

| 項目 | 状態 |

| Lambda 上での実ビルド時間 | **実測なし。** 5.3 秒は手元の `--cpus=2` の値 |
| 1.51 GB イメージのコールドスタート | **実測なし。** 素の上乗せになる。キャッシュが効かないことは実測済みなので、暖機してもビルド本体は速くならない |
| **brotli q11 の圧縮時間** | **実測なし。** 5.3 秒に足して 3.8 の 10 秒に収まるかは**未検証**（#76 でも触れていない） |

| 実行 uid の実値 | **実測なし** |

##### `scripts/check-isolated-build.sh` は本番構成の検証ではなくなる

**この検査はローカル Docker の封じ込め（`--network=none` / `--read-only` / tmpfs / `--user 65534`）を
本番と同じイメージ・同じフラグで回すものだった。** 本番が Lambda になった以上、
**同じ形を回してはいるが、それは本番構成ではない。**
**本番に egress の遮断は無い**（#76。上の「受け入れた劣化」1 点目）ため、
**`--network=none` はローカルにしか存在しない層**になった。**ずれの向きは「ローカルのほうが
本番より強い」**であり、9.1 の表の 6 行目にその形で残した。
検査そのものは、イメージが壊れていないことと上流の層（vendor 固定・ホワイトリスト）の
回帰検知として**引き続き価値があるため残す。**

> **#76 注記（v1.11 で改訂）。** v1.9 はここを「**本番の egress 遮断は「VPC に NAT が無いこと」で
> 成立し、ローカルでは再現できない**」と書いていた。**旧記述はこの注記に残す。**
> 本番に遮断が無くなったので、**再現できないのではなく、本番側に対応物が無い。**

##### #76 の調査で判明した別の穴 2 件（VPC の要否とは独立）

**次の 2 件は VPC を使うかどうかと関係が無く、事実として記録するだけにとどめる。**
**対処は別 issue が持つ**（ここで直さない）。

1. **上流の層はまだ結線されていない。** 上の「受け入れた劣化」4 点目（v1.9 では 3 点目）は、`--pids-limit` と
   `no-new-privileges` の欠落を受け入れる理由として「**`CGO_ENABLED=0` ＋ vendor 固定 ＋
   import ホワイトリスト（5.2-5）という上流の層が残っている**」を挙げている。だが
   **`inspectGoImports`（`src/go-imports.ts`）は `src/generate.ts` から呼ばれていない。**
   パイプラインの `inspectSource` は宣言された継ぎ目のままで、`PipelineStepNotImplemented` を
   投げる。**現時点の露出は無い**（生成パイプラインは手前の `checkQuota`（3.3-2）で先に止まり、
   ビルドの段まで到達しない）。**しかし 7.1 の記述は「いま守られている」と読める。**
   **読めてしまうこと自体をここに記録する。**
2. **`//go:wasmimport` は import ホワイトリストを迂回する（実測）。**
   **import 文が 0 個のままホストの関数を呼べる**ため、**import を見る検査器は原理的に
   検出できない。** 実測では生成した wasm に `syscall/js.valueCall` が実際に現れ、
   **プロジェクト自身の検査器は `{"ok":true,"imports":[]}` を返した。**
   **この経路を実際に押さえているのは 7.1 ではなく 7.2 である**
   （CSP の `sandbox` ＋ `connect-src 'none'` ＋ 別オリジンの iframe）。

### 7.2 ブラウザ実行のサンドボックス

- **ユーザー生成コンテンツは必ず親と別オリジンから配信する。** 配信元は `sandbox.game-forge.ojos.jp`（確定16）。同一オリジンに置くと `sandbox` 属性の意味が大きく削がれる。
- `iframe sandbox="allow-scripts"`。**`allow-same-origin` は絶対に付けない。`allow-popups` も付けない。**

#### 同一サイトであることの帰結（確定16に伴う必須仕様）

`ojos.jp` は登録可能ドメイン（eTLD+1）である。したがって `sandbox.game-forge.ojos.jp` と `app.game-forge.ojos.jp` は**別オリジンだが同一サイト**になる。上の「別オリジン」要件は満たすが、同一サイトであることの影響は残る。

> **v1.4 注記。** アプリ用ホストは `game-forge.ojos.jp` から `app.game-forge.ojos.jp` へ変わり、
> 2 つは親子ではなく**兄弟**になった（1.2.11 / #89）。**この節の結論は変わらない。**
> 登録可能ドメインはどちらも `ojos.jp` のままで、兄弟であっても `Domain=game-forge.ojos.jp`
> の cookie は相手へ届く。以下の表と 3 つの必須要件は、そのまま本番の構成に当てはまる。

| 経路 | 危険性 |
|---|---|
| iframe 内（`sandbox="allow-scripts"`、`allow-same-origin` なし） | **安全。** 不透明オリジンになり cookie に触れない |
| **サンドボックス URL への直接アクセス** | **危険。** 実オリジンで動く（下表） |

直接アクセスされたときに何ができるかを分解する。**セッション cookie は `HttpOnly` なので「盗み読まれる」わけではない。**危険なのは書き込みと、同一サイトであるがゆえの資格情報付きリクエストである。

| 攻撃 | 成立するか | 理由 |
|---|---|---|
| セッション cookie の読み取り | **しない** | `HttpOnly` のため `document.cookie` から参照できない |
| `Domain=ojos.jp` の cookie を書く | **する** | cookie tossing / セッション固定。`__Host-` 接頭辞の cookie は上書きできないが、接頭辞なしの cookie は上書きされる |
| `HttpOnly` でない cookie の読み取り | **する** | 同スコープに置けば読めてしまう。**`Domain=ojos.jp` の cookie をどこにも置かない**理由 |
| 資格情報付きリクエストの送信 | **する** | 同一サイトのため **`SameSite=Lax` が効かない。** レスポンスは CORS で読めなくても、状態を変える要求は届く |

**次の 3 つを必須要件とする。1 つでも欠けると直接アクセスの穴が開く。**

1. **配信レスポンスに `Content-Security-Policy: sandbox allow-scripts` をヘッダとして付ける。** iframe 属性と違い、ドキュメント自身が不透明オリジンになるため、**直接アクセスでも上表の 3 つがすべて塞がる**（cookie を持たず、リクエストは `Origin: null` の cross-site 扱いになる）。
2. **セッション cookie は `__Host-` 接頭辞にする。** サブドメインからの上書きを防ぐ（8.1）。1 が破れたときの二段目。
3. **`Domain=ojos.jp` の cookie をどこにも置かない。** 読み取りの経路を最初から作らない。

**塞げないのはレピュテーションである。** 悪意ある UGC が `*.ojos.jp` で配信されると、Safe Browsing やスパムフィルタの評価は `ojos.jp` 単位で下がりうる。5.5 の改造通知メール（Resend）の送信ドメインが ojos.jp 系である以上、**到達性に影響しうる**。GitHub が `githubusercontent.com` を別の登録可能ドメインにしているのはこの問題を避けるためであり、**将来 UGC を別の登録可能ドメインへ移す判断は残しておく**（移行時は公開済み URL がすべて変わるため、招待制を外す前に決める）。
- CSP は **`connect-src 'none'`** まで絞る。6.1 により生成物に外部通信は一切不要であり、これでマイニング・DDoS 踏み台・情報送出をまとめて塞げる。
- COEP / CORP、`credentialless` iframe も検討する。

### 7.3 費用 DoS の防御

生成の敷居値は**招待コード必須**（8.1）であり、これが一次の防波堤である。加えて 4.3 の月次上限が機構的な最終防御となる。BAN は `google_sub` 単位で行うが、Google アカウントは作り直せるため、**BAN 時は招待した側の招待枠も止める**運用を検討する。

## 8. 認証・招待・モデレーション

### 8.1 認証と招待

- **ログイン手段は Google OAuth のみ。** X API の料金・ポリシー変更リスクを認証基盤という土台に持ち込まない。作者の X ハンドルは任意入力のプロフィール項目として保持する（5.6）。
- **生成は招待コード保有者のみ。** 匿名でのお試し生成は提供しない。
- **登録フローは「招待コードの検証を先、Google OAuth を後」。** 逆にすると無効なコードの利用者にログインだけさせて弾くことになる。
- セッションは Workers 側で署名付き Cookie（**`__Host-` 接頭辞** / `HttpOnly` / `Secure` / `SameSite=Lax`）。`__Host-` は 7.2 の必須要件である（サンドボックスと同一サイトのため、接頭辞なしではサブドメインから上書きされうる）。
- **招待は既存参加者への招待枠付与**を基本とする。誰が誰を呼んだかが `users.invited_by` に記録され、コミュニティの初期構造がそのまま資産になる。
- 未招待ユーザーが「改造する」を押した場合は、**待機リスト登録**へ導線を変換する。
- **招待枠は 1 人 3 本。**（2026-08-26 決定 / #91）発行できる総数の上限であり、使い終わった枠は戻らない（戻ると、コードを配り直すだけで無制限に呼べる）。発行はログイン済み利用者が自分で行う（`POST /api/invites`）。本数を 3 とする根拠は、下記 Testing 運用の**上限 100 人が全体の天井として先に効く**ことと、招待が 7.3 の費用 DoS に対する一次の防波堤であること。**環境変数にしない。** 環境ごとに違ってよい値ではないため、コード側の定数（`src/invite-issuance.ts` の `INVITE_QUOTA`）として持ち、この記述との一致を `test/invite-issuance.test.ts` が機械照合する。

#### Google OAuth を Testing のまま運用する（2026-08-25 決定 / #89）

**クローズドβの間、Google の OAuth 同意画面は公開ステータス `Testing` のまま運用する。**
`In production` へ切り替えると、非機密スコープのみでも承認済みドメインの要求が変わり、
ローカル開発で使っている `localtest.me` の登録を維持できなくなる可能性がある
（docs/gcp-oauth-setup.md 5 章）。母数が数十人のクローズドβでは、切り替えの利得より
開発経路を失う損失のほうが大きい。

**その代償として、招待が二重になる。** これは 8.1 が想定している形ではないため、
運用上の制約として明記する。

| | アプリ側 | Google 側 |
|---|---|---|
| 何をするか | 招待コードを発行して渡す | Console のテストユーザーへメールアドレスを手登録する |
| 記録先 | `invites` / `users.invited_by`（5.1） | Google Cloud Console のみ（API から列挙できない） |
| 欠けたときに起きること | 登録画面でコードが弾かれる | **Google のログイン画面にすら到達できない** |

- **上限は 100 人。** テストユーザーの登録数がそのまま招待可能な人数の上限になる。
  2.1 が見込む「数十人規模」には収まるが、**招待枠の設計（確定2 / 8.1）とは別の上限が
  もう 1 つある**ことを、招待を配る側が知っている必要がある。
- **`users.invited_by` に記録されるのはアプリ側の招待だけである。** Google 側の登録は
  この系統に現れない。招待の系統をコミュニティの資産とする 8.1 の意図に対して、
  Testing の間は「登録できる人の集合」が仕様の外に 1 つ存在することになる。
- **リフレッシュトークンが 7 日で失効する Testing の制約は影響しない。** セッションは
  Google のリフレッシュトークンではなく自前の署名付き cookie で保持する
  （docs/gcp-oauth-setup.md 4 章）。
- **解消の条件。** 招待制を外すか、承認済みドメインの要求を満たしたうえで
  `In production` へ切り替えたときに、この二重化は消える。切り替えの判断は
  ローカル開発のリダイレクト URI をどうするかとセットで行う。

### 8.2 入力側のモデレーション

危険度の高いプロンプトを、Gemini Safety Settings または OpenAI Moderation API（無料）で事前遮断する。使用する API はコード生成モデルと独立に選べる。

### 8.3 出力側のモデレーション

**生成コード内の文字列リテラルを抽出して NG ワード検査を行う。** `text` 描画で差別語を画面に出すことは容易であり、入力検査だけでは防げない。安価に効く。文字描画は 6.1 が明示的に許しているため（確定23 / #72）、この検査は空振りにならない。

**捕まえるのは「文字列リテラルとしてソースに現れる語」だけである。** 6.1 は文字描画と並んで**コード内の算術ピクセル描画**も許しており、座標計算だけで任意のグリフを描ける。その経路には検査すべき文字列リテラルが 1 つも残らない。`strconv` やコードポイントの配列から実行時に組み立てた文字列も同様に素通りする。**この取りこぼしは仕様上避けられない。** 文字描画を禁じたとしても算術ピクセル描画が残る以上、禁止で塞がる穴でもない（#72 の決着の根拠 3）。したがって 8.3 は「安い検査で大半を捕まえる層」と位置づけ、**残りを捕まえる責任は 8.4 の通報と審査キューが負う。** 8.3 が通ったことをもって「差別的な表示が無い」とは主張しない。

### 8.4 通報と削除

- ワンタップ通報機能を提供する。
- **閾値到達時は「自動非表示」ではなく「審査キューへ投入」とする。** 自動非表示は組織的通報（通報爆撃）で正常なコンテンツを消せてしまう。代替として、新規露出のみ停止し既存 URL は生かす運用も可。
- フッターに権利者向け削除申請フォームを常設し、利用規約で即時削除権限を明示する。
- **送信防止措置の手順と記録を残す**（情報流通プラットフォーム対処法への対応）。削除申請フォームの設置だけでは足りない。
- 招待制であるため、クローズドβ期のモデレーション負荷は構造的に低く抑えられる。

#### 分離をアカウント分割で行う（v1.1 で変更）

**決め手は Bedrock のクォータの粒度である。** クォータは **アカウント × リージョン ×
モデル**で定義され、**IAM プリンシパルの次元を持たない**（実測）。

- したがって **1 アカウント内では、開発と本番に別々のレート上限を張れない。**
- 4.3 の最外周の候補のうち **即時に効くのはクォータだけ**である（Budgets Actions は
  コストデータの反映に数時間かかる）。**その唯一の速い層がアカウントでしか割れない。**
- 同居させると開発の暴走がそのまま本番のレート枠を食う。**4.3 が避けている事態そのもの。**

Bedrock 側でできるのは**帰属**（アプリケーション推論プロファイル＋コスト配分タグ）と
**遅い停止**（タグやプリンシパルへ絞った Budgets Actions）までで、4.3 が求める
「機構的に停止する」を速い層で満たせない。

**Dev アカウントに IAM ユーザーは置かない。** 開発では SSO の一時資格情報を使う。
長命キーが要るのは Workers が動く本番だけである（4.1）。

> **この節は履歴である。** v1.1 で上記のとおり分割へ戻したため、**現在の方針ではない。**
> ここに残すのは、v0.9 時点で何をどういう理由で決めたかの記録としてである。

**v0.8 までは Dev / Prod の 2 アカウントとしていた。** その Dev アカウントに置くものは
「Claude Platform on AWS の組織だけ」であり、**確定19 を直販へ差し替えた時点で、置くものが無くなった。**

- 9.1（確定20）のとおり、**開発環境はクラウドを使わずローカルで完結する。** 今後 Dev に AWS リソースを置く見込みも無い。

  「開発と本番の枠を分けるだけならアカウントを分ける必要はない」と認めており、**AWS アカウントはその手段ではない。**
- 分離すべき対象が無いアカウントには、blast radius・IAM・請求行の分離という根拠が働かない。
  **空のアカウントを 1 つ維持するだけになる。**

**確定21 の根拠（通常のマルチアカウント衛生）を否定したのではない。** その根拠が適用される対象が、
Dev アカウントから無くなったということである。

> **v1.1 で対象が戻った。** 確定19 を Bedrock へ差し替えた結果、Dev アカウントに
> 「置くもの」（Bedrock の開発用の枠）ができた。**根拠は否定されていなかったので、
> 対象が戻れば結論も戻る。**

> **v0.5 での誤り（v0.6 で訂正）。** v0.5 は「Claude Platform on AWS は Workspace 単位の spend limit を設定できず組織単位のみ。組織は AWS アカウントに 1:1 で紐づくので、分離するにはアカウントを分けるしかない」を分割の根拠としていた。**これは誤りである。**設定できないのは Workspace 単位の *rate limit* であり、*spend limit* は Workspace 単位で設定できる（4.3）。rate limit の制約を spend limit へ広げて読んでいた。**分割の判断自体は上記の理由で維持するが、根拠は差し替える。**
>

#### Anthropic の組織は AWS アカウントと無関係になった

> 確定19 を Bedrock へ差し替えたため、Anthropic の組織そのものが不要になった。

### 9.3 デプロイパイプライン (CI/CD)

- **アプリ (Cloudflare Pages Functions):** `main` への push を契機に、**GitHub Actions から `wrangler pages deploy` を実行して配備する**（#95。実体は `.github/workflows/verify.yml` の `deploy` ジョブ）。
  - **`verify` が緑のときにしか走らない。** 同じ実行の中で `needs: verify` の後段に置いており、**ゲートの外側に配備経路を作らない**（条件式ではなく依存関係で保証する）。
  - **`--commit-hash` / `--commit-message` を必ず渡す。** どのコミットが本番に居るかを Cloudflare 側から辿れるようにするためである。#95 の調査ではこの情報が決め手になった。
  - **`main` へのマージは、そのまま本番への反映を意味する。** 配備は外部状態の変更であり、自動化した以上、マージという操作の意味がここで変わっている。**本番へ出せないものを `main` へ入れない。**
  - **配備の成否とは別に、一致を検査する。** `scripts/acceptance-remote.sh` が「本番がいま配っている配備のコミット」と `main` の HEAD を突き合わせる。自動化で消えるのは「配備し忘れ」だけで、**「配備が失敗したまま気づかない」は残る**ため、**「配備されたか」ではなく「一致しているか」**を見る。
  - **手動配備（`docs/pages-deploy.md`）は初回と緊急時の手段として残す。** 日常の配備経路ではない。

  > **v1.6 までの記述（#95 で訂正）。** v1.6 までの 9.3 は「**フロントエンド (Next.js/React):** Cloudflare Pages と GitHub リポジトリを連携。`main` への Push で自動デプロイ」と書いていた。**その連携は存在しなかった。** 2026-08-26、#92〜#94 をマージした直後に本番の `/invites` が 404 を返して発覚した。Pages プロジェクトの Git 連携は `No` で、`wrangler pages deploy` を呼ぶワークフローも無く、**本番は 4 コミット古い `5ea727a` を配り続けていた**（#89 が手で配備したきりだった）。**最も悪いのは、すべてのゲートが緑のまま本番だけが古いことに気づく仕組みが無かったことである。** 記述は上のとおり実態へ改め、旧記述はこの注記に残す。なお **「Next.js/React」も実態ではない**（画面はすべて Worker が生成する。確定22）。

- **ビルド実行環境 (AWS Lambda):** GitHub Actions (`deploy-compiler.yml`) から **ECR へイメージを push し、関数のイメージを更新する**（`aws lambda update-function-code --image-uri`）。**SSH は使わない。** 関数と ECR リポジトリそのものは `terraform/` で宣言する（**VPC は作らない。** #76 / 7.1。v1.9 はここに「関数・VPC・ECR リポジトリ」と書いていた）。
  - **これが確定24 の決め手そのものである。** さくらのVPS は**手で立てて手で patch するペットサーバ**になり、shared-ai-rules 4 章「恒久的な状態変更は宣言側を通す」と相性が悪い。**確定17 が DNS で同じ理由から Route53 委譲を選んだ前例に倣う**（下の DNS の項）。
  - **配備の対象はイメージのダイジェストである。** どのイメージが本番の関数に載っているかを ECR のダイジェストで辿れるようにする（Pages 側で `--commit-hash` を必ず渡すのと同じ理由）。

  > **#76 注記（確定24）。** v1.8 までは「**ビルドサーバー:** GitHub Actions (`deploy-compiler.yml`)
  > 経由で SSH 接続し、Docker イメージをさくらのVPS へ自動更新・コンテナ再起動」だった。
  > **旧記述はこの注記に残す。** **9.1 が「VPS 固有なのは SSH デプロイだけ」と書いていた
  > その 1 点が、ここで消えている。**
- **DNS:** `game-forge.ojos.jp` をさくらのドメインから **AWS Route53 へ NS 委譲**し、以降は `hashicorp/aws` プロバイダで Terraform 管理する（確定17）。さくら側の作業は NS レコードを 1 組置く初回のみ。
  - **さくらのドメインは DNS の API を持たない**ため、委譲しない限り恒久的な状態変更が手動になり、shared-ai-rules 4 章「UI やアドホックな CLI での直接作成・変更を、恒久的な状態変更の手段にしない」に反する。委譲はこの規範を満たすための手段である。
  - Cloudflare へのサブドメイン委譲（subdomain setup）は **Enterprise プラン限定**のため使えない。
  - **Cloudflare Pages のカスタムドメインは、サブドメインであれば外部 DNS のままで CNAME 1 本でよい。** ただし **Workers のカスタムドメインはゾーンが Cloudflare 上にあることを要求する**ため、API を `game-forge.ojos.jp/api/*` に置くなら Pages Functions を使う。
  - **「サブドメインであれば」が効く（v1.4 / #89）。** 委譲したゾーンの名前が `game-forge.ojos.jp` である以上、その名前自体は**ゾーンの apex** であり、Route53 は apex に CNAME を作れない。Cloudflare Pages 側も外部 DNS のままの apex を対象外としている。したがって**アプリ用ホストには `app.` を足す**（1.2.11 / 確定16）。

#### 確定22: 配置先は Cloudflare Pages Functions とする（M2-1 で確定）

**アプリと API はどちらも Pages Functions に置く。** 上の制約は `/api/*` だけの問題ではない。ゾーンは確定17 に従って Route53 へ委譲済みで Cloudflare 上に無いため、**Workers のままでは `game-forge.ojos.jp` にカスタムドメインを張れない**。M1 で作った登録画面・OAuth・待機リストも同じ制約を受ける。

- ゾーンを Cloudflare へ戻す案は採らない。確定17 の NS 委譲と 9.2 の AWS アカウント設計を巻き戻すことになり、DNS を Terraform で宣言的に管理する目的（さくらに DNS の API が無いことへの対処）を捨てることになる。
- **Pages Functions は Workers と同じランタイムである。** 経路の実装（`src/` 配下）はそのまま使える。付け替えが要るのはエントリと配備の構成であり、アプリのロジックではない。M0.5-3 で `wrangler.toml` を最小構成に留めておいた判断がここで効いている。
- API のパスは `/api/*` を正とする。M1 で置いた `/waitlist` はこの確定より前の綴りであり、移行の対象とする。
- **Go バージョン更新時の手順を 3.5 と連動させる**（`wasm_exec.js` の出し分け）。
- 本リポジトリの既存機構（`scripts/verify.sh`、`scripts/check-no-secrets.sh`、Copilot code review ワークフロー）に従う。

## 10. KPI と撤退条件

### 10.1 主 KPI

**フォーク率 = フォーク生成数 ÷ 全生成数**

母数が固定（招待制）であるため DAU は意味を持たない。差別化仮説を直撃し、小さい母数でも測定できる指標としてフォーク率を主 KPI とする。

### 10.2 補助指標

- 3世代以上の系統の本数
- 招待者あたりの生成数
- 「改造する」を押した未招待ユーザー数と、そこからの待機リスト登録率（**匿名お試しを廃止したことで失った「踏んで即改造」の転換率の代理指標**）
- 1生成あたりの実コスト（`effort` の A/B 判定用）
- 初回コンパイル成功率

### 10.3 撤退条件

**開始から3ヶ月時点で、次のいずれかに該当する場合は縮小または中止する。**

- フォーク率が 40% 未満
- 3世代以上の系統が1本も出ていない

基準が厳しすぎたと判断して後から緩めるのは構わない。**決めていない状態のみが危険**であり、個人開発でランニングコストが出ている以上、先に線を引くこと自体が目的である。
