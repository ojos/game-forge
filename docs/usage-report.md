# 運用のための集計

**運用者が「いま何が起きているか」を非対話で読むための集計を、ここにまとめます。**

利用者の画面には出しません（2026-08-29 決定。費用も所要時間も、**利用者にできることが
無い**ためです）。ここにあるのは運用者が回すスクリプトだけです。

| 見たいもの | スクリプト | 読む先 |
|---|---|---|
| 日毎の生成回数・成功率・費用（#149） | `scripts/usage-report.sh` | D1 の `generations` |
| ビルド時間が天井へ近づいていないか（#166） | `scripts/build-time-report.sh` | CloudWatch の `REPORT` 行 |
| 10 章の KPI（#42） | `scripts/kpi-report.sh` | D1 の `games` / `generations` / `waitlist` / `game_revisions` |
| 審査待ちの作品（#40） | `scripts/report-queue.sh` | D1 の `games` / `reports` |
| 未対応の削除申請（#41） | `scripts/takedown-queue.sh` | D1 の `takedown_requests`（手順は [takedown.md](takedown.md)） |
| 遮断の記録の掃除（#37） | `scripts/moderation-prune.sh` | D1 の `moderation_blocks` |
| 数え方の定義（両方が共有する） | `scripts/report-window.sh` | — |
| 自己検査 | `scripts/report-selftest.sh` | 使い捨ての手元 D1 と宣言 |

## なぜ要るのか

**台帳はありましたが、読む手段がありませんでした。** `generations` は 1 呼び出しにつき
1 行を持ちます（4.3 の記録規約 / #22）。しかし読むには毎回 SQL を手で書いて
`wrangler d1 execute` へ渡すしかなく、**推移としては誰も見ていませんでした。**

その結果どうなったかは実例があります。~~**1 生成あたりの費用は見込み 12 円に対して実測
約 16 円でしたが、本番で 1 回通すまで分かりませんでした**（1.2.38）。4.3 の月次上限は
1 万円です。~~ **上限へ張り付いてから気づくのでは遅すぎます。**

**→ 同じずれがもう一段進みました（#296）。** 打ち消したのは 2026-08-28 の値です。

| 時点 | 1 生成あたり | 母集団 |
|---|---|---|
| 見込み（4.2 の試算） | 12 円 | #7 の 6 本 |
| 2026-08-28 の本番初通過 | 約 16 円 | n=2 |
| **2026-09-04（いまの値）** | **¥22.41** | **本番の既定群 20 件の平均**（直近 10 件は ¥26.75） |

**見込みの 1.87 倍です。** 月次上限も #284 で 1 万 → 2 万円へ引き直しました。数え直すと
2 万円 ÷ ¥22.41 ＝ **892 生成/月**、30 日で割って **29.7 生成/日** となり、4.3 の逆算が
いま置いている母数と一致します。**#284 でソース上限を 64KB へ上げたので、単価はこれからも
上がります**（上限まで出したときの試算は ¥75）。**このレポートを定期的に見る理由がそれです。**

## 使い方

```bash
bash scripts/usage-report.sh                                  # 手元の D1・直近 14 日
bash scripts/usage-report.sh --remote --days 30               # 本番の D1・直近 30 日
bash scripts/usage-report.sh --by-model                       # モデル別に割る
bash scripts/usage-report.sh --from 2026-08-01 --to 2026-08-31
bash scripts/usage-report.sh --remote --days 30 --format json # 機械が読む形
```

| 引数 | 意味 |
|---|---|
| `--local`（既定） / `--remote` | 手元の D1 か、本番の D1 か。**どちらも読み取りのみ** |
| `--days N` | 今日を含む直近 N 日（既定 14。**最終日は途中まで**） |
| `--from` / `--to` | JST の暦日で範囲を指定する。**`--to` はその日を含む** |
| `--by-model` | `model` 列で割る（#25 が乗る形） |
| `--format` | `table`（既定） / `tsv` / `json` |
| `--persist-to` | 手元 D1 の置き場所を差し替える（自己検査専用） |

出力（`--format table`）:

```
[usage-report] 生成の台帳（generations）／ 本番 D1（読み取りのみ）
期間: 2026-08-24 〜 2026-08-30（JST の暦日で 7 日ぶん / 半開区間 [1787497200, 1788102000)）

日付        生成回数  LLM成功  LLM成功率  費用合計(円)  1回あたり(円)
----------  --------  -------  ---------  ------------  -------------
2026-08-29         3        3     100.0%         40.48          13.49
合計               3        3     100.0%         40.48          13.49
```

**終了コードで成否が判定できます**（0 = 表を出せた / 1 = 出せなかった）。表の末尾には
`USAGE_REPORT_PASS` が出ます。**0 行でも成功です。** 「その期間に生成が無かった」は
正常な答えであり、「集計できなかった」とは別だからです。

## 数え方の定義は 1 か所です

**期間の切り方・日の境界・日付の綴りは `scripts/report-window.sh` だけが持ちます。**

複数の集計が別々の定義を持つと、**同じ「2026-08-29 の」という語が別の 24 時間を指す**
ようになり、2 つの表を並べても比較が成立しません。定義を共有していることは呼びかけでは
なく、`scripts/report-selftest.sh` が機械で検査します（消費側が
`report-window.sh` を読んでいること、自前の JST オフセットを持っていないこと）。

- **日の境界は JST の 0 時です**（確定25 / `src/quota.ts` の `jstDayRange`）。UTC で切ると
  日次枠の判定（1 人 1 日 12 回）と食い違い、「枠を使い切った日」と「表に出る日」が
  9 時間ずれます。
- **区間は半開区間 `[from, to)`** です（`src/cost-ledger.ts` と同じ）。境界の 1 行が
  2 つの日に数えられる経路を作りません。
- **JST のオフセットは `src/quota.ts` の `JST_OFFSET_SECONDS` と機械照合します。**
  シェルから TypeScript の定数を実行時に引く手段が無いため写しを置いていますが、
  **古くなったまま通る経路は塞いであります**（shared-ai-rules 12 章）。

定義そのものは、スクリプトを読まなくても印字できます。

```bash
bash scripts/report-window.sh
```

## `LLM成功` を「成功率」と読まないこと

**`generations.succeeded` は LLM 呼び出しの成否であって、パイプライン全体の成否では
ありません**（`src/cost-ledger.ts` の `isUsableGeneration`。`end_turn` で返ったか）。
3.3 の順序では費用計上がビルドより前にあり、**この列が立った時点でビルドはまだ走って
いません。**

**2026-08-29 に `succeeded=1` のまま作品にならなかった行が実際に出ています**（ビルドの
タイムアウト。#164）。上の実際の出力がまさにその日で、**`LLM成功率 100.0%` と出ています。**
作品ができた率ではありません。

この注記は**出力そのものに載せています**（`table` の注記欄と `json` の `notes`）。
凡例をこの文書だけに置くと、数字を貼り付けた先には意味が付いていきません。

## 読み取りのみであること

**本番 D1 へ書き込みません**（#149 の constraints）。呼びかけではなく、送る直前に
組み立てた SQL が `select` で始まることを検査しています。組み立てるのはスクリプト自身
ですが、**組み立てを間違えたときに本番へ届く経路を残さない**ためです。

`--remote` は `CLOUDFLARE_API_TOKEN` を要します。値はスクリプトへ持ち込まず、
`scripts/load-project-env.sh` で環境へ移すだけです（`scripts/wasm-exec-versions.sh` と
同じ形）。

## ビルド時間が天井へ近づいていないか（#166）

**2026-08-29 のタイムアウト（#164）は、利用者が踏んで初めて分かりました。** あとから
CloudWatch を掘ると、分布はすでに天井に迫っていました。**見ていれば予告できました。**

```bash
bash scripts/build-time-report.sh --days 14         # AWS_PROFILE が要ります
bash scripts/build-time-report.sh --explain-threshold  # 閾値の導出だけ（AWS 不要）
bash scripts/build-time-report.sh --days 14 --format json
```

実際の出力（2026-08-29 時点。**#164 が起きた分布そのものです**）。
**この頃は打ち切りを「所要 ≧ 天井」から推測しており、列の名前も「超過」でした**
（#211 で直しました。下記）:

```
日付        呼び出し  中央値(秒)  p95(秒)  最大(秒)  接近  超過  コールド
----------  --------  ----------  -------  --------  ----  ----  --------
2026-08-27        11        23.7     34.5      34.5     4     3         5
2026-08-28         2        21.6     24.4      24.4     1     0         1
2026-08-29         2        23.3     29.5      29.5     1     0         2
合計              15        23.7     34.5      34.5     6     3         8

判定: 天井へ達した呼び出しが 3 件あります（打ち切られています）。
BUILD_HEADROOM_NEAR
```

終了コード:

| コード | 信号 | 意味 |
|---|---|---|
| 0 | `BUILD_HEADROOM_PASS` | 天井に対して余裕がある |
| 1 | `BUILD_HEADROOM_NEAR` | 接近している、または**打ち切られた**呼び出しがある |
| 2 | `BUILD_HEADROOM_UNKNOWN` | 判定できない（未認証・ログが無い・**現在の構成での呼び出しが 0 件**） |

**0 件を「余裕あり」にしません。** 測っていないことと、測って余裕があることは別です
（`scripts/acceptance.sh` の `ran_any` と同じ考え方）。未認証やオフラインも同じで、
それは分布の異常ではなく前提の不成立です。

### なぜ CloudWatch を読むのか（新しい計測を足していません）

#166 は「新しい計測を足す前に、いま捨てている値を残せないか」を求めています。
**調べた結果、足さずに済みました。**

- ビルド関数の応答の `buildMs` / `compressMs` は、`src/build-client.ts` が `BuildTimings`
  へ読んだあと**どこへも残していません**（ログにも D1 にも出ません）。**捨てているのは
  事実です。**
- 残すには D1 への書き込みを増やすか、`src/` を変えるかになります。**前者は 3.6 と #166 の
  constraints が禁じています**（観測のために本番への書き込みを増やさない）。
- **CloudWatch の `REPORT` 行は、すでに全呼び出しぶん 14 日保持されています**
  （`terraform/build-function.tf` の `aws_cloudwatch_log_group.build`）。追加の計測も
  追加の書き込みも無しに読めます。
- しかも **`REPORT` の `Duration` こそがタイムアウトの掛かる量です。**
  `buildMs + compressMs` はその内訳（部分集合）でしかありません。**天井への近さを見る
  のに、天井が掛かっていない量を見る理由がありません。**

段ごとの内訳（どこで時間を食っているか）まで見たくなったときは、`buildMs` /
`compressMs` を **D1 ではなくログへ 1 行出す**のが次の一手です（書き込みは増えません）。
`src/` の変更になるため、このレーンでは行っていません。

### 天井への近さをどう判定しているか

**天井を書き写していません。宣言から導いています。**

| 値 | 出所 |
|---|---|
| 天井 | `terraform/build-function.tf` の `build_function_timeout_seconds` |
| ロググループ | 同ファイルの `build_function_name`（綴り `/aws/lambda/${name}` が宣言に在ることを確かめてから組み立て） |
| 接近とみなす線 | 天井 × 0.8（余裕が 20% 未満） |
| 接近の割合の線 | 0.10 |
| 打ち切り | `Task timed out` の実ログ（**1 件でもあれば不合格**。所要と天井の比較では数えません。#211） |
| 判定に使う構成 | 同ファイルの `build_function_memory_mb`（**このメモリで走った呼び出しだけを判定に使います**。#211） |

**#164 が第 4 波で天井を動かします（30 → 60 秒を想定）。** 動いたら接近の線も一緒に
動きます。それが本当に動くことは `scripts/report-selftest.sh` が検査します（宣言を
差し替えた写しを渡し、線が 24.0 秒から 48.0 秒へ移ることを見ます）。**宣言が読めない
ときは落とします。決め打ちの値へ倒れません。**

割合の 0.8 と 0.10 は、どちらも記録から導いています。

- **0.8（余裕 20% 未満）** … #103 がタイムアウトを 25 秒から 30 秒へ改めた理由が
  「コールドの実測 23.685 秒に対して 25 秒では余裕が 1.3 秒しか無い」ことでした。
  退けた 25 秒の余裕は**天井の 5.3%**、選んだ 30 秒の余裕は**天井の 21.1%** です。
  つまり宣言は 2 割ほどの余裕を意図して買っています。**実際の呼び出しがその余裕を
  食い始めたら、その値を選んだ理由がもう成り立っていません。**
- **0.10** … #164 のとき、15 回中 5 回（33%）が天井の 96% 以上に達していて、それでも
  誰も気づきませんでした。**33% で気づけないなら、線はそれよりずっと手前に要ります。**
  10% なら 15 回中 2 回で鳴ります。

**上の実際の出力は、この判定を #164 が起きた分布へ当てたものです。** 超過 3 件・接近
6/15 件で `BUILD_HEADROOM_NEAR` が出ています。**踏む前に読み取れていた**ということです。

### 天井やメモリを動かした直後に、過去の完走を「打ち切り」と呼ばない（#211）

**2026-08-31、メモリを 3,008 → 10,240 MB、天井を 45 → 20 秒へ動かした直後、この道具は
3,008 MB 時代の完走（23〜37 秒）を 19 件「打ち切られています」と報告しました。**
どれも当時の天井 45 秒の内側で完走しています。**嘘の赤は、ゲートへの信頼を削ります。**

原因は 2 つでした。

1. **天井は現在の宣言から読み、所要は過去のログから読んでいた。** どちらも単体では
   正しいのですが、突き合わせると「**天井を下げた直後は、過去の完走が打ち切りに化ける**」。
2. **打ち切りを「所要 ≧ 天井」から推測していた。** 実際の打ち切りは `Task timed out`
   としてログに出ます。**推測する必要がありません。**

直したあとの出力（2026-08-31。**同じ 22 件が消えずに残っています**）:

```
日付        呼び出し  中央値(秒)  p95(秒)  最大(秒)  接近  打ち切り  コールド
----------  --------  ----------  -------  --------  ----  --------  --------
2026-08-31         4        11.9     12.6      12.6     0         0         2
2026-09-01         4        11.6     12.2      12.2     0         0         3
合計               8        11.9     12.6      12.6     0         0         5

判定から外した呼び出し（現在の宣言と違うメモリで走ったもの。表からは消していません）:
メモリ(MB)  呼び出し  平均(秒)  最大(秒)  コールド
----------  --------  --------  --------  --------
      1769         2      33.9      34.5         1
      2048         2      30.1      30.4         1
      3008        18      21.8      37.8        11

判定: 天井に対して余裕があります。
BUILD_HEADROOM_PASS
```

- **`REPORT` の `Memory Size` を読み、現在の宣言と違うメモリで走った呼び出しを判定から
  外します。** Lambda はメモリに比例して vCPU を割り当てるので、メモリが違えば所要も
  違い、**同じ天井に対する余裕として並べられません。**
- **ただし表からは消しません。** 別の構成での実測として、**なぜ外したか**を添えて残します
  （消すと「データが無い」と読まれます）。
- **外した結果、現在の構成での呼び出しが 0 件になったら `BUILD_HEADROOM_UNKNOWN`**
  （終了コード 2）。**「測っていない」と「測って余裕がある」は別です。**
- **打ち切りは `Task timed out` のログを `RequestId` で `REPORT` と突き合わせて数えます。**
  突き合わないもの（`REPORT` が窓の外にある等）は件数を注記に出し、**判定には使いません**
  ——どの構成のものか確かめられていないからです。

**`Task timed out` の綴りは、本番ログのこの窓では 0 件でした**（保持は 14 日で、#164 の
打ち切りはすでに流れています）。**綴りに寄りかからない形にしてあります**——判定に使うのは
`Task timed out` を含むかどうかだけで、後続の書式は読みません。

**この 2 つは `scripts/report-selftest.sh` が検査します**（`--events-file` に
`filter-log-events` の応答の形を渡します。**AWS も認証も要りません**）。検査には
「天井を超えているが打ち切られていない完走」と「天井より短いが打ち切られた呼び出し」を
**両方**置いてあります。**片方だけだと、推測でも実ログでも件数が一致してしまい、
変異を当てても緑のまま通ります**（実際に一度そうなりました）。

### 母数が #149 と違います

**同じ日の境界で畳んでいますが、数えている対象は違います。**

- #149 の `生成回数` … `generations` の行数（費用の出る LLM 呼び出し 1 回 = 1 行）
- #166 の `呼び出し` … ビルド関数の実行回数

**ビルド結果キャッシュに当たった生成は関数を呼びません**（確定26 / `src/build-cache.ts`）。
逆に、LLM が使えないソースを返した生成はビルドまで進みません。**2 つの数が一致しない
のは正常です。** 一致させるべきなのは数え方（窓・日の境界・日付の綴り）であって、
母数ではありません。

## `effort` の A/B で使うお題（正本。#25 / M3-4）

**`effortExperimentTotals` はこの 6 本を前提に読む。** #25 の手順は「4.2 の実測と同じ
6 本」と書いているが、**その 6 本の文面は残っていなかった**（仕様書 4.2 は「同じ 6 本の
お題で測った」と書くだけで、本文が無い）。**測り直しのたびに引ける正本をここに置く。**

| # | お題 | 何を効かせたいか |
|---|---|---|
| 1 | 左右キーで自機を動かし、上から落ちてくる岩を避けるゲーム | 最小構成。両群とも成功する想定の下限 |
| 2 | 迷路を上下左右に進んでゴールを目指すゲーム | 盤面データと衝突判定 |
| 3 | 上下キーでラケットを動かし、球を打ち返す卓球ゲーム | 反射と 2 者の状態 |
| 4 | 重力と反発のある球をパドルで跳ね返し、ブロックを崩すゲーム | 物理と衝突解決 |
| 5 | 敵の弾を避けながら撃ち返す縦スクロールシューティング | 複数オブジェクトの生成と破棄 |
| 6 | 制限時間内にコインを集め、時間切れでゲームオーバーになるアクションゲーム | 時間管理と終了条件 |

### なぜこの形なのか

- **易しいものだけにしない。** 全部が初回で通ると、**`high` と `medium` の差が出る余地が
  消える**（4.2 の Sonnet は 5/6 だった）。4〜6 に機構を要求している
- **固有名詞を入れない。** 本番の実プロンプトには「スーパマリオのような」があるが、
  これは 8.3 / M6-3（#39）が扱う範囲に触れる。**正本として残すものに入れると、測り直す
  たびに同じ懸念が付く**
- **6 本は互いに別の文面である。** 台帳は作品行と結び付いていないため（確定27 / 5.1）、
  「どの行が同じ依頼のリトライか」は**同じ利用者の同じプロンプト**であることから引いて
  いる。**1 群の中で文面が重なると `ambiguousJobs` が立つ**（`src/cost-ledger.ts`）。
  **これは実在する危険である**——本番の台帳には、ほぼ同一の長文プロンプトが 2 行ある
- **同じ 6 本を両群へ使うのは正しい。** 群は `model` で分かれる（`sonnet-4-6-high` /
  `sonnet-4-6-medium`）。同じお題を両群へ通すことで、**お題の難しさの分散が両群で相殺される**

### 4.2 の #7 の表とは横並びにできない

## どこで走るか（CI に配線しました。#226）

**`scripts/report-selftest.sh` は `.github/workflows/verify.yml` の `verify` ジョブで走ります**
（`Report selftest` の段）。**ローカル層（`scripts/acceptance.sh` / `scripts/verify.sh`）へは
入れていません。**

| 層 | 走るか | 理由 |
|---|---|---|
| CI（`verify.yml`） | **走る** | 1 回払えば足りる。PR ごとに必ず通る |
| ローカル事前ゲート（`scripts/loop-gate.sh`） | 走らない | 反復のたびに 17 秒を払う価値が薄い（下記） |
| 外部層（`scripts/acceptance-remote.sh`） | 走らない | AWS も本番 D1 も要らないので、外部層の関心事ではない |

**なぜローカル層へ入れないのか。** 実測で `report-selftest.sh` は **17 秒**、
`scripts/acceptance.sh` は **20 秒**です（1,183 テスト込み）。入れると事前ゲートが
**20 → 37 秒（+85%）**になります。**この検査が守っているのは「集計の読み方」であって、
反復のたびに壊れる層ではありません**——`src/` を触っても壊れず、壊れるのは
`scripts/usage-report.sh` / `scripts/build-time-report.sh` / `scripts/report-window.sh` /
`src/quota.ts` の境界を動かしたときだけです。

**代わりに「ローカルで緑・CI で赤」が起こりえます。** それは受け入れています
（`docs/handoff.md` 4 章「**PR を出したら `gh pr checks` を見る**——CI にしかない検査は
他にもある」）。**集計まわりを触ったら、push を待たずに手で回してください。**

```bash
bash scripts/report-selftest.sh   # 17 秒
```

**手元で回すには GNU date が要ります**（`date -d @<epoch>`。`scripts/report-window.sh` が
実際の変換で確かめ、**明示して落とします**——黙って別の日付を出すことはありません）。
**利用者の端末は macOS なので、そのままでは通りません**（`docs/handoff.md` 3 章）。
coreutils の `gdate` を `date` として見せるか、**devcontainer の中で回してください。**
CI は ubuntu-latest なので、そのまま通ります。

**`verify` ジョブの段なので、これが赤いと `deploy` も起きません**（`deploy` は
`needs: verify`）。集計を読み違える状態で本番を進めない、という意味では筋が通りますが、
**影響は `scripts/verify.sh` の失敗と同じ広さになります。** 別ジョブにすればそこは切れますが、
`checkout` と `npm ci` をもう一度払うことになるため採っていません。

**`scripts/build-time-report.sh` そのものは、どの層にも配線していません。**
AWS の認証を要するため、ローカル層へ入れると認証の失効でループ全体が止まります
（プロジェクト共通ルール「外部層を単一入口へ含めない理由」）。ただし**これは「宣言と外部状態の
一致」ではなく「外部状態の傾向」**なので、外部層の性格とも少しずれます。**定期実行
（cron / GitHub Actions）のほうが素直です。** 自己検査の側は `--events-file` で
CloudWatch を置き換えるので、**CI では AWS を要しません。**
