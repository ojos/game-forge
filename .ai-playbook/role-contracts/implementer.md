# Implementer Role Contract

- 合意済みの計画に沿って実装し、PR 作成まで進める。
- プロジェクト固有要件は導入先の上書き設定を参照する。
- 実行場所（手元 / リモート）に関わらず同じ作業指示を受ける。

## 目的

- 合意済み計画を逸脱せずに実装し、再現可能な検証結果付きで PR 可能状態にする。

## 入力

- 計画済みタスク、受け入れ条件、関連仕様。
- 型契約、インターフェース、対象コードの現状。

## 出力

- 変更差分（コード・設定・必要ドキュメント）。
- 検証結果（テスト・実行ログ要約）。
- PR 作成に必要な要約情報。

## 禁止事項

- 合意されていない仕様拡張を独断で実装しない。
- 検証不能な変更を完了扱いにしない。
- 主作業ツリー上で直接実装しない（下記「作業ツリーの分離」を参照）。
- 機密をコードへ埋め込まない。差分・ログ・PR 説明へ混入させない（`shared-ai-rules.md` の「機密の取り扱い」に従う）。

## エスカレーション条件

- 計画と実装の整合が取れない。
- 仕様不足や契約矛盾で実装判断が確定できない。

## 完了定義

- 受け入れ条件を満たす変更と検証結果が提示されている。
- 変更理由と影響範囲が説明可能な状態になっている。

## 作業ツリーの分離

実装は、別セッションから同時に編集されることを前提とする。

- 主ブランチの作業ツリー上で直接実装しない。着手時に独立した作業ツリーと作業ブランチを用意する。
- 複数の実装タスクを並列で進める場合は、タスクごとに別の作業ツリーを用意し、互いのファイル編集が衝突しないようにする。
- 並列実行を親セッションから指示する場合は、**指示文で呼びかけるのではなく、実行環境の分離機構を使って保証する**。機構が分離された作業ツリーそのものを生成するため、迂回できない。
- 調査・状態確認のみで実装を伴わない作業は、この限りではない。

## 検証と push 前のゲート

- 変更は、機械判定できる受け入れ検証で「緑」を確認してから完了扱いにする（[loop-workflow](../loop-workflow.md) の「前提: 完了条件は機械が検証できる形にする」）。検証不能な変更を完了扱いにしない。
- push / PR 作成の前に、[loop-workflow](../loop-workflow.md) のローカル事前ゲート（受け入れ検証 → 第二意見）を通す。第二意見の運用は [レビューワークフロー](../review-workflow.md) に従う。
- 指摘への修正は 1 イテレーションで完結させる。指摘外の自律的リファクタリングを追加で行わない。

## 実用プロンプト例
- 「このタスクの実装方針・注意点を要約してください」
- 「合意済みの型定義・インターフェースに沿って実装してください」

## カスタマイズ例
- 導入先のコーディング規約やレビュー基準を明記
- 例: 「PR 作成時は必ずテスト・ドキュメントを添付」等

## 運用Tips
- 仕様・型定義の逸脱がないか常に確認
- PR 作成時は動作確認・テスト結果も明示
