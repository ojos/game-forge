## M8 画面デザイン

**画面は M7 まで SSR の素の HTML で、CSS ファイルが 1 枚も無い。**
**アプリ用ホストの画面にある `<style>` は 1 か所だけ**（`src/work-page.ts` の
ロード中画面のレイアウト 7 行）で、`style=` 属性は `src/` 全体で 0 個である。
**`src/sandbox-loader.ts` にも `<style>` があるが、あれは別ホストである**——
`/g/*` で配る iframe の中身であり、M8 の対象外（M8-2 の scope.out）。
M6 まではそれで通した——9.3 / #89 が「MVP の画面は SSR の素の HTML に留める」を
scope.out に置いており、**先取りすると捨てる量が増える**ためである。

**M8 でそれを解く。** 主 KPI（フォーク率）の入口は作品ページと OGP 画像であり、
**β 参加者が最初に見る 10 本（M7-2）より前**に土台が入っていないと、コールドスタートの
第一印象が素の HTML になる。

### 決めてから起票した 4 点（intake / 2026-09-03）

| 決めたこと | 決めた内容 |
|---|---|
| 範囲 | **全画面 ＋ 見た目の土台。** 拡散の着地点 3 枚に絞らない |
| CSS の配り方 | **`public/assets/app.css` に 1 枚。** 全ページが `<link>` で参照する |
| 受け入れ条件 | **機械検証 ＋ 本番での目視。** 見た目の良し悪しは acceptance に入れない |
| 見た目の方針 | **作品を主役にする。** プラットフォーム側は無彩色・装飾最小 |

**`public/` へ置く判断は、既存の記述と正面から当たる。** `docs/pages-deploy.md` は
「**`public/` に静的ファイルを置かないこと**」と書いているが、そこに書かれている根拠は
「`index.html` を置くと `/` の経路が隠れる（実測で確認）」の 1 点だけである。
**覆いが根拠より広く読めていた形で、#241 の関門と同じ**（`docs/handoff.md` 1 章）。
経路と衝突しないパスには当たらないので、**記述を「経路と衝突するパスに置かない」へ狭める**
（M8-1 の scope.in）。**狭めた以上、衝突しないことは機械で確かめる**（M8-1 の acceptance）。

**`<style>` を各ページへ差し込む案は採らない。** すべてのページ応答に
`cache-control: no-store` が付いている（`src/routes.ts` の `html()`）ため、
**CSS 本文がページを開くたび丸ごと再送される。** `no-store` は保存そのものを禁じるので、
再検証で 304 に落とすこともできない。

`public/` 側で確かなのは **Worker を経由しないこと**である（Pages が静的ファイルを
Functions より先に解決する。`functions/[[path]].ts` の冒頭が書いており、`index.html` を
置くと `/` が隠れることも実測で確かめられている）。**D1 も CPU も使わない。**

**キャッシュについては何も確かめていない。** Pages が既定でどの `cache-control` と `ETag` を
返すかを 1 度も測っておらず、**「再検証が効く」は仕様上の期待であって実測ではない。**
だから M8-1 の acceptance は「本番で 200 が返り、静的解決で返っている」までしか要求せず、
**キャッシュの挙動を完了条件にしていない。** 測ったらここへ書き足すこと。

**配備順の事故は起きない**——
`public/` と `functions/` は同じ `wrangler pages deploy` で一緒に出る（Lambda と Worker が
別々に出る #263 の形とは違う）。

## M9 共有ハブ

**M8 が「1 枚の画面をどう見せるか」を解いたのに対し、M9 は「画面がどう繋がるか」を解く。**

そこへ至る道は SNS で共有された URL しかない。**URL を知っている人しか作品へ着けない状態**は、
#152 が `/works` について解いた問題が、公開側にそのまま残っていたものである。

**構造の正本は仕様 2.3 である。** 以下の issue はそこから導かれるもので、**ここへ複製しない。**

### 決めてから起票した 5 点（intake / 2026-09-05 / #326）

| 決めたこと | 決めた内容 |
|---|---|
| 一覧の綴り | **`/works` を公開作品の一覧にする。** 自分の作品は `/works/mine` へ移す（同じものに綴りを 2 つ作らない） |
| トップ | **D1 を読む。** 3.6 の「読まない」を 3 条件付きで解禁（件数の固定・索引・Cache API） |
| 並べ替え | **新着と「改造された数」の 2 軸だけ。** `fork_count` を読むだけで済み、書き込みが 1 行も増えない |
| 持たないもの | **いいね・プレイ数・タグ・キーワード検索。** 見直しの契機は公開 100 本（2.3.8） |
| 置かないもの | **お知らせ・会社情報・SNS・お問い合わせ**（行き先が実在しない） |

### 実装が最初に当たる 2 つ（起票時に判明。先に書いておく）

1. **`games` に `status` と `published_at` の索引が無い。** いまの索引は `parent_id` /
   `author_id` / `artifact_key` の 3 本だけで、「公開作品を新しい順に 20 件」は全表走査になる。
   **読み取り行数が開設以来の全作品数に比例する形**であり、2.3.3 の条件 2 はこれを指している。
2. **Cache API に載せるのは HTML ではない**（2.3.3 の条件 3）。理由が 2 つあり、**どちらも
   同じ結論を指す**。(a) **ヘッダはログイン状態で出し分かれる**（2.3.7）ので、HTML を丸ごと
   共有キャッシュへ載せると未ログインの閲覧で作られた HTML がログイン済みの利用者へ配られる。
   (b) `src/routes.ts` の `html()` は `cache-control: no-store` を固定で付けており（引数で
   上書きできない）、`caches.default` はその応答を保存しない。**したがって `html()` は
   触らない**——合成したキーの下に**引いたデータだけ**を置き、HTML は毎回そのリクエストの
   ログイン状態で組み立てる。

### M9-1 サイト構造を情報設計として確定する
- **goal:** 共有ハブとしてのサイトマップ・URL 体系・各画面の要素を仕様の決定として確定し、以後の実装 issue がそこから導ける状態にする。

## 起票時の共通事項

- 各 issue の本文には、本文書の該当節（goal / scope.in / acceptance / priority / 参照）をそのまま転記する。
- ラベルは既存の `enhancement`（実装）、`documentation`（M0 の確認タスクと M6-5）を使う。新規ラベルは作らない。
- issue 本文に機密（`.env` の値、`GH_TOKEN`、R2 認証情報、OAuth クライアントシークレット）を含めない。
- 依存関係は issue 本文の「依存」行で示す。GitHub の依存機能は使わない。
