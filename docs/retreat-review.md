# 撤退条件の判定

**仕様書 10.3 が定めた撤退条件を、判定日に迷わず実行するための手順と、結果の記録先です。**

- 位置づけ: **手順と記録。** 条件そのもの（何を下回ったら撤退か）の正本は
  [product-spec.md](product-spec.md) 10.3 です。
- **閾値の数値は、この文書では 2.2 の判定コマンドの中に 1 度だけ現れます。** 散文へは
  書きません——**2 か所に置くと、10.3 が基準を緩めた日に片方が古くなります。**
  緩めるのは 10.3 が明示的に許している操作なので、**起こる前提**で置き場を 1 つにします。
  （1 度だけであることは `scripts/report-selftest.sh` が機械で見ます。）
- 10.3 は「基準が厳しすぎたと判断して後から緩めるのは構わない。**決めていない状態のみが
  危険**」と書いています。この文書は**決めていない状態を無くすため**のものです。

---

## 1. 開始日と判定日

### 開始日の定義: **M7 の完了日**

**M7 の完了条件（サンプル 10 本の公開を含む）を満たした日を「開始」とします。**

**#43（コールドスタート用サンプル 10 本）が揃って初めて、「招待された人が改造する対象」が
存在します。** 11.3 がその 10 本を「ツッコミどころと改造余地のある初期サンプル」と位置づけて
いるとおり、フォーク率の分母も分子も、対象が無ければ意味を持ちません。

> **これは基準を緩める操作ではありません。** 10.3 の 2 つの条件はどちらも動かして
> いません。**測る期間の定義だけ**を決めています。

<!-- 判定日は M7 完了時にここへ書き込む。空欄のまま β を始めないこと。 -->

| 項目 | 値 |
|---|---|
| 開始（M7 完了の時刻。2.1 の `--since` に渡す値） | `2026-09-14T06:25:38+09:00`（**#43 の 10 本目「ネズミのカギ」の `games.published_at`**。M7-1（#42）と M7-3（#44）は 2026-09-03 に完了済みで、**#43 が M7 の最後の 1 件だった**。照合は本番の D1 の読み取りで行った） |
| 判定日（開始の 3 ヶ月後） | **2026-12-14**（JST） |

**開始の時刻の値は、上の表のこの 1 か所にだけ置きます。** 2.1 のコマンドは、この行から値を
読んで `scripts/kpi-report.sh` へ渡します。**スクリプトにも、この文書の散文にも書き写しません**
——2 か所に置くと、片方だけを直した日に、判定が古い境界で数えられます
（1 か所であることは `scripts/report-selftest.sh` が機械で見ます）。

**境界は秒の単位で、日に丸めません**（#456）。開始の日の 0 時で切ると、同じ日の開始前に
作ったサンプルづくりの行が勘定に入ります。数えるのは**開始より後に作られた作品**です
（`created_at` が開始の時刻を含まずに後）。

- **フォーク率:** 開始より後に作られた作品だけで数えます。**開始前の作品（サンプル）への
  フォークも、開始より後に作られていれば数えます**
- **3 世代以上の系統:** 開始より後に作られた作品が 3 世代目以降にいる系統を数えます。
  **根は開始前でもかまいません**——根で切ると、サンプルから伸びた系統が 1 本も数えられません
- **生成に失敗した作品（`generation_state = 'failed'`）は、どちらにも数えません**
  （10.1 の「作品を生まない試行」）

**空欄のまま β を始めないこと。** 空欄で始めた瞬間に、10.3 が名指しした「決めていない状態」へ
戻ります。

### なぜ「最初の招待使用日」を採らなかったか

台帳から機械的に導ける値ではありますが（2026-08-27）、**判定期間に作りかけの 1 ヶ月以上を
含みます。** その期間にはサンプルも招待もありませんでした。**サンプルが無い期間のフォーク率を
撤退の根拠に含めることになる**ため、採りません。

## 2. 判定の手順

### 2.1 数を取る

```bash
set -a; source scripts/load-project-env.sh; set +a
since="$(grep -E '^\| 開始（M7 完了の時刻' docs/retreat-review.md | grep -oE '[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}[+-][0-9]{2}:[0-9]{2}')"
bash scripts/kpi-report.sh --remote --format json --since "$since" > /tmp/kpi.json
jq -e '.since.epoch' /tmp/kpi.json
```

**開始の時刻は 1 章の表から読みます**（値をここへ書き写さないため）。表から読めなかったとき
（行の見出しを変えた等）は、`kpi-report.sh` が**空の値や形の違う値を受け付けずに 2 で
落ちます**——期間を指定しないまま全期間で数えることにはなりません。最後の `jq -e` は、
**出力が開始の時刻で絞られていること**を確かめます（絞られていなければ `null` で 1 を返します）。

**10.3 の 2 指標は、どちらも M7-1 の出力だけで賄えます**（2026-09-04 に実測で確認）。
**別の集計を書き足す必要はありません。**

| 10.3 の条件 | 読む場所 |
|---|---|
| フォーク率の条件 | `.forkRate.rate` |
| 3 世代以上の系統の条件 | `.deepLineages.count` |

### 2.2 判定する

```bash
jq -r 'if .forkRate.rate == null then "判定不能" elif .forkRate.rate < 0.40 then "該当（撤退側）" else "非該当" end' /tmp/kpi.json
jq -r 'if .deepLineages.count == 0 then "該当（撤退側）" else "非該当" end' /tmp/kpi.json
```

**「判定不能」を「非該当」に倒さないこと。** `forkRate.rate` は作品が 0 件のとき `null` に
なります（`scripts/kpi-report.sh`）。**0% ではありません。** 0% と「まだ 1 本も無い」は別の
状態で、後者は判定できる状態にありません。

### 2.3 数え方の落とし穴

**系統は `status` ではなく `parent_id` で数えています。** 本番には真ん中が `removed` の
3 世代系統が実在し、**「公開済みだけ」で数えるとその系統が勘定から消えます**
（`docs/usage-report.md`）。`kpi-report.sh` はそう数えており、変異でも確かめてあります。

**フォーク率の分母は「新規生成数＋フォーク生成数」であって「全生成数」ではありません**
（10.1 の v1.35 注記）。推敲を分母へ入れると、**フォークが健全に起きていても 10.3 の
下限を割ります。**

## 3. 判定の記録

**判定日に、下の表へ 1 行追記します。追記のみで、過去の行を書き換えません。**

**判定した結果は、条件に該当したかどうかに関わらず残します。** 「該当しなかったので何も
書かなかった」を許すと、**次の判定のときに「前回どうだったか」が分からなくなります。**

| 判定日 | フォーク率 | 3 世代以上 | 該当した条件 | 決定 | 備考 |
|---|---|---|---|---|---|
| （未実施） | | | | | |

**決定の欄には「継続」「縮小」「中止」「基準の見直し」のいずれかを書きます。**
10.3 は「基準が厳しすぎたと判断して後から緩めるのは構わない」としているので、
**「基準の見直し」も正当な決定です。** ただし**見直したこと自体をこの表へ残します**
——残さないと、基準が動いた事実が消えます。

## 4. 判定日より前に見ておくとよいこと

**判定日に初めて数を見ると、打つ手が無くなります。** 途中で見る分には枠も費用も動きません
（`kpi-report.sh` は読み取りのみ）。

### 2026-09-04 時点の数（参考。判定ではありません）

**#456 より前の数え方です。** 全期間で数えており、生成に失敗した作品も含みます。

| 指標 | 値 |
|---|---|
| フォーク率 | **25.9%**（フォーク 7 / 新規 20 ＝ 全 27 作品） |
| 3 世代以上の系統 | 1 本 |
| 利用者 | 3 人 |
| 待機リスト | 0 件 |

**この数で判定してはいけません。** 開始日（M7 完了日）より前であり、サンプル 10 本も
招待の配布も行われていません。**利用者 3 人は開発と試用の分です。**

> **フォーク率が既に 10.3 の下限を割っていること自体は、事実として見ておく価値があります。**
> 「β を始めたら上がる」という見込みが外れた場合に備え、**判定日を待たずに手を打てる
> 余地がどこにあるか**を考える材料になります。
