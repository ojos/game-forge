# レビューワークフロー

AI によるコードレビューを、無限修正ループに陥らせずに機能させるための規範です。

## 目的

実装 AI と レビュー AI の間で「指摘 → 修正 → 別の指摘 → 修正」が終わらなくなる状態を防ぎます。
そのために、**ローカルで異なるモデルによる二段ゲートを通し、リモートのレビューは最終ゲートとして 1 回に絞ります**。

## 前提: 同一モデルの自己レビューは盲点を共有する

実装したモデル自身によるレビューは、実装時と同じ前提・同じ見落としを引き継ぎます。
このため、**別ベンダーのモデルによる独立したクロスチェック**を組み合わせます。ベンダーが異なるほど、指摘の観点が重複しにくくなります。

この規範は特定のベンダーに依存しません。実装を担うモデルと、第二意見を担うモデルが**異なるベンダーであること**のみを要求します。

## 品質整理（任意の前段）

主レビューの前に、実装したモデル自身が差分のコードを 1 回だけ整理してよいものとします。観点は再利用・簡素化・効率化で、バグの探索はここでは行いません（主レビューの役割です）。
レビューへ渡す差分を先に小さくし、文書や実装の重複を早い段階で減らすことが狙いです。

- **位置は、受け入れ条件を満たした後、主レビューの前です。** 主レビュー・第二意見の後には行いません。レビュー済みの差分が書き換わり、ゲートの緑が実質的に無効になるためです。
- **整理でコードが変わるため、受け入れ検証は整理後の差分に対して改めて通します。** 整理前の緑は、整理後の差分の緑を意味しません。ローカル事前ゲートの受け入れ検証が、この再実行を兼ねます。
- **回数は 1 回です。** 結果を比べるための再実行はしません。「もっと簡単にできる」という余地は尽きないため、回すたびに差分が動き、収束しなくなります。
- **ゲートにしません。** 合否を判定せず、ローカル事前ゲートの単一入口にも含めません。改善の余地に終わりが無い以上、機械的な合否を定義できないためです。整理を省いても push は妨げられません。
- **対象はコードに限ります。** 規範文書・README 等の文章は対象外です。文章を簡素化すると、規則に添えた理由（「〜のため」）が削られ、規則だけが残るためです。
- 下記「両段に共通する制約」の「指摘外の自律的リファクタリングを追加で行わない」は、レビュー指摘を受けた後の修正に掛かる規則です。この前段はレビューより前の工程なので抵触しません。逆に、レビュー後にこの前段を持ち出して整理を行うことは、同規則に反します。

起動手段はプロジェクト層で定義します。

## ローカル事前ゲート（push 前）

### ① 主レビュー

実装したモデル自身で、ステージ済み差分をレビューし、その場で修正します。
セキュリティに関わる差分は、セキュリティ観点のレビューも行います。

### ② 第二意見

別ベンダーのモデルで独立にクロスチェックします。
リモートのレビューが出しがちな別視点の指摘を、push 前に先取りすることが狙いです。

**起動方法はプロジェクト層で定義し、参照できる状態にしておきます。** 「別モデルでレビューする」とだけ書かれ、何をどう実行するのかが定義されていない規範は、実行されません。

必要な条件は次の 3 点です。

- 実装を担当したモデルとは**別ベンダー**であること
- 差分を渡して**非対話で実行**でき、結果を機械的に判定できること
- 重大な指摘が無いことを機械的に判定できる形で返すこと。返し方は次の 2 通りを認めます。
  - **出力の最後の行に一意な判定トークンを置く**（例: 最後の行へ `VERDICT: LGTM` と書かせ、指摘があるときは別のトークンを書かせる）
  - **回答の形をスキーマで強制し、指摘の種別（category 等）から判定を導出する**（ツールが構造化出力の強制に対応する場合に限る。下記「第二意見の非決定性」の該当節）

具体的なコマンド、モデル、認証情報の扱いはプロジェクト層で定めます。この文書ではベンダーを指定しません。

**報告できる範囲と、通過を落とす範囲は区別します。** 第二意見が報告してよい内容を、下記「両段に共通する制約」が定める 4 点より広げてもかまいません（例: 参照した issue / PR の状態と実際の変更が食い違う点）。ただし**通過を落とすのは、その 4 点に該当する指摘がある場合のみ**です。4 点の外の報告は、通過判定を動かさない参考情報として扱います。

### 両段に共通する制約

- **対象は致命バグ・脆弱性・型エラー・エッジケース見落としのみ**とします。
- 好みのリファクタ・命名・可読性の軽微提案は、ゲートの対象外とします。
- 両段で重大な指摘がなければ push 可とします。
- **レビュー指摘への修正は 1 イテレーションで完結させます。指摘外の自律的リファクタリングを追加で行いません。**
- 指摘が事実誤認だった場合の扱いは、下記「指摘の却下」に従います。

### 第二意見の非決定性

第二意見は**非決定的**です。同じ差分でも実行のたびに結果が変わり、指摘内容も一定しません。実測では、同一コミットに対する 4 回の実行が LGTM 2 回・指摘あり 2 回に分かれました。

- **1 回の LGTM は「重大な指摘が無いこと」の証明ではありません。** 通過はあくまで確率的な結果です。
- したがって第二意見は**主レビューを省略してよい根拠になりません**。主レビューを飛ばして第二意見だけに頼らないでください。
- **同じ差分に対する実行回数 N を増やし、多数決で判定できるようにします。** 指摘を報告した実行が**過半数**（`floor(N/2)+1`）に達したときだけ落とします。既定は 1 回で、この場合は閾値も 1 になり、1 回実行と同じ挙動になります。回数の指定方法（環境変数・引数など）はプロジェクト層で定義します。
- 過半数を採るのは、誤検出 1 回でゲートが止まると毎回反証が必要になり、ゲート自体が無視されるようになるためです。**少数回しか現れない指摘は通過します。**これは意図した妥協で、上記のとおり第二意見を補助と位置づけることで受け入れます。
- 過半数に届かなかった指摘も出力には残ります。確認したうえで採否を判断してください。

**回数を増やしても消えない故障があります。** 多数決が効くのは、ぶれが実行ごとに独立して現れる場合だけです。出力の形が毎回同じように崩れる故障は、回数では救えません。

実測では、モデルが回答の前に「これから何をするか」という作業ナレーションを 1 行出したために、指摘が 1 件も無いのに 3 回の実行すべてが「指摘あり」に分類されました。**却下の手順も使えません。** 却下は事実誤認の指摘を人間が退ける規則であり、このときは却下すべき指摘そのものが存在せず、分類が誤っています。

この故障は、**出力の最後の行に置かれた判定トークンを解析する方式に固有**です。

- **通過の判定は、出力全体の一致ではなく、出力の最後の行に置かれた判定トークンで行います。** 全体の一致を要求すると、前置きが 1 行出ただけで偽の赤になります。
- **判定トークンの存在を「含むこと」で判定しません。** 指摘と併記された通過トークンをそのまま通し、重大な指摘が push まで抜けます（上記「両段に共通する制約」の趣旨に反します）。
- **判定トークンが無い出力は指摘ありとして扱います。** 指示に従わなかった出力を通すと、判定していないものを緑として報告することになります。ただしその場合は、指摘本文と区別できる形で「トークンが無い」ことを示します。原因が読み取れない赤は、偽の赤と同じようにゲートへの信頼を削ります。

**回答の形をスキーマで強制し、指摘の種別から判定を導出する方式（上記「② 第二意見」の該当節）を使えるツールでは、この故障クラスは構造的に起きません。** モデルに判定そのものを出させず、出力全体を解析して判定トークンを探す工程自体が無いため、ナレーションが先に付いても判定が化けません。構造化出力を強制する手段を持たないツールでは、上記の「出力の最後の行」方式を使い、同じ対策（全体一致にしない・含むことで判定しない・トークン無しは指摘ありとする）を保ちます。

**「読めなかった」を「指摘なし」に倒してはいけません。** スキーマ方式では、JSON として読めない回答・形を満たさない回答・スキーマに無い種別の回答は、いずれも失敗として扱います。読めなかったものを緑として報告すると、レビューしていないものを通すことになります。

**差分そのものを読めなかったと答えた回答も、指摘の中身によらず同じ扱いにします。** ツールの実行が失敗するなどで差分を読めなかった事実を、指摘の 1 件（通過判定を動かさない種別）として報告しただけの回答を緑にすると、読んでいないものがレビュー済みとして記録されます。これを防ぐには、差分を実際に読んでレビューできたかどうかを回答の必須項目として答えさせ、読めなかったと答えた回答は指摘の中身を見る前に落とし、通過を示す判定（出力の最後の行の判定トークン、または完了を示す行）を出さないようにします。判定に到達したことを記録の契機にしている場合、この行を出さないことがそのまま「記録を残さない」ことに繋がります。

## 並列実装後の統合検証

複数のレーンで並列に実装した場合、レーン単体の緑は統合後の緑を意味しません。
統合したツリー上で、**各レーンの受け入れ条件をすべて再実行してから**先へ進めます。

### 統合パスだけでは漏れる

実測では、8 レーン並列の統合で 3 件、3 レーン並列の統合で 5 件の統合欠陥が出ました。
いずれも**レーン単体の受け入れ検証は緑**で、マージの機械的な衝突検査も衝突を報告していません。

原因はすべて同一で、**文書が実装の一覧を書き写している**構造でした。
一方のレーンが実装側へ項目を足し、他方のレーンが同じ一覧を別の理由で書き換えると、
どちらのレーンも自分の中では整合しているため単体検証を通過します。
編集した行が重ならなければ、テキストの衝突検査も何も報告しません。
一覧が実装に追随していない状態は、統合したツリー上で初めて成立します。

衝突検査が見るのは**同じ行を触ったか**であって、**内容が整合しているか**ではありません。
この差が、レーン単体の緑と統合後の緑を分けます。

### 工程

1. すべてのレーンを取り込んだ統合ツリーを作ります。
2. そのツリー上で、**各レーンの受け入れ条件をすべて再実行します**。自レーン分だけの再実行にしません。
3. 落ちた場合は統合ツリー上で修正します。レーンへ差し戻しても、そのレーン単体では再現しないため、修正の妥当性を確認できません。
4. 全通過してから、次の段へ進みます（リモート最終ゲートを置いているなら下記「リモート最終ゲート（任意の層）」、置いていないなら push・PR 作成。どちらでも push 後に第二意見の記録を投稿する）。

### 目視の照合を工程にしない

統合後に人が一覧を目視で突き合わせる運用は漏れます。
上記 8 レーンの回では、3 件のうち 1 件が統合後の目視照合をすり抜け、リモート最終ゲートで初めて検出されました。

一覧の照合は、目視ではなく**機械照合で担保します**（[shared-ai-rules.md](shared-ai-rules.md) の「機構化の判断基準」）。
統合検証は、その機械照合を統合ツリー上で再実行する工程として位置づけます。

## リモート最終ゲート（任意の層）

push / PR 作成後にリモート側の機構を 1 段挟むかどうかは、**プロジェクト層が選ぶ任意の層です。** この規範はベンダーも手段も指定しません。

### 常に置く標準の機構層

リモート最終ゲートを置くかどうかにかかわらず、次の 2 つを標準の機構層として置きます。リモート最終ゲートは、この上に足す層です。

- **第二意見の記録と確認側**（上記「② 第二意見」）。push 前に回した第二意見の出力を記録に残し、確認側が push 後の別の契機（PR 更新・定期実行）から、その head に紐づく記録があることを確かめます。要求はしません——第二意見を回すかどうかは著者側の判断のままです。置く場合も置かない場合も、記録の投稿は著者側の手順に含めます。
- **CI による受け入れ検証の再実行。** push した差分に対して、受け入れ条件をもう一度機械的に走らせます。

### 置かない場合

上記の標準の機構層だけで運用します。リモート最終ゲートが買っていた性質のうち、置かない場合に失うものは次のとおりです。

| 性質 | 置かない場合 |
|---|---|
| (a) 著者の操作なしに記録が作られる | ❌ 投稿するのは著者側 |
| (b) 記録を著者が消せない | △ 部分的（「書かない」から「消す」へ変わる。削除は意図的な行為として見える） |
| (c) 記録が無いことを検出できる | ✅（確認側が head SHA と照合する） |
| (d) 内容が著者を通らない | ❌ ローカル実行では原理的に無理 |

**偽造はできます。** レビューを回さずに記録だけを作って投稿すれば通ります。検出できるのは失念であって、迂回ではありません。この性質で足りるかどうかは、プロジェクトの事情（外部からの PR を受け付けるか、著者をどこまで信頼するか）によって変わります。足りない場合は、下記「置く場合」に従ってリモート最終ゲートを置いてください。

### 置く場合

リモート最終ゲートを置く場合は、次の規律に従います。「要求と確認を 2 本で 1 組にする」「1 回だけ要求する」「要求された ≠ 読まれた」は、置く場合に適用する規範です。

- push ごとの自動フルレビューには依存しません。**1 回だけ要求する**運用とします。
  - 守りたいのは「手動であること」ではなく**要求回数を 1 回に限定すること**です。回数が 1 回に限定されるなら、手動要求でも機構による自動要求でもかまいません。
  - 機構で自動要求する場合は、**再要求されないイベントに限定します**（例: `pull_request` の `opened` のみを契機とし、`synchronize`（push 更新）では再要求しない）。これにより「1 回だけ」を運用者の記憶に頼らず機構で保証します。
  - **失敗時にジョブの中で再試行することは、この規則が禁じる対象ではありません。** 禁じているのは要求が**別のイベント・別の契機から重ねて出て二重要求になること**です。1 回の起動（1 イベント）の中で、成功するまで・または上限に達するまで試すのは、外から見た要求を依然として 1 件に保ったままの挙動であり、「1 回だけ」を壊しません。要求側は空レスポンス等で間欠的に失敗することがあり（実例: `copilot-review.yml`）、再試行を欠くと 1 回の間欠故障がその PR から要求の機構を恒久的に奪います。再試行を尽くしても失敗した場合は、下記「要求の失敗を握り潰してスキップにしません」に従い、黙って緑にせず実行を落とします。
  - **ただしこれは「再送が重複を生まない」ことを確かめてから再送する場合に限って成り立ちます。** 呼び出しが失敗として返っても、それは応答の解析に失敗しただけで、要求自体はサーバ側に届いて成立している可能性があります（実例: `gh` が `unexpected end of JSON input` を返す空レスポンス）。この区別を付けずに無条件で再送すると、1 回のつもりの要求が実際には複数回記録され、レビューが重複して起動しえます——それは「1 回だけ」をこの再試行自身が壊すことに等しくなります。**再送する前に、直前の要求が既に成立していないかを別の記録（例: `issues/{pr}/timeline` に残る `review_requested` イベント）で確かめ、成立していれば再送せずに成功として扱います。** 確かめられなかった場合は「まだ要求されていない」と同一視せず（下記「確認できなかったこと」と同じ考え方）、多重要求の危険を避けて再送しない側に倒すか、少なくともどちらに倒したかを判断根拠とともに記録します。
- **重大でない指摘**は、次のいずれかを満たせば解決済みとして扱い、マージしてよいものとします。
  - CI がすべて通っている
  - 指摘が今回の差分外の既存コードに対するものである（スコープ外）
  - 指摘が命名・可読性・好みのリファクタ提案である（技術負債として記録した上でマージ）
  - 指摘が事実誤認であることを実測で示せる（下記「指摘の却下」に従って記録する）
- **重大な指摘は、この列挙の対象外です。** 致命バグ・脆弱性・データ破壊・正しさ（型エラー、エッジケースの見落としを含む）に関わる指摘は、CI が通っていても解決済みになりません。**直すか、下記「指摘の却下」に従って実測で却下するまで、マージしません。** CI は指摘が述べる故障モードを検査しているとは限らず、緑であることはその指摘が誤りである証拠にならないためです。打ち切りの規則は軽微な指摘で AI 同士を往復させないためのもので、重大な指摘を素通りさせるためのものではありません。
- **2 巡目以降の軽微な指摘は人間が却下します。AI 同士を往復させません。**

### 要求されたことを別の契機で確認する

機構で自動要求する場合、**要求する機構とは別に、要求されたことを確認する機構を置きます**。

- **契機は届かないことがあります。** ある利用プロジェクトの実運用では、連続する 2 日間に開いた 6 本の PR のうち 2 本で、`pull_request` の `opened` が届かず自動要求のワークフローが起動しませんでした。設定の誤りではなく、イベント配信の取りこぼしです。起動しなければエラーも出ず、他のチェックは緑なので、**最終ゲートだけが黙って抜けます。**
- **`opened` を見る 2 本目のワークフローでは塞げません。** 届いていないのはイベントそのものなので、同じ契機を見る側も同じように起動しません。**別の契機が要ります。** 確認側は、要求側と同じ契機に加えて、PR 更新（`synchronize` 等）と**定期実行**を張ります。定期実行は「開いたきり触っていない PR」を拾う最後の担保です。
- **確認側は要求しません。** 確認側も要求すると、「1 回だけ要求する」が 2 か所から壊れます。要求と確認は別の機構に分けます。
- **判定は head コミットの status として出します。** ジョブの成否だけでは、定期実行から見た PR に何も現れません（その実行が PR に紐づかないため）。status にすれば、どの契機から判定しても同じ場所（PR のチェック欄）に出ます。
- **要求側と同時に走る契機だけ、猶予を置いてから判定します。** 待たずに見ると、要求が届く前に「要求されていない」と判定します。
- **「いまの状態」だけを判定材料にしません。** レビュアーの要求一覧が返すのは現在の状態で、**レビューが始まった時点でそこから消えることがあります。** ある利用プロジェクトの実運用では、要求の 7 秒後に要求一覧から消え、指摘が投稿されるまでの約 3 分間、要求一覧にも投稿済み一覧にも現れませんでした。同じ日に開いた PR 2 本がともにこの窓の中で判定され、**要求は成功しているのに「要求されていない」で赤が出ています。**
- **この窓は猶予では塞げません。** 猶予が待っているのは「要求がまだ出ていない」場合で、この窓は要求が出た**後**にあります。猶予を延ばすほど、窓の中で判定することになります。
- **「起きたこと」の記録を判定材料に加えます。** 要求されたという出来事は、レビューがどこまで進んでも消えません。状態と違って進行に左右されないため、上記の窓を塞げます。
- **取り消しを勘定に入れます。** 出来事が残っていることだけを見ると、要求してすぐ取り消した PR も「要求された」になり、**要求を出して消すだけでゲートが外れます。** 出来事は時系列で並ぶので、同じ相手について最後の 1 件が要求であるときだけ、要求が生きているとみなします。
- **呼び出す先の権限は宣言します。** 隣接する系統の権限でたまたま読めることが実測されていても、宣言を省くと、提供側の扱いが変わった日に判定が全 PR で出なくなります。
- **確認できなかったこと（API から読めない等）を「要求されていない」と同じに扱いません。** 一時的な不調で赤が出ます。逆に握り潰して緑にすると、確かめていないものを通したことになります。判定を保留し、次の契機へ持ち越します。
- **required check にはしません。** レビュー機構側の遅延や障害でマージが止まる副作用があるためです。ここで止めたいのは「要求されていないことに気づかないまま通ること」だけです。
- **要求の失敗を握り潰してスキップにしません。** リモート最終ゲートが実行されていないのに緑を出すと、偽の緑と通過の区別が付かなくなります。間欠的な失敗に対しては上記のとおりジョブの中で再試行してよく、それでも失敗した場合は切り分け手順を出力し、実行を落とします。

### 要求された ≠ 読まれた

「要求されたことを別の契機で確認する」は、要求と投稿が記録として残っていることを見ます。**それだけでは、投稿されたレビューに中身があることまでは保証しません。**

- **原因は配信側にあります。** レビュー機構（例: GitHub の API）は、1 ファイルの差分が大きすぎるとレビュー対象の差分そのものを返さないことがあります。行数では決まりません。巨大な 1 行を書き換えると、その行だけの差分が閾値を超えることがあります。
- **配信できない対象でも、レビュー機構は要求どおりに動きます。** 差分を受け取れないファイルしかない PR に対しても、レビューは投稿されます。ただし中身は「1 行も読めなかった」という趣旨の定型文だけになります。要求も投稿も記録としては正しく残るため、**「要求されたか」だけを見る確認は、この状態でも緑を出し続けます。** ある利用プロジェクトの実運用では、この形で複数本の PR が緑のまま通過し、最初の 1 本から気づくまで 3 日かかりました。
- **2 段で見ます。** 片方だけでは取りこぼします。
  1. **原因そのもの**（配信できる差分があるか）—— レビューが届く前でも判定が確定します（返事を待っても変わらない事実であるため）。ただし配信側の挙動が変われば意味を失います。
  2. **最後の砦**（投稿されたレビューが定型文だけでないか）—— 1 段目をすり抜けても拾えます。ただしレビュー側が文面を変えれば静かに効かなくなります。
- **判定コードは、判定対象と同じ木から取りません。** 確認側のワークフローが PR のブランチから判定スクリプトを取得すると、PR の投稿者がスクリプトを書き換えるだけでゲートを常に緑にできてしまいます。判定コードは常に既定ブランチなど信頼できる場所から取得します。
  - **例外は、既定ブランチに判定コードがまだ無い場合だけです。** この機構自体を初めて導入する PR（確認側のワークフローと判定スクリプトを同じ PR で足す場合）は、判定コードがまだ既定ブランチに存在しません。このときに限り PR 側の写しへフォールバックしてよいものとします。守りたいのは「既定ブランチにある判定コードを PR が差し替えられないこと」であり、既定ブランチにまだ無い状態はその対象外だからです。かつこの状態は PR からは作れません——既定ブランチから判定コードを消すには、その削除自体が別のレビューを通る必要があります。フォールバックしたことは、確認側の出力（status の description・`::notice::` 等）へ必ず明示します。黙って PR 側のコードで判定すると、既定ブランチの版で判定したと読み違えるためです。
  - **この例外にも限界があります。** 判定コードそのものを変更する PR は、その変更を PR 上で検証できません（フォールバックが使われるのは「既定ブランチに無い」ときだけで、既に存在する判定コードを更新する PR ではフォールバックせず既定ブランチの旧版で判定されるため）。変更の効果はマージ後、次の実行で既定ブランチの新しい版が使われて初めて確認できます。
- **判定は確認側のワークフロー（`.yml` 等）へ埋め込みません。** そこでしか実行できない形にすると、「特定の入力で正しく落ちるか」のような受け入れ条件を、実際に PR を立てる以外の方法で確かめられなくなります。判定は独立したスクリプトへ切り出し、確認側は一覧を集めて渡し、結果を status へ書くだけにします（[shared-ai-rules.md](shared-ai-rules.md) の「機構化の判断基準」と同じ考え方）。

### この機構が保証すること／しないこと: run: ブロックそのものの書き換え

上記の「判定コードは、判定対象と同じ木から取りません」は `scripts/review-usable.sh` を守ります。ですが `pull_request` 契機では、GitHub が実行するワークフロー定義そのもの（`review-gate.yml` の `run:` ブロック）を、**同じリポジトリの PR は自分の版で置き換えられます**。判定コードの出所を既定ブランチへ固定しても、それを呼び出す側のロジックが PR 側の版で動く以上、`statuses: write` の権限を保持したまま `run:` を書き換えて緑を捏造できます。

- **`pull_request` 契機の判定経路は、被検査対象である PR に握られています。** GitHub は同一リポジトリの PR に対して PR 側の版のワークフロー定義を実行するため、`run:` を書き換えるだけで判定を経ずに `success` を書けます。
- **`schedule` 契機は既定ブランチの版で実行されます。** 定期実行は常に既定ブランチのワークフロー定義を取得するため、PR 側の書き換えはここには届きません。**この契機は open な PR のうち、フォークではない（同一リポジトリの）ものを全件、既定ブランチの判定ロジックで判定し直します。** フォークからの PR は要求側（copilot-review.yml）と同じくここでも対象外であり、この上書きの保証はフォークからの PR には及びません。（実測: 手動 dispatch した `schedule` 相当の実行が、起動した契機とは別の PR まで再判定し、status を書き換えることを確認しています。）
- **したがって、同一リポジトリの PR について `pull_request` 契機で緑を捏造しても、捏造された status は次に `schedule`（`cron: '*/20 * * * *'`）が実行されたときに上書きされます。** この性質は既に存在しており、この文書が明文化するまで書かれていませんでした。
- **ただし「次の実行」の時刻は保証されません。** cron は定刻の実行を保証するものではありません。GitHub 側のスケジュール遅延・欠落や API エラーが起これば、捏造された `success` は次に `schedule` が実際に走るまで残り続けます。それまでにマージすれば通ります。**この窓は塞がず、承知のうえで受け入れます。** 塞ぐには信頼境界の設計変更（再利用可能ワークフローを既定ブランチ参照で呼ぶ、判定を `schedule` 実行だけに限る等）が要り、このゲートのスコープを超えます。

## 指摘の却下

主レビュー・第二意見・リモート最終ゲートのいずれについても、**指摘が事実誤認であることを実測で示せる場合は、人間の判断で却下してよい**ものとします。

AI のレビューは事実誤認の指摘を出します。第二意見に限った話ではなく、リモート側のレビューでも起こります（上記「第二意見の非決定性」）。却下の根拠が規範に無いと、採れる手は次の 3 つに限られます。**いずれも規範の意図に反します。**

- **存在しない不具合の修正を入れる。** 実測と矛盾する説明がコードに残り、次に触る人を誤らせます。
- **ゲートを迂回して通す。** 記録の上で、通したのか迂回したのかが区別できなくなります。
- **指摘が出なくなるまで再実行する。** 非決定性に賭けるだけで、何も確かめていません。

却下は打ち切り規則の一部です。「2 巡目以降の軽微な指摘は人間が却下する」と同じ理由で、**反証の往復を無限に続けないため**に置きます。

### 却下には記録を伴わせます

**再現手順と実測結果を残さない却下を認めません。** 「事実誤認だから」を主張だけで通せるようにすると、この条件がそのまま抜け道になります。却下の正しさは、後から第三者が確かめられる形でだけ担保できます。

- 何を実行し、何が観測されたかを、**同じ手順で再現できる形**で残します。
- 指摘が述べる故障モードが**起きないこと**に加えて、**同じ位置で実際にそれが起きる条件**（対照）も示せると、誤りの所在がはっきりします。「起きなかった」だけでは、確かめ方が間違っていた可能性を排除できません。
- 指摘の前提が誤っていても、**指摘が示唆する対処には価値がある場合があります**。前提の誤りを理由に対処ごと捨てません。却下と採否は別に判断します。
- 記録の置き先はプロジェクト層で定めます。

## この規範が守るもの

レビューの価値は、指摘の網羅性ではなく**収束すること**にあります。
網羅性を上げるほど往復が増え、往復が増えるほど人間の判断が遅れます。
上記のスコープ限定と打ち切り規則は、その交換条件を明示的に固定するためのものです。
